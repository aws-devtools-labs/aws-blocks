# AWS CDK Blocks SQL Application

Backend-only TypeScript API on a PostgreSQL database — the CDK Blocks
`Database` Building Block on Aurora DSQL. Relational modeling with foreign keys,
transactions, and version-controlled SQL migrations. No frontend included.

## Getting Started

```bash
npm run dev         # Local dev server on http://localhost:3001 (long-running)
npm run test:e2e    # Run end-to-end tests against the dev server
npm run sandbox     # Deploy to AWS sandbox (Aurora DSQL)
```

## What's Included

- **`cdk-blocks/index.ts`** — a relational **notebooks → notes** API: create/list
  notebooks, add/list notes, and delete a notebook (with its notes, in one
  transaction). Every query is parameterized via the `sql` tagged template
  (injection-safe) and scoped to the signed-in user.
- **`cdk-blocks/migrations/main/`** — the schema as numbered `.sql` files, in a
  directory named after the `Database` block's id (`main`):
  - `001_create_notebooks.sql` — notebooks, unique name per owner
  - `002_create_notes.sql` — notes, foreign key to notebooks
- **Auth** — `Auth` (email + password; Amazon Cognito on AWS) gates every
  method; callers sign up, confirm their email with a 6-digit code (printed in
  the `npm run dev` terminal locally), and their data is isolated by owner.

## The database

| Environment | Engine | Storage |
|-------------|--------|---------|
| `npm run dev` | PGlite (WASM PostgreSQL) with the Aurora DSQL rules | `.cdk-blocks/local/data/` (gitignored) |
| `npm run sandbox` / `npm run deploy` | Aurora DSQL | AWS, serverless, no VPC |

Migrations run automatically — on first query locally, and during the deploy on
AWS, before the new code goes live. Each file runs once. Add a migration by
dropping a higher-numbered `.sql` file into `cdk-blocks/migrations/main/`.

### Writing SQL for Aurora DSQL

Aurora DSQL is PostgreSQL-compatible with a few differences. The block checks
every migration file and every query against them at `npm run dev`, so SQL the
cluster would reject fails on your machine first, with a message that names the
fix. The ones you meet first:

- An index is built by an asynchronous job: write `CREATE INDEX ASYNC` (see
  `001_create_notebooks.sql`).
- There is no `SERIAL`: use a text or UUID key, as this template does, or
  `BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 65536)`.
- No triggers, extensions, or `TRUNCATE`.
- Transactions never wait on a lock. When two change the same rows, one commit
  fails with `DatabaseErrors.SerializationFailure`; pass `{ retryOnConflict: true }`
  to `db.transaction()` to run the callback again (see `deleteNotebook`).
- One transaction can change at most 3,000 rows.

Need triggers, extensions, or larger transactions? Put the block on an Aurora
PostgreSQL cluster instead:
`new Database(scope, 'main', { cluster: new DatabaseCluster(scope, 'cluster', { type: 'aurora' }) })`.
The query code stays the same; the migration files become plain PostgreSQL
(`CREATE INDEX` without `ASYNC`). Choose before the first deploy that holds real
data: the block does not move rows between clusters. See "Which cluster" and
"Migrations" in `npm run docs Database`.

## Commands

`npm run help` lists every command. `AGENTS.md` covers the development, test and deploy commands.

`npm run typegen` regenerates the secret and config key types; run it once and commit `.cdk-blocks/hosting-values.d.ts` before gating CI on `npm run typegen -- --check`.

After code changes, run `npm run typecheck`: `npm run test:e2e` does not type-check.

### RPC endpoint (local dev)

Tests and TypeScript callers import the typed client (`import { api } from 'cdk-blocks'`). Call the endpoint directly only to troubleshoot connectivity; `AGENTS.md` describes the request format, the error responses and the session cookie.

```bash
# JSON-RPC 2.0 at POST /cdk-blocks/api. Auth methods are on the auth namespace (authApi);
# every api method needs the session cookie of a signed-in user.
curl -X POST http://localhost:3001/cdk-blocks/api \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"api.listNotebooks","params":[],"id":1}'
```

## Adding a frontend later

This template is backend-only. To add a frontend, add `Hosting` to
`cdk-blocks/index.cdk.ts` (`npm run docs core -- --section Hosting`) and remove
`"frontend": false` from the dev server settings in `package.json` (`AGENTS.md`
describes them). For a wired example, scaffold the `react` template in another
directory and compare its `package.json`, `vite.config.ts` and
`cdk-blocks/index.cdk.ts`:

```bash
npx @aws-cdk-blocks/create-blocks-app my-app --template react
```

# Auth — Design

> **Status: published.** `@aws-blocks/bb-auth` is a published package, and `@aws-blocks/blocks` re-exports `Auth` and its helpers and types. It replaced `AuthBasic`, `AuthCognito` and `AuthOIDC` at the auth-unification cutover (see [MIGRATION.md](./MIGRATION.md)). This document was seeded by tasks D1/D2 and grew with each later task.

## Purpose

AWS Blocks ships three auth Building Blocks (`AuthBasic`, `AuthCognito`, `AuthOIDC`) that disagree on error names, on what `userId` means, and on how to choose between them. `Auth` replaces all three with one block configured through one options object, with email + password, social, generic OIDC and SAML as sibling keys.

Two properties are non-negotiable:

1. **Existing `AuthCognito` deployments survive the switch untouched, including signed-in sessions.** The CDK layer reproduces `AuthCognito`'s resource identity: child construct ids `pool`, `client`, `sessions`, `session-secret`, `group-<name>`; `userPoolName: this.fullId`; and no `GenerateSecret` on `client`. Changing any of these makes CloudFormation create a new resource and delete the old one. The class name is not part of the construct path or `fullId`, so renaming `AuthCognito` to `Auth` is identity-neutral.
2. **Unsupported calls are compile errors, not runtime surprises** (see [Mode gates](#mode-gates)).

## Structure: one base class, pluggable engines

`AuthCognito` today is two independent classes (mock and AWS) that each reimplement every method. `Auth` instead follows `AuthOIDC`'s shape: a shared base plus injected engines.

```
AuthBase  (extends Scope, implements BlocksAuth)
  owns:      session cookie + session store, AuthState builders, createApi(),
             RawRoute mounting, requireAuth / requireRole / checkAuth / getCurrentUser,
             validateUser dispatch, the runtime mode-gate backstops, error mapping
  delegates: NativeEngine        — native-cognito (AWS) | native-mock (local)
             FederationEngine[]  — one per provider: federation-direct | federation-hosted-ui | stub-idp
```

Federation engine selection is **per provider**, not per instance. That fixes a live `AuthOIDC` bug where one `cognitoFederated()` entry makes every co-declared provider unreachable.

| Entry (`exports` condition) | Today (D1/D2) | Replaced by |
|---|---|---|
| `default` / `types` → `index.mock.ts` | `AuthBase` (D5a) + the local user pool `native-mock` (D5b) + the direct federation engine and the stub IdP (D6a); hosted-UI providers answer an actionable `501` ("unavailable locally") | — (a hosted-UI shim, if ever) |
| `aws-runtime` → `index.aws.ts` | `AuthBase` (D5a) + the Cognito engine `engines/native-cognito.ts`: the sign-in core (D5c) and the full account + admin surface (D5c2; only `rememberDevice` is a `501`, a [known gap](#known-gaps-documented-not-built)); the direct federation engine (D6a, HTTPS only); the hosted-UI engine `engines/federation-hosted-ui.ts` (D6b) for social, SAML and `federateVia: 'cognito'`; a `stubIdp()` provider `501` ("local only"), or — only with `unsafeAllowDeployed: true` — the stub IdP itself, lazily loaded ([below](#deploying-the-stub-idp-unsafeallowdeployed-fx8)) | — (the CDK layer refuses to synthesize a `stubIdp()` provider without `unsafeAllowDeployed`) |
| `cdk` → `index.cdk.ts` | D3a: core identity, identical to `AuthCognito` (see [CDK layer](#cdk-layer)); `synthGuard` stubs. D3b: [hosted-UI federation](#hosted-ui-federation-d3b). D4: the [immutability guard](#immutability-guard-q5). FX2: [`validateUser`'s PreSignUp trigger](#validateuser-and-the-presignup-trigger-q10) | — |
| `browser` → `index.browser.ts` | throwing stub; never imports server code | D7 |

All four entries export the same names (`Auth`, `AuthErrors`, `isAuthError`, the provider factories `stubIdp` / `github` / `customOauth2`, `relayOrigin`, and the types), which `packages/blocks/src/conditional-exports.test.ts` enforces in both directions. The error vocabulary is re-exported from `@aws-blocks/auth-common`, never redefined.

**`AuthBase` is exported as a type only** (`export type { AuthBase }` from every entry; no runtime name, so the parity test is unaffected). It is the declared base of the mock and AWS `Auth`, so its public members *are* `Auth`'s public surface, and API Extractor needs it exported to document them (D5b removed the `ae-forgotten-export`). To keep the internal engine types out of the public API, the runtime layer is **not** a constructor argument: `AuthBase`'s constructor is `(scope, id, options?)`, and each entry registers its layer for its class with `defineAuthLayer(Auth, LAYER)` (`auth-base.ts`); the constructor looks the layer up from `new.target` (nearest registered ancestor, so an app's subclass of `Auth` works). `test-helpers.ts` registers a fresh subclass per harness.

### Session compatibility contract

The non-negotiable: an app switching `AuthCognito` → `Auth` with the same id keeps its signed-in users. `Auth` therefore uses **exactly** `AuthCognito`'s session layer, not `AuthOIDC`'s:

| Aspect | Contract (identical to `AuthCognito`) |
|---|---|
| Cookie name | `auth_<fullId>` in **every** runtime (one prefix, so a session also survives a mock↔AWS switch — this settles the `_` vs `-` question from D2) |
| Cookie value | `<sessionId>.<base64url(HMAC-SHA256(sessionId, secret))>`, verified in constant time |
| Cookie attributes | `HttpOnly; <D-007 SameSite/Secure/Partitioned>; Path=/; Max-Age=<session ttl>` (default 400 days), re-issued on refresh |
| Secret | AWS: the `session-secret` `AppSetting` child (same SSM parameter). Mock: `sessionSecret` in `.bb-data/<fullId>/state.json` (the file `AuthCognito`'s mock uses — D5b's mock engine must preserve that field) |
| Store | `KVStore` child `sessions` (table / mock dir `<fullId>-sessions`); key = 24 random bytes, base64url |
| Pool row | `{ idToken, accessToken, refreshToken }` — **no discriminator**; user decoded from the ID token, validity from the access token's `exp`, freshness from `auth_time` (else `iat`). `Auth` adds an optional `provider` only for hosted-UI federated sessions (ignored by `AuthCognito`) |
| TTL | every write stamps `now + session ttl`, recomputed per write (sliding) |
| Auto-sign-in bridge | `autosignin_<fullId>`, same AES-GCM + HMAC construction and HKDF `info` strings |

**Direct-federated sessions** (Q1, no Cognito tokens) are rows with the discriminator `kind: 'direct'` plus `provider`, `issuer`, `subject`, `username`, `groups`, `attributes`, `authTime`, `expiresAt` and the optional raw tokens; `userId = userSub = ${issuer}:${subject}`. Pool rows are read exactly as before.

**Tolerated as signed-out — never a throw, never a 500, never authenticated:** an `AuthBasic` HS256 JWT under `auth_<fullId>`, a tampered / wrong-secret / malformed cookie (all *reject-and-clear*: the response carries a `Max-Age=0` clearing cookie, which core forwards even on an error response — A1c); a verified cookie whose row is missing or not one `Auth` wrote (an old `AuthOIDC` row `{ userId, refreshToken, expiresAt, claims, state }`, garbage) — signed-out and cleared, the foreign row left untouched; sibling cookie names (`my_auth_<fullId>`, look-alikes from regex metacharacters in `fullId`) — ignored, via the anchored, escaped reader (never `AuthBasic`'s unanchored regex).

**How it is proven** (`session-compat.test.ts`): (1) the real `AuthCognito` mock signed a user up and in; `Auth` (default entry, same id) is then constructed and the same browser cookie is signed in as the same `userSub`; (2) a row written by `bb-auth-cognito`'s own `SessionStore` plus a cookie under the `session-secret` value is signed in by `AuthBase`; (3) captured fixtures (`src/__fixtures__/authcognito-*.json`) pin the exact cookie bytes, `Set-Cookie` line and row; (4) rows `Auth` writes are byte-shape-identical and readable by `AuthCognito`'s store (rollback-safe). `bb-auth-cognito` was deleted at the cutover (F1b): what it left on disk and in the cookie jar for (1) and (2) was captured from the real package first, into `src/__fixtures__/legacy-mock-state.json`, and the tests restore it with `Date` pinned to the capture (`src/test-support/legacy-fixtures.ts`). The tolerance cases are in `auth-base.test.ts`.

### Guards

`requireAuth(ctx, { fresh })` — the truth table is in its JSDoc. Refresh happens when the access token has expired (or `getAuthSession({ forceRefresh })`), through the engine that issued the session: the native engine for password sessions, the provider's engine otherwise. An engine returning `null` (revoked, user disabled or deleted) deletes the row and clears the cookie → 401; an engine *throwing* is treated as transient: the session is kept and a retriable 5xx surfaces. So a disabled user is detected at the next refresh (≤ the access-token lifetime).

`requireRole` reads live groups through `NativeEngine.listGroups` (#583): deduped per request on a `WeakMap` keyed by the request context (rejections evicted), the returned `groups` narrowed to the declared `users.groups`, and `UserNotFoundException` → 403 `NotAuthorized` (fail closed). Direct-federated users use their `groupsClaim` snapshot.

### Bearer tokens (`allowBearerAuth`, D6c — `bearer.ts`)

With `allowBearerAuth: true` the guards (`requireAuth`, `requireRole`, `checkAuth`, `getCurrentUser`, `getAuthSession`, and so `getAuthState`) also accept `Authorization: Bearer <access token>`. Off (the default), the header is ignored exactly as before. The wire behaviour is `AuthOIDC`'s, so the native SDKs work unchanged:

- **Precedence:** the session cookie first; the bearer token only when the request has no valid cookie session (an unreadable cookie is still cleared, then the bearer is tried).
- **Direct-OIDC users:** the IdP's JWT access token — what `/exchange` returns as `accessToken` and `/exchange/refresh` renews. `DirectFederationEngine.verifyBearer` (the optional `FederationEngine.verifyBearer`) checks it as `AuthOIDC` did: `iss` = the provider's issuer (pre-checked before any network call), signature against the provider's JWKS (asymmetric algorithms only), `aud` = the client id, `exp` / `nbf` with 30 s tolerance, a `sub`. Identity `` `${iss}:${sub}` `` (Q1), projected like a direct sign-in (profile claims, `attributeMapping`), groups from `groupsClaim` in the access token. Bare OAuth 2.0 providers' access tokens are opaque and are not accepted (nor were they by `AuthOIDC`).
- **Pool users** (password, or federated through Cognito): the Cognito access token, checked by the entry's `AuthLayer.poolBearer` verifier. AWS (`bearer-cognito.ts`): `aws-jwt-verify`, RS256 only, issuer = this pool, `token_use: access`, `client_id` = the native client or the hosted-UI client, 30 s grace. Identity is the cookie session's (`userId` = the Cognito username, `userSub` = `sub`); `signInProvider` is the Cognito-federated provider whose name prefixes the username when the token came from the hosted-UI client, else `password`; `attributes` is empty (an access token has no profile claims); `requireRole` reads live groups.
- **Errors:** a token that does not verify is "no user": 401 `NotAuthenticatedException` with the generic message, nothing about why (the reason is logged at warn). `TokenExpiredException` is only sent by the `/refresh` routes, as `AuthOIDC` sends it; the SDKs react to the 401 status by refreshing.
- **Not checked against the session store:** a bearer token outlives `signOut()` until it expires (documented on `allowBearerAuth`). `getAuthSession` on a bearer request returns `{ tokens: undefined, userSub }`; `{ fresh: true }` measures the token's `auth_time` (none → never fresh).
- **Scope:** only the guards. The account surface (attributes, password, MFA, devices, passkeys) still requires the session cookie.

**The account and admin contract (D5b).** `AuthBase` owns the guards; engines map 1:1 onto Cognito access-token and `Admin*` APIs (each method's JSDoc in `engines/types.ts` names the call and the field mapping, for D5c2). Account calls: `AuthBase` resolves the session (401 when signed out), applies `MfaGate` / `PasswordGate` / `PasskeyGate` and their runtime backstops, refuses a directly federated session (400 `InvalidParameter` — no pool record) and, for MFA / devices / passkeys, a hosted-UI federated one too (email + password only). An engine that reports `UserNotFoundException` for the token's user makes `AuthBase` delete the session row, clear the cookie and answer 401 `NotAuthenticated` — so `UserNotFoundException` never reaches a public caller. Admin calls: `AuthBase` gates `admin` / `admin.actions` (403 before any engine call), prefixes `custom:` attributes, narrows groups to the declared set, pages, and maps errors **without** enumeration masking (404 `UserNotFound` / `ResourceNotFound` are legitimate inside `auth.admin`); `admin.getUser` returns `null`; `admin.listGroupsForUser` reuses `NativeEngine.listGroups`; `admin.revokeUserSessions` is `globalSignOut` **plus** deleting this block's session rows for the user (`SessionStore.deleteByUsername`, a table scan — admin-only), which makes it immediate on both runtimes (`AuthCognito`'s AWS runtime only revoked refresh tokens, so sessions lived until the next refresh).

`EngineHost` gives an engine the `Auth` scope (for `registerSdkIdentifiers` in its constructor and `getSdkIdentifiers` at call time), the user-agent chain, options, logger and the session secret. The federation routes are mounted through the layer's optional `routes(host)` hook, which the `AuthBase` constructor calls (only when a provider is configured) with a private `federationRouteHost()` bundle: providers + engines, the session secret, sign-in / callback / exchange completion, sign-out with its logout redirect, and the error policy. Both runtime entries' layers implement it with `mountFederationRoutes`; a test layer without it mounts nothing.

**"No user pool provisioned" (Q6).** `AuthBase` decides from the options alone with `requiresUserPool()` from `cdk/contract.ts` — the same function the CDK layer uses to decide whether to provision `pool` / `client` and register the `BLOCKS_AUTH_COGNITO_*` keys — and never constructs a native engine when it is false: password methods answer with the `EmailPasswordNotEnabled` gate, `requireRole` for a pool session fails closed, and nothing reads the (unregistered) Cognito config keys. The one remaining case is a deployment mismatch (the options need a pool but the runtime has no identifiers): the Cognito engine resolves identifiers at call time and throws `userPoolNotProvisioned()` — a 500 `InternalErrorException` for the client, the actionable detail in the log. Engine construction never throws for it (client code generation imports the module outside Lambda).

### The Cognito engine (D5c)

`engines/native-cognito.ts` is `AuthCognito`'s AWS layer (with B6's fixes) minus everything `AuthBase` owns. It only talks to Cognito and returns data.

- **Construction never throws and creates nothing.** The backend module is also evaluated during client code generation, outside Lambda. The constructor reads the three `cognitoConfigKeys(fullId)` keys and `registerSdkIdentifiers(fullId, { userPoolId, clientId, region })`; the SDK client (`customUserAgent: host.userAgentChain()`) and the `aws-jwt-verify` ID-token verifier are created on first use. Every call resolves the ids with `getSdkIdentifiers` **at call time**; an empty pool or client id throws `userPoolNotProvisioned()` before any Cognito call. A pool-less configuration (Q6) never builds the engine, so nothing reads the keys.
- **Every ID token is verified before it is returned** — sign-in, every challenge answer, and every `REFRESH_TOKEN_AUTH` (B6 fix 3): pool JWKS signature, issuer, audience = the app client, `token_use: id`, expiry.
- **Refresh: rejected vs transient.** `NotAuthorizedException`, `UserNotFoundException`, `PasswordResetRequiredException`, `UserNotConfirmedException`, no tokens in the response, or a refreshed ID token that fails verification → `null` (signed out). Anything else — throttling, a Cognito 5xx, a network error, a JWKS fetch failure — is thrown, so `AuthBase` keeps the session (L15).
- **Challenges** (`USER_PASSWORD_AUTH` and `USER_AUTH`): SMS / TOTP / email MFA, MFA selection, in-flow MFA setup (TOTP via `AssociateSoftwareToken` → `VerifySoftwareToken`, email via address → `EMAIL_OTP`), new-password-required, `USER_AUTH` first-factor selection (the `PASSWORD` pick is a synthetic step: Cognito wants `ANSWER` and `PASSWORD` in one call), email / SMS OTP first factors, and passkey (`WEB_AUTHN`) sign-in. The Cognito session never reaches the client: it travels in `AuthCognito`'s HMAC-signed envelope (same format, same `session-secret`). SRP, remembered-device SRP and `CUSTOM_CHALLENGE` are refused with `501` (the app client does not enable SRP).
- **Errors** are thrown raw for `AuthBase` to map, except a challenge answered with a password, which the engine maps as `signIn` (uniform credential failure). Enumeration on paths `AuthBase` cannot see into: `ForgotPassword` for an unknown user returns `fabricateCodeDelivery(...)`, `ResendConfirmationCode` for an unknown user resolves.
- **Sign-out:** local sign-out makes no Cognito call (as `AuthCognito`); `{ global: true }` sends `GlobalSignOut` with the session's access token, best-effort.
- **The account surface (D5c2)** maps 1:1 onto Cognito access-token APIs, ported from `AuthCognito`: `GetUser` (attributes, MFA settings), `UpdateUserAttributes` (a `CodeDeliveryDetailsList` entry → `CONFIRM_ATTRIBUTE_WITH_CODE`), `VerifyUserAttribute`, `GetUserAttributeVerificationCode`, `DeleteUser`, `AssociateSoftwareToken`, `SetUserMFAPreference` (`AuthCognito`'s per-factor mapping, byte-identical), `ListDevices` (`Limit` 60, `PaginationToken`), `ForgetDevice`; `ListWebAuthnCredentials` again reports `transports` / `authenticatorAttachment` (L22). `verifyTotpSetup` is `VerifySoftwareToken` (a `Status: 'ERROR'` answer → `EnableSoftwareTokenMFAException`), then `GetUser` + `SetUserMFAPreference` to enrol TOTP — preferred only when nothing is preferred yet — the same end state as the local engine. A deleted user's token answers `UserNotFoundException`, which `AuthBase` turns into a sign-out + 401. `rememberDevice` rejects with the known-gap `501` before any call (L25).
- **The admin surface (D5c2)** is `engines/native-cognito-admin.ts`, `AuthCognito`'s `Admin*` / `List*` calls minus what `auth-admin.ts` owns. Errors pass through unmasked; `getUser` answers an unknown user (also one deleted between `AdminGetUser` and the group read) with `null`, and reports `groups` absent when a hand-narrowed policy denies `AdminListGroupsForUser`. `createUser` reports `groups: []` (a just-created user is in no group). `listUsersInGroup` / `listUsers` return one page (`NextToken` / `PaginationToken` ↔ `nextToken`, `ListUsers` `Limit` 60); `AuthBase` pages.
- **IAM.** No grant changed: every account call is in the base statement (`CLIENT_IAM_ACTIONS`), and every admin call is in the `adminIamActions()` slice of the methods that send it. `iam-coverage.cdk.test.ts` proves it by driving each method through the AWS entry, collecting the commands actually sent, and checking them against a real synth's policy — and that each slice grants nothing from the other.

The offline harness `src/test-support/aws-harness.ts` (ported from B5) drives `Auth`'s AWS entry against a spied SDK client, a real verifier over a local JWKS and the mock session store; the `index.aws.*.test.ts` suites are B5/B6's `AuthCognito` AWS-layer tests ported to `Auth`, with every changed expectation explained inline, plus the flows B5 did not cover (`index.aws.flows.test.ts`). The 15 B5 tests that were `todo` until D5c2 now run, and `index.aws.account.test.ts` / `index.aws.admin.test.ts` pin every account and admin call's exact SDK input, pagination and error mapping. `parity.test.ts` drives the local and the AWS engine through the same `Auth` API and requires the same observable result.

### Error policy

Everything an engine or hook throws goes through `toAuthApiError` (`error-mapping.ts`):

- **Every client-visible name is an `AuthErrors` member** (L10). A raw error with a vocabulary name keeps it, with the status from `statusForAuthError` (401 / 404 / 409 / 429 / 500, else 400; `ReauthenticationRequired` 401; both mode gates 409) and `retriable` from `isRetriableAuthError` (`AuthCognito`'s set). Anything else — an unmapped Cognito exception such as `CodeDeliveryFailureException`, a `TypeError` — becomes `InternalErrorException`, 500, retriable, generic message; the original name and message are logged server-side only. An `ApiError` raised on purpose (by `Auth`, an engine, or app code in `validateUser` / `onSignIn`) passes through by name.
- **No engine text on the wire** (FX59, R93; the guarantee `AuthCognito` 0.1.11 shipped in #678). An error an engine throws with a vocabulary name — Cognito's, or the local engine's stand-in for it — reaches the client with that name's fixed, BB-authored message (`CLIENT_ERROR_MESSAGES` / `clientMessageFor` in `error-mapping.ts`, exhaustive over `AuthErrors`), never its own: Cognito's text can quote the request (the login, a rejected value), name an endpoint, a role or the account, and `ApiError.message` is what the Authenticator UI shows. Cognito's text goes to the server log with the name and request id, the login redacted (`withoutLogin`), at `error` for a 5xx name or text naming AWS resources and at `info` otherwise; nothing is logged when the text already is the fixed message. The strings are `AuthCognito`'s (#678) except where `Auth` already sent one: `CodeMismatchException` and `EnableSoftwareTokenMFAException` use the masked wrong-code text (`WRONG_CODE_MESSAGE`, so a real wrong code and a masked one stay byte-identical, FX3), `InternalErrorException` the generic internal-error text, `NotAuthenticatedException` / `ReauthenticationRequiredException` the text `Auth` throws itself. Both runtimes map through the same table, so the local engine sends the same text as Cognito (`parity*.test.ts` compare messages). An `ApiError` raised on purpose (by `Auth`, an engine's own check such as "Authenticator code must be 6 digits.", or app code in `validateUser` / `onSignIn`) keeps its message. The trade-off is the one #678 made: the client no longer sees Cognito's detail (which password rule failed, which attribute was rejected, "User is already confirmed."), only the name's message; the operator sees it in the log. `index.aws.wire-messages.test.ts` drives every public path that sends a Cognito call with every name.
- **No external text on the wire from a federation callback** (FX60). The guarantee above is about what an engine *throws*; a federation callback also *reads* text — the OAuth `error` / `error_description` on the redirect — and both engines that read one used to quote it in the `IdpErrorException` they raise. That text is the IdP's (for hosted-UI, Cognito managed login's own, so FX59 applied to it directly), so the client now gets one fixed message, `The identity provider '<id>' refused the sign-in.` (`engines/idp-callback-error.ts` `idpRefusedMessage`, shared by `federation-hosted-ui.ts` and `federation-direct.ts` so the two cannot drift), and `maskIdpCallbackError` logs the provider id, `error` and `error_description`: at `error` for an IdP fault (`server_error`, `temporarily_unavailable`) or text naming AWS resources (the same `AWS_IDENTIFIER_PATTERN`), `info` otherwise, matching FX59's levels. Nothing is redacted — a callback has no login to redact against, since the user is not identified until the code is redeemed. Neither path is injectable: both run only after the returned `state` has been matched against this browser's pending-auth cookie (R2-2), so this is defence in depth, not a fix for a forgeable input. A decoded `validateUser` rejection still reaches the client with its own name and message (the hosted-UI trigger path, above). **The one exception is the native / CLI relay** (`federation-routes.ts` `dispatchCallback`): a `relay-error` forwards `error` and `error_description` verbatim in the 302 to the signed, re-validated `relayTo` target, because there the callback *is* the OAuth error response being handed back to the app that started the sign-in (RFC 6749 §4.1.2.1), which needs it to stop waiting for a code. Nothing is rendered to a browser on that path — the redirect answers with an empty body, so a browser only carries the parameters on to the app. See L71.
- **No AWS identifiers** (B6): AWS access/credential errors and any message naming an ARN or a 12-digit account id get a generic message; the detail is logged. Since FX59 this matters only for an `ApiError` raised on purpose (an engine error never sends its own text). Every log line in `error-mapping.ts` that carries a thrown error's own message passes it through `withoutLogin` — including the AWS-access and out-of-vocabulary lines, which did not before FX60 (an unmapped name such as `CodeDeliveryFailureException` quotes the delivery destination).
- **No SDK metadata**: the result is always a fresh `ApiError`; the original rides as `cause`, which `Error` installs non-enumerably, so `$metadata` never serializes.
- **Enumeration** (design 04 §6.3, R9): sign-in failures are byte-identical (`NotAuthorizedException`, 401, `Incorrect username or password`); confirm-code flows answer an unknown user like a wrong code; password reset fabricates delivery details; resend succeeds; and the **public** sign-up form answers an existing account exactly like a new one unless `emailPassword.revealExistingUsers: true` (the imperative `signUp()` still throws `UsernameExistsException`). With that option off (the default) the **account state** is hidden on the steps that follow too (FX3), imperative or through `setAuthState`: Cognito's `PreventUserExistenceErrors` masks only a *missing* user, so `toAuthApiError`'s `hideAccountState` folds `NotAuthorizedException` (an already-confirmed or disabled user) and `ExpiredCodeException` into the wrong-code error on `confirmSignUp` / `confirmResetPassword`, and `AuthBase` turns `InvalidParameterException` / `NotAuthorizedException` from `resendSignUpCode` ("User is already confirmed.") and `resetPassword` (no verified contact, disabled, never signed in) into the masked success (`enumeration.ts` `isAccountStateAnswer`). Each withheld answer is logged server-side at **warn** (R2-4) — the masking also hides answers an operator needs, every `InvalidParameterException` from resend / reset (a malformed username "succeeds") and an expired code shown as a wrong one — with Cognito's error name and message, the login redacted from the message (`error-mapping.ts` `withoutLogin`, since Cognito quotes rejected values). Unknown, unconfirmed and confirmed users are byte-identical on all four (`index.aws.enumeration.test.ts`, `enumeration.mock.test.ts`). **Not covered** (residual, LATER-DISCUSSION R9): the account a masked sign-up actually *creates* for a new username (a later sign-in with the chosen password says `UserNotConfirmedException`, and the code goes to the address the visitor typed); per-user throttling (`LimitExceededException`); and, under `USER_AUTH`, Cognito's random first-factor choice for an unknown user versus a real user's stable one, and its answer for an unconfirmed or disabled user at the first step (unverified without a sandbox).
- The runtime mode-gate backstops throw `ApiError` 409 `EmailPasswordNotEnabledException` / `NoFederatedProviderException` before any engine call; an unknown provider id is 400 `ProviderNotConfiguredException`.

### `createApi()`

Exactly `getAuthState` / `setAuthState` — no `getClient()`. Federated providers appear as `signIn:<id>` actions with `url: /aws-blocks/auth/signin/<encodeURIComponent(id)>`, `method: 'GET'` and no fields, after the password actions (which are absent under `emailPassword: false`); a federated session's `signOut` action carries `url: <signOutPath>`, `method: 'POST'`. Every action and field name is carried over from `AuthCognito` unchanged — they are the `data-testid` contract (#272) and the keys `core/src/redact.ts` masks; `state-machine.test.ts` pins both.

**`AuthState.user.displayName`** (R34, `displayNameOf` in `state-machine.ts`): a chosen username stays; otherwise the email, then the phone number — each skipped when it is marked unverified — then `preferred_username`, then the username. "Unverified" is read from the **session ID token's** `email_verified` / `phone_number_verified`, which `identityOf` keeps on the internal `SessionIdentity.verified` (`contactVerificationOf`), because a Cognito ID token — and an OIDC provider's, per OIDC Core §5.1 — carries them as JSON booleans and they are therefore never in `attributes` (FX26). A string `'true'` / `'false'` is accepted too (some providers send that), and a string flag in `attributes` is the fallback. `toUser` records the flags per user object in a `WeakMap` and `stateUser` reads them, so `AuthenticatedUser`'s public shape doesn't change. Same code on both runtimes; the mock's ID token carries the flags as booleans like Cognito's. A pool user whose email was changed with `updateUserAttributes` and not yet confirmed (the pool doesn't set `keepOriginal`, so Cognito changes it at once and marks it unverified) has it skipped once the session's tokens are refreshed — before FX31, a pool session's display name could never see the flags and showed it on both runtimes. A direct-OIDC user's flags come from the stored IdP ID token; from an OAuth 2.0 provider with no ID token, only a string flag in its profile claims survives (`attributes` keep string claims only). A bearer-token session has no ID token, so no flags (and a pool bearer user has no `attributes` either).

## Federation (D6a)

### Per-provider engines

`AuthLayer.federation(host, provider)` is called once **per configured provider**, so one provider's transport never decides another's. That fixes `AuthOIDC`'s bug where a single `cognitoFederated()` entry switched the whole instance to the Cognito engine and made every co-declared provider unreachable. `federation-routes.test.ts` proves a mixed configuration — a stub, a direct OIDC provider, an id needing URL encoding, `github()`, a social, a SAML and a `federateVia: 'cognito'` provider — reaches every provider.

| Provider | Mock (`index.mock.ts`) | AWS (`index.aws.ts`) |
|---|---|---|
| `oidcProviders` entry (default `federateVia: 'direct'`) | `DirectFederationEngine` against the real IdP (`http:` allowed, for a local IdP) | `DirectFederationEngine`, HTTPS only |
| `github()` / `customOauth2()` (bare OAuth 2.0) | `DirectFederationEngine` (OAuth 2.0 mode) | same |
| `stubIdp()` | `DirectFederationEngine` + the in-process stub IdP (its issuer is derived per request) | actionable `501`: the stub runs only in local dev. The CDK layer fails the synth ("`stubIdp()` is local-only"), so this is reached only by a Lambda whose module chose a different provider set than synth did. With `unsafeAllowDeployed: true`: `DirectFederationEngine` (HTTPS only) + the stub IdP served by the Lambda ([below](#deploying-the-stub-idp-unsafeallowdeployed-fx8)) |
| social, SAML, `federateVia: 'cognito'` | actionable `501`: "unavailable locally — use a direct provider or the stub IdP" (never a 404) | `HostedUiFederationEngine` — Cognito managed login (D6b, [below](#the-hosted-ui-engine-enginesfederation-hosted-uits-d6b)) |

The `501`s are `ApiError`s named `ProviderMisconfiguredException`; their routes are still mounted, so the `signIn:<id>` button reaches the message.

### The direct engine (`engines/federation-direct.ts`)

The same code runs locally and in Lambda; only the issuer differs. Discovery from `{issuer}/.well-known/openid-configuration` (cached per issuer; a failure is not cached), whose `issuer` must equal the configured one; or the `endpoints` override, which skips discovery. Authorization code + **PKCE S256 on every request**, so public clients work (`clientSecret` is optional; when set it is sent `client_secret_post`, or `client_secret_basic` when that is all discovery advertises). The ID token is verified with `jose` against the JWKS: asymmetric algorithms only, `iss`, `aud` (+ `azp` with several audiences), `exp`/`nbf` with 30 s tolerance, and the nonce. Userinfo only fills claims the ID token left out, and only for the same `sub`. RFC 9207: an `iss` response parameter from another server is refused (mix-up). Groups for `requireRole` come from `groupsClaim` (a string array, or one string), narrowed to `users.groups` by `AuthBase`.

**Bare OAuth 2.0** (`github()`, `customOauth2()`): no ID token, so userinfo — called with the access token — is the identity source and `mapClaims` turns it into `{ providerSub, email, name }`. The issuer is the synthetic `oauth2:<name>`, so `userId` is `oauth2:<name>:<providerSub>` — `AuthOIDC`'s value. Cognito cannot federate bare OAuth 2.0; this engine is the only path.

**Sessions** are `kind: 'direct'` rows (D5a format); `AuthBase` builds them from the verified identity: profile attributes are the string claims minus JWT / OIDC protocol claims (`nonce`, `at_hash`, `azp`, …), with the provider's `attributeMapping` (attribute ← claim) on top; `username` is `name`, else `email`, else `sub` (as `AuthOIDC`). `validateUser` receives the verified claims. The session is due for refresh at the access token's `expires_in` (else the ID token's `exp`). A direct user's `AuthenticatedUser.claims` — what `AuthOIDC`'s user carried, and what `db.crud()` / `supabaseCrud()` hand to Postgres RLS, so `claims.sub` is the raw provider `sub` — is derived on every read from the row: the stored ID token's claims (else the profile `attributes`), with the row's `iss` / `sub` on top; for a direct bearer token, the verified access token's claims. Nothing new is persisted. It is server-side only: `AuthState.user` and the `/exchange` response drop it. Pool users have none (their claims are in `getAuthSession()`), so RLS keeps seeing their `userId`, as under `AuthCognito`.

**Refresh** uses the refresh token (rotation honoured; a refreshed ID token must verify and keep the same `sub`). An OAuth error answer → `null` (signed out); a transport failure or 5xx → a retriable throw (the session is kept). With no refresh token, an OIDC session ends with the IdP's token (request `offline_access` for long sessions — `AuthOIDC`'s behaviour), and a bare OAuth 2.0 session re-validates its access token against userinfo (GitHub issues long-lived tokens and no refresh token).

**Sign-out** revokes the refresh (else access) token at `revocation_endpoint` (RFC 7009, best-effort), and when discovery advertises `end_session_endpoint` returns a logout URL with `id_token_hint`, `client_id` and `post_logout_redirect_uri = <app origin><redirects.postSignOutPath>` (default `/`) — **register that URI with the IdP**. Bare OAuth 2.0 providers have neither; GitHub's own session can therefore re-authorize silently (documented, not fixable in-block).

### The stub IdP (`engines/stub-idp.ts`, mock only)

`bb-auth-oidc`'s stub, carried over: a real RS256 key pair per provider (`jose`) — now an ES256 (P-256) key derived from the session secret, see below — discovery, JWKS, `/authorize` with PKCE S256 required and a server-rendered account picker, self-contained HMAC-signed codes, `/token` with a real S256 check of the verifier and rotating refresh tokens, `/userinfo` (verifies the bearer access token), `/revoke`, and — new — `/logout` as `end_session_endpoint`, so local sign-out walks the same redirect chain as production. Like a real IdP (OIDC RP-Initiated Logout §3–4), `/logout` redirects only to a registered `post_logout_redirect_uri`, compared exactly: the app origin plus the instance's normalised `redirects.postSignOutPath` or `redirects.signOutPath`. Any other URI, or another `client_id`, gets a `400` and no redirect; without a URI it shows a signed-out page. It rejects the `redirect_uri`s real IdPs reject (custom schemes, fragments, reserved response parameters), which is what forces native apps onto the relay. Both `/authorize` routes also accept only the registered client (FX10, RFC 6749 §4.1.2.1): the stub's `client_id`, and a `redirect_uri` equal to the instance's `redirects.callbackPath` on one of the two front doors hosted-UI federation registers with Cognito — the app base (`BLOCKS_PUBLIC_ORIGIN`, else the request origin plus stage; what the direct engine sends) and the stub's issuer base (locally the request origin, deployed the registered API Gateway URL; what the native SDKs send). Anything else is a `400` error page with no redirect, checked before the picker renders, `onAuthorize` runs, or an `access_denied` is sent. A browser-PKCE SPA must therefore use the app's callback as its `redirect_uri` against the stub; there is no option to register another one. A deployed stub (`unsafeAllowDeployed`) needs the compute's API URL for its issuer: synth fails without one. The user directory is the provider's inline `users`, else `.bb-data/<fullId>/users.json` (the `bb-auth-oidc` fixture), else one default user; `onAuthorize` can pick a user or deny. `stubIdp()` is a public (PKCE-only) client with `groupsClaim: 'groups'` (set per user with `extra: { groups }`). Keys and refresh tokens are process memory: a dev-server restart signs stub sessions out. (FX8 changed this: the signing key, the code key and the refresh-token key are derived with HKDF-SHA256 from the block's session secret under a per-provider label, and refresh tokens are self-contained and MAC'd, so a restart no longer signs stub sessions out; only rotation/revocation bookkeeping is per process.)

### Deploying the stub IdP (`unsafeAllowDeployed`, FX8)

`AuthOIDC` served its stub from the deployed Lambda too, which is how the comprehensive app's OIDC e2e ran in sandbox and production. `Auth` keeps that capability behind an explicit, alarming opt-in, because a deployed stub's account picker signs anyone in as its users:

- **Synth.** Without `stubIdp({ unsafeAllowDeployed: true })` the synth fails ("`stubIdp()` is local-only", plus a pointer to the flag). With it, synth succeeds, emits the `@aws-blocks/bb-auth:StubIdpDeployed` warning naming the users anyone can become, and registers the compute's API Gateway URL under `stubIdpConfigKeys(fullId).API_URL`.
- **Module graph.** `index.aws.ts` statically imports only `engines/stub-idp-routes.ts` (the route table). `engines/stub-idp.js` is reached through one dynamic `import()` inside `deployedStubIdp()`, which runs only for an opted-in provider, on its first request — so a normal deployed app never loads the stub. `index.aws.bearer.test.ts` pins both halves.
- **Keys across Lambda instances.** `AuthOIDC`'s deployed stub generated a fresh RSA key per process and kept its refresh tokens in memory, so a token minted by one instance could fail at another instance's JWKS (and the HMAC key of its codes was a constant in the source, so anyone could mint a code for any user). The keys are now derived from the session secret (the `session-secret` SSM parameter), which every instance reads: the same key and `kid` everywhere, codes and refresh tokens no one without the secret can mint. P-256 because an EC key derives deterministically from bytes and an RSA key does not; the direct engine accepts ES256 like any IdP's.
- **Issuer.** The gateway URL plus `/aws-blocks/auth/idp/<id>` — HTTPS (the AWS direct engine requires it), reachable by the Lambda itself (discovery, token and JWKS are server-side fetches), and the same value whichever front door a request came through (CloudFront, the gateway, the sandbox dev server's loopback proxy). It is also exactly the issuer `AuthOIDC`'s deployed stub derived from its requests, so `userId` (`` `${iss}:${sub}` ``) carries over. Without a registered URL (a compute with no API Gateway) the issuer is derived per request.
- **Comparisons.** Like a real IdP, the stub compares what a client presents against what it bound into a code or token — the PKCE challenge, the client id, the redirect URI — in constant time (`stubValueMatches`), and its codes' and refresh tokens' MACs too.
- **Rotation.** Refresh-token rotation and revocation are remembered per process: exact on the single-process dev server, best-effort across Lambda instances (a test double does not need a store).

`index.aws.stub-idp.test.ts` drives it offline against an in-process API Gateway stage: nothing mounted without the flag; discovery, JWKS, authorize, token and userinfo with it; a sign-in through the HTTPS-only direct engine; and two instances built from the same configuration interoperating (keys, codes, refresh tokens, a sign-in started on one and completed on the other). `stub-idp.cdk.test.ts` covers the synth side.

`stubIdp()` is an ordinary `oidcProviders` entry (`StubOidcProviderOptions extends DirectOidcProviderOptions`), so `ProviderIdOf<O>`, the `FederationGate`, the sign-in UI and Q6 provisioning (no pool for `emailPassword: false` + a stub) need no special case.

### Routes (`federation-routes.ts`)

Mounted only when a provider is configured. `<base>` is the directory of `redirects.callbackPath` (default `/aws-blocks/auth`); `<id>` is `encodeURIComponent(id)`; all paths are explicit — **no wildcard, no root route** (rule 12) — and `redirects.callbackPath` / `signOutPath` must sit under `/aws-blocks/auth/` (a construction-time error otherwise).

| Construct id | Method | Path | Response |
|---|---|---|---|
| `auth-signin-<id>` | GET | `<base>/signin/<id>` (`?redirectPath=` optional, same-origin) | `302` to the IdP + pending cookie; error JSON |
| `auth-callback` | GET | `<base>/callback` | `302` landing (`redirectPath ?? postSignInPath ?? '/'`, `?state=<appState>` when given) / `302` relay / 4xx JSON |
| `auth-signout` | POST | `<base>/signout` | form post → `303` to the IdP logout URL (or `redirects.postSignOutPath`, default `/`); API client → `204` (+ `Location` when the IdP has a logout URL) |
| `auth-signout-landing` | GET | `<base>/signout` | `302` to `redirects.postSignOutPath` — where Cognito's `/logout` returns (with a GET, D6b). Changes no state: a GET that signed users out would be logout CSRF |
| `auth-exchange` | POST | `<base>/exchange` | `{ user }` (+ `accessToken`, `refreshToken`, `expiresIn` with `allowBearerAuth`); sets the session cookie |
| `auth-authorize-params-<id>` | GET | `<base>/authorize-params/<id>` | `{ authorizeUrl, clientId, scopes, kind }` |
| `auth-authorize-params-post-<id>` | POST | `<base>/authorize-params/<id>` | + `state` (signed envelope) and `nonce` (OIDC only) |
| `auth-refresh` | POST | `<base>/refresh` | `allowBearerAuth` only — `{ accessToken, refreshToken, expiresIn }` / `401 TokenExpiredException` |
| `auth-refresh-exchange` | POST | `<base>/exchange/refresh` | the same; see the native note below |
| `auth-idp-<id>-*` | GET/POST | `/aws-blocks/auth/idp/<id>/{.well-known/openid-configuration, jwks.json, authorize ×2, token, userinfo, revoke, logout}` | mock only |

**The pending cookie** (`authpending_<fullId>`, `engines/pending-auth.ts`): one 10-minute, `HttpOnly`, HMAC-signed cookie holding `provider`, `state`, `nonce`, the PKCE verifier, the exact `redirect_uri`, `redirectPath` and `appState`. Every engine writes it with `writePendingAuth` — that is the contract D6b plugs into — because the single callback route reads `provider` from it to pick the engine. Its key, like the relay envelope's, is derived from the session secret and domain-separated from the session-cookie signature.

**Same-origin landing paths** (`src/redirect-path.ts`). Every caller- or config-supplied landing path — `redirectPath` (`getSignInUrl()` and the sign-in route), `redirects.postSignInPath`, `redirects.postSignOutPath` — goes through one check, `safeRedirectPath()`, and the **normalised** result is what is stored and emitted, never the raw string. A string test alone is not enough: a browser parses `Location` with the WHATWG URL parser, which strips TAB, CR and LF and treats `\` as `/`, so `/\t/evil.example` lands on `https://evil.example/`; dot segments collapse the same way (`/.//evil.example` → `//evil.example`). So a path is safe only if it starts with a single `/`, has no control character (U+0000–U+001F, U+007F) or `\`, resolves to the same placeholder origin with the URL parser, and its re-serialised `pathname + search + hash` passes the same test again. The sign-in route answers an unsafe `redirectPath` with `400 InvalidParameter`; an unsafe configured path fails construction; and the callback re-checks the pending cookie's `redirectPath`, landing on `postSignInPath` if it fails (a cookie may predate the check). Relay targets are absolute URLs, checked separately by `validateRelay()` and re-serialised through `URL`.

**The three transports and the dispatcher.** Carried over from `AuthOIDC`: a `state` that is a relay envelope signed by this backend → relay, re-validated against `redirects.allowedRelayOrigins` (loopback and same-origin always allowed), and the code (or the IdP's error) is 302'd to the `relayTo` target; otherwise a pending cookie → server-initiated (the named provider's engine completes it). One deliberate change: `AuthOIDC` checked the cookie first, so a stale pending cookie (a web sign-in abandoned in the same browser) broke a native relay; a server-initiated `state` is a random token and never an envelope, so checking the envelope first is unambiguous. **`state` before `error`** (R2-2): on a server-initiated callback each engine checks the returned `state` against the pending cookie before it honours `error` / `error_description` or decodes a trigger rejection — RFC 6749 §4.1.2.1 returns `state` on error responses too — so a link an attacker sends to a user mid-sign-in (`?error=…&error_description=bb-auth-rejection:…`) gets the generic `InvalidStateException`, never an error name, status or message the attacker chose; a relay forwards an IdP error only with a `state` this backend signed. Every such check is constant-time (FX7b): the pending `state` through `pendingStateMatches` (`engines/pending-auth.ts`), the ID-token `nonce`, and the relay envelope's and pending cookie's HMACs, all via core's `constantTimeEquals` — never `===`. `POST /exchange` also requires `Content-Type: application/json` (`415` otherwise) — every SDK already sends it, and it closes login CSRF from a cross-site form. `CallbackResult` is `server-exchange | relay | relay-error | error`, and the error bodies are `{ error: <code>, message, name }` with the codes `invalid_state` / `sdk_outdated` / `invalid_relay` / `invalid_callback` and the matching `AuthErrors` names. Every other error body is `AuthOIDC`'s `{ error: <message>, name }`. `handleCallback` is not a public method — the callback is reachable only through its route.

**Native SDK compatibility** (checked against `native/{swift,kotlin,dart}`): the SDKs call `POST <exchangePath>` with `{ code, verifier, state, nonce, provider, callbackUrl, iss? }` and read `user.userId` / `user.username` (+ `accessToken` / `refreshToken`); `POST <authorizeParamsBasePath>/<provider>` with `{ csrf, relayTo }` and read `{ authorizeUrl, clientId, scopes, kind, state, nonce? }`; split `state` at the first `.` and base64url-decode `{ v, csrf, relay?, app? }` (`state-envelope.ts` is byte-identical to `AuthOIDC`'s and pinned by a golden-vector test); and `POST <signOutPath>` with a JSON body. Swift and Dart refresh at `<exchangePath>/refresh` with only `{ refreshToken }` — a path `AuthOIDC` never served (so their refresh 404'd); `Auth` serves it and accepts a missing `provider` when exactly one provider is configured. `getClient()` (the SDKs' descriptor source) is gone by design; E3 moves the SDKs to the fixed default paths above.

**Not built in D6a:** accepting `Authorization: Bearer` in the guards (built in D6c — see [Bearer tokens](#bearer-tokens-allowbearerauth-d6c--bearerts)); the browser-side PKCE helper (the old `AuthOIDC` client); the hosted-UI engine and its local shim (D6b).

### The hosted-UI engine (`engines/federation-hosted-ui.ts`, D6b)

Social, SAML and `federateVia: 'cognito'` providers, on the AWS runtime. Cognito federates only through its Login / Authorize endpoints, so the engine is an OAuth 2.0 client of the pool's **domain**, using D3b's separate **hosted-UI app client** (public — no secret):

- **Authorize** — `https://<DOMAIN>/oauth2/authorize?response_type=code&client_id=<hosted-UI client>&redirect_uri=<origin><callbackPath>&scope=openid email profile&state=…&code_challenge=…&code_challenge_method=S256&identity_provider=<name>`. `identity_provider` is `cognitoProviderName(family, id)` (`google` → `Google`, `apple` → `SignInWithApple`, `amazon` → `LoginWithAmazon`, `facebook` → `Facebook`; SAML and OIDC ids as-is), so the user goes straight to the IdP. `state`, the PKCE verifier and the exact `redirect_uri` go in the **shared pending-auth cookie** (`writePendingAuth`), so the one callback route dispatches to this engine like any other. No `nonce` is sent (as `AuthOIDC`'s `cognitoFederated()`): PKCE binds the code to the browser that started the sign-in.
- **Token** — the code + verifier are redeemed at `/oauth2/token`. The Cognito ID token is verified with `aws-jwt-verify` against the pool and the hosted-UI client (signature against the pool's JWKS, issuer, audience, `token_use: id`, expiry), exactly as the native engine verifies its tokens; a JWKS fetch failure is a retriable `502`, anything about the token a `401 IdpErrorException`. Its `identities` claim must name **this** provider: the browser controls `identity_provider`, and without the check a user could start "Sign in with Google", swap in another configured IdP, and reach `validateUser` / `signInProvider` labelled `google`.
- **The user is a pool user.** `completeSignIn` returns `{ kind: 'pool', tokens }`; `AuthBase` stores the row with `provider: '<id>'` (the only difference from a password row). `userId` / `username` are Cognito's `cognito:username` (`<ProviderName>_<sub>`, lowercased on a case-insensitive pool), `userSub` the pool `sub`; `requireRole` reads live groups (`AdminListGroupsForUser`) and `auth.admin` applies, exactly as for email + password users. This differs from `AuthOIDC`'s `cognitoFederated()`, whose `userId` was `` `${iss}:${sub}` `` from the `identities` claim. The strategy doc's upgrade table already accepts that a `cognitoFederated()` app's users change identity (its `cognito-pool` is replaced by `pool`, so their Cognito users and subs are new anyway); F2's migration guide must say so.
- **MFA is the IdP's.** Cognito delegates authentication of federated users to their IdP and never challenges them, so the engine has no challenge path; `AuthBase` refuses the MFA, device and passkey methods for these sessions (400). **Enforce MFA at your IdP.**
- **Refresh** — `/oauth2/token` with `grant_type=refresh_token` (Cognito-issued; Cognito does not rotate it unless rotation is enabled, so the stored one is kept). A rejected grant or a refreshed ID token that fails verification or names another `sub` → `null` (signed out); a 5xx or transport failure → a retriable throw (session kept). **Revocation** — `/oauth2/revoke` with the refresh token, best-effort, on sign-out and when `validateUser` / `onSignIn` rejects the sign-in.
- **Sign-out** — see [the sign-out flow](#hosted-ui-sign-out-flow).
- **Client-driven transports** — `authorizeParams` (the authorize URL with `identity_provider`, `kind: 'cognito-federated'`, no nonce), `exchangeCode` (same verification) and `refreshBearer` are implemented, so the relay and browser-PKCE routes work for hosted-UI providers as they did for `AuthOIDC`'s `cognitoFederated()`.

**Configuration is resolved at call time.** The constructor registers `BLOCKS_AUTH_COGNITO_<UPPER_FULLID>_DOMAIN` / `…_HOSTED_UI_CLIENT_ID` (`federationConfigKeys`) with `registerSdkIdentifiers` as `hostedUiDomain` / `hostedUiClientId`, as the native engine registers the pool keys; every call resolves them with `getSdkIdentifiers(this)`, plus the native engine's `userPoolId`. The `DOMAIN` value is a bare host (`https://` is implied); an explicit `https://` value is accepted, and `http://` only for a loopback host (the in-process fake the tests use — the same exception Cognito makes for localhost callbacks). **Pool-less safety:** a hosted-UI provider always provisions a pool (Q6), but if a runtime has no domain, client or pool id (client code generation, a stale deployment), every call refuses with a `500 ProviderMisconfiguredException` naming the provider ("this deployment has no Cognito managed-login configuration. Redeploy the stack."), the missing config keys in the log, before any request; sign-out stays local.

#### Hosted-UI sign-out flow

Managed login keeps its own session cookie (one hour, non-renewing). If sign-out only cleared `Auth`'s cookie, the next "Sign in with Google" would be answered by that cookie and silently sign the user back in.

1. The browser POSTs the sign-out form to `<base>/signout` (`auth-signout`). `AuthBase.signOut` runs `onSignOut`, the engine revokes the refresh token at `/oauth2/revoke` and returns `https://<DOMAIN>/logout?client_id=<hosted-UI client>&logout_uri=<app origin><redirects.signOutPath>`; the session row is deleted and the cookie cleared.
2. The route answers `303` to that URL (an API client gets `204` with it in `Location`).
3. Cognito clears its managed-login cookie and redirects — with a **GET** — to `logout_uri`. That is `<origin><signOutPath>`, not `postSignOutPath`, because Cognito accepts only a URL registered on the client, and D3b registers `<front door><signOutPath>` (both the API's URL and the Hosting origin). `<app origin>` is computed like the callback URL (`BLOCKS_PUBLIC_ORIGIN`, else the request origin plus any stage prefix), so it is one of those.
4. `GET <signOutPath>` (`auth-signout-landing`) `302`s to `redirects.postSignOutPath` (default `/`).

`federation-hosted-ui.test.ts` walks this chain against the fake domain and checks the next sign-in carries no managed-login cookie.

## CDK layer

`index.cdk.ts` (`class Auth extends BuildingBlockScope`, VPC needs: the SSM interface endpoint) provisions what `AuthCognito` provisions, under the same construct ids. Option mapping lives in `src/cdk/mappers.ts`; the names and decisions every layer shares live in `src/cdk/contract.ts`, which is pure (no `aws-cdk-lib`) so the runtime layers import it too.

### The frozen contract

| Item | Value | Why it is frozen |
|---|---|---|
| Child construct ids | `pool`, `client`, `sessions`, `session-secret`, `group-<name>` | They are the logical IDs. A rename makes CloudFormation create a new resource and delete the old one — for `pool`, every user. |
| `userPoolName` | `this.fullId` (synth fails above 128 chars, never truncates) | Replacement on change. |
| `client` `GenerateSecret` | never set | Replace-only. Replacing `client` invalidates every refresh token in `sessions`. Hosted-UI federation (D3b) uses a **separate** client. |
| Config keys | `BLOCKS_AUTH_COGNITO_<UPPER_FULLID>_{USER_POOL_ID,CLIENT_ID,REGION}` (`cognitoConfigKeys()`) | The runtime looks them up independently. |
| Session cookie | `auth_<fullId>` (`sessionCookieName()`) | Renaming it signs every user out. D5's cookie writer/reader must use this function. |
| `featurePlan` | always pinned (default `ESSENTIALS`) | Left implicit, Cognito re-applies the tier on every `UpdateUserPool` and resets `AllowAdminCreateUserOnly`. |

IAM is `AuthCognito`'s: one base statement on the pool ARN (the 25 client-facing actions, **including `AdminListGroupsForUser`**, because `requireRole` reads live groups — #583), plus the `Admin*`/`List*` statement only when `admin` is set, scoped by `admin.actions`. Grants go to the shared execution role. With `validateUser` set on an owned pool, the same statements go into a separate `iam.Policy` (`pool-access`) on that role instead of its default policy, to break a dependency cycle ([Q10](#validateuser-and-the-presignup-trigger-q10)); unset, nothing moves.

**How it is enforced.**

- `resource-identity.cdk.test.ts` runs B1's golden fixture (`bb-auth-cognito/src/__fixtures__/resource-identity.json`, vendored byte-identical as `src/__fixtures__/authcognito-resource-identity.json`; since the cutover deleted the original, its SHA-256 pins the copy) against the equivalent `Auth` configurations. Only the fixture's `construct` label is not compared. Never regenerate that fixture here: if `Auth` cannot match it, the refactor stops.
- `property-snapshot.cdk.test.ts` compares `Auth` with `AuthCognito` for each equivalent configuration in `src/test-support/authcognito-pairs.ts`, under both stack presets (the `AuthCognito` side synthesized from the real block and frozen into `src/__fixtures__/authcognito-templates.json` at the cutover), and requires the pool and client `Properties`, and then the **whole template**, to be identical — except the allowlist below. It catches a changed default (for example `signInWith`), which keeps every logical ID and still rolls the stack back on `UpdateUserPool`. Content-addressed asset hashes (aws-cdk-lib's own handlers and the config bundle) are masked on both sides of the whole-template comparison, so the frozen side survives dependency bumps; the full config registry, the config bundle's content, is compared exactly instead.

**The allowlist** (on the `AWS::Cognito::UserPool` resource only): the resource attributes `DeletionPolicy` and `UpdateReplacePolicy` (Q4, below). **No pool property under the sandbox preset**: there the pool's `Properties` equal `AuthCognito`'s exactly. Under the production preset, exactly one: `Properties.DeletionProtection: 'ACTIVE'` where `AuthCognito` has none (Q4) — any other value, notably `INACTIVE`, fails. The test runs every pair under both presets. Plus the immutability guard's footprint (D4, [below](#immutability-guard-q5)): its new `BlocksAuthPoolGuard*` resources at the stack root, and one `DependsOn: [BlocksAuthPoolGuard]` entry on the pool. `DependsOn` is template metadata, not a property, so adding it is no pool update. The snapshot test also checks that every guard resource is a new logical id outside the block's subtree and that every `AuthCognito` logical id is kept. Nothing else.

### Q4 — the pool follows the stack defaults

When `removalPolicy` / `deletionProtection` are unset, the pool resolves them from `this.defaults` (`BlocksPresets.production`: retain + protected; `sandbox`: destroy + unprotected), exactly as `KVStore` does. `AuthCognito`'s pool is `DESTROY` unless `removalPolicy: 'retain'`, even under the production preset, and never sets `DeletionProtection`. For an `AuthCognito` app that switches, this is safe: `DeletionPolicy` is template metadata, and `DeletionProtection` updates in place.

**`DeletionProtection` is emitted only when it resolves to `ACTIVE`** (L20) — the production preset, or `deletionProtection: true`. Otherwise (the sandbox preset, or `deletionProtection: false`) the property is omitted, exactly as `AuthCognito` does. Omitted already means inactive: a pool created through the `CreateUserPool` API has deletion protection inactive by default ([User pool deletion protection](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-deletion-protection.html)). Emitting `INACTIVE` would change nothing but would turn every sandbox upgrade from `AuthCognito` into an `UpdateUserPool` call, with its rollback risk; omitted, the sandbox upgrade leaves the pool's `Properties` untouched. Under the production preset the switch is a real, intended in-place update to `ACTIVE`.

**Dropping `DeletionProtection` from a pool that had `ACTIVE` turns protection off.** Going from `ACTIVE` to omitted (`deletionProtection: false`, or moving a stack from the production to the sandbox preset) is an in-place update ("Update requires: No interruption" — [`AWS::Cognito::UserPool` `DeletionProtection`](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cognito-userpool.html#cfn-cognito-userpool-deletionprotection)), and it does **not** keep the old value. The resource is documented as "If you don't specify a value for a parameter, Amazon Cognito sets it to a default value" (same page), and the update goes through `UpdateUserPool`, which states "If you don't provide a value for an attribute, Amazon Cognito sets it to its default value" ([UpdateUserPool](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_UpdateUserPool.html)); the default is inactive. So the pool's protection is deactivated on that deploy, the same as writing `INACTIVE`. That is what `deletionProtection: false` asks for. To keep a pool protected, keep it resolving to `true`. The pool's `DeletionPolicy` is separate: a `removalPolicy: 'retain'` pool is still kept when the stack is deleted. Deletion protection is not one of the guard's immutable properties, so the guard permits both directions (`immutability-guard.cdk.test.ts`, *turning deletion protection off*). Neither page spells out the remove-a-property case word for word; the conclusion follows from the two "unspecified → default" statements above and was not checked against a live stack (no AWS writes in this work).

An unset `removalPolicy` on a pool `Auth` owns emits a synth warning (`@aws-blocks/bb-auth:RemovalPolicyUnset`, via `Annotations.addWarningV2`, naming the resolved default). There is no warning for a wrapped pool (`userPool`) or a pool-less configuration. The `sessions` table receives the same two options and otherwise follows the stack defaults, as it does under `AuthCognito`.

### Q6 — a pool only when something needs it

`requiresUserPool(options)` is `true` when email + password is enabled (the default), when any `socialProviders` / `samlProviders` entry or any `oidcProviders` entry with `federateVia: 'cognito'` is set, or when `userPool` wraps an existing pool. Otherwise — every sign-in method is a directly federated OIDC provider — the CDK layer synthesizes **no Cognito resources** (not even the declared `users.groups`; direct users' groups come from `groupsClaim`), grants no `cognito-idp:*` action, and registers **no `BLOCKS_AUTH_COGNITO_*` key**. `sessions` and `session-secret` are still created: direct sessions are stored and signed the same way.

Enabling a pool-backed method later adds `pool` and `client` under the frozen ids and leaves `sessions` / `session-secret` untouched, so the result is identical to a config that always had a pool (`provisioning.cdk.test.ts` checks this against the fixture).

⚠️ **The reverse is destructive.** Removing the last pool-backed method from a deployed config deletes `pool` — and, under a `destroy` policy, every user. The committed baseline refuses it at synth ([Immutability guard](#immutability-guard-q5)); so does swapping an owned pool for a wrapped one (`userPool`), which removes `pool` the same way. Only a baseline that already exists can refuse it: on a block's **first** synth (an `AuthCognito` app switching to `Auth` has none) the baseline is written from the current configuration, so a first configuration without a pool passes with a warning (`@aws-blocks/bb-auth:FirstBaselineWithoutPool`), and CloudFormation applies the old template's `DeletionPolicy` — `AuthCognito`'s was `Delete` unless `retain`. Hence MIGRATION.md's first rule: deploy the codemod's output unchanged, commit the baseline, then change the configuration.

**How the runtime tells that no pool exists (for D5).** Call `requiresUserPool()` on the runtime's own copy of the options — the backend module, and so the options object, is evaluated identically in every layer. Do **not** infer "no pool" from a missing config key: a missing `…_USER_POOL_ID` while `requiresUserPool()` is `true` is a deployment error and must fail loudly, never fall back to pool-less behaviour.

### Synth-time checks

Each fails at synth with the reason: an unsupported `users.authFlow`; `passkeys` without `users.authFlow: 'USER_AUTH'`, or without `relyingPartyId` / `origins`; `featurePlan: 'lite'` with passkeys, `USER_AUTH` or EMAIL MFA; EMAIL MFA, or `users.preferredChallenge: 'EMAIL_OTP'` under `USER_AUTH`, on a block-created pool (no SES sender option); an empty `users.signInWith`; `emailPassword: false` with `mfa`, `passkeys` or `users.deviceTracking` (all email + password only), or with no provider at all; `admin` on a pool-less config; and a `fullId` over 128 characters — checked even without a pool, so enabling one later never forces a block rename. (`passkeys.userVerification: 'discouraged'` is a compile error, not a synth check: the type admits only `preferred` / `required`, all Cognito supports — `AuthCognito` silently mapped it to `preferred`.)

### Mapping notes

- `AuthOptions.mfa.types` defaults to `['SMS', 'TOTP']`. `AuthCognito` with `mfa` on and no `mfaTypes` left the factors to CDK (SMS only), so the equivalent of `AuthCognito({ mfa: 'optional' })` is `Auth({ mfa: { mode: 'optional', types: ['SMS'] } })`. `EnabledMfas` is mutable, so getting this wrong enables TOTP rather than breaking the deploy.
- Under `USER_AUTH`, the email/SMS OTP first factors follow the `mfa.types` the caller **listed** (not the defaulted list), as `AuthCognito`'s did, plus `users.preferredChallenge` (`AuthCognito`'s top-level `preferredChallenge`, restored by D5c2 — L22): `'EMAIL_OTP'` / `'SMS_OTP'` also enable that first factor. `'EMAIL_OTP'` under `USER_AUTH` is refused at synth on a block-created pool (Cognito sends that code only through SES, which `AuthOptions` does not configure — the same rule as EMAIL MFA; `AuthCognito` synthesized it); a wrapped pool (`Auth.fromExisting`) is allowed. Unset, the template is byte-identical to `AuthCognito`'s (`property-snapshot.cdk.test.ts` pins both). At runtime `AuthBase` applies it as the default `signIn` hint for both engines; the per-call `preferredChallenge` wins, and `USER_PASSWORD_AUTH` ignores it.
- `emailPassword: false` with a hosted-UI provider creates the pool with self-service sign-up off, and restricts the native `client`'s explicit auth flows to `ALLOW_REFRESH_TOKEN_AUTH` only, so no password flow is reachable through it (D3b). `ExplicitAuthFlows` updates in place, so `client` keeps its logical id and its refresh tokens.
- `fromExisting(userPoolId, clientId)` wraps the pool with `UserPool.fromUserPoolId` at child id `pool`; as in `AuthCognito`, the CDK layer still creates its own `client`, groups and grants, and ignores `clientId`.

### Immutability guard (Q5)

Four user-pool properties cannot change once the pool exists, yet CloudFormation documents every one as "Update requires: No interruption". CDK synths the change, `cdk diff` shows a harmless update, and the deploy fails on the pool and rolls the whole stack back. `src/cdk/immutability.ts` holds the evidence and the one diff both layers use:

| Guarded (refused) | Why Cognito refuses (AWS docs) |
|---|---|
| Sign-in attributes — `UsernameAttributes` / `AliasAttributes` (`users.signInWith`) | "After you create a user pool, you can't change this setting." ([attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#user-pool-settings-aliases)) |
| `UsernameConfiguration.CaseSensitive` (L1 only; unset means `true`) | "This configuration is immutable after you set it." ([CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cognito-userpool.html), [default](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_UsernameConfigurationType.html)) |
| The required-attribute set (standard attributes with `Required: true`; L1 only today) | "After you create a user pool, you can't switch an attribute between required and not required." ([attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html)) |
| Changing or removing an existing custom attribute (type, mutability, developer-only, length constraints) | "You can't remove or change a custom attribute after you add it … You also can't change its data type, mutability, or length constraints." (same page) |
| Removing the pool (layer 1 only) — including by renaming or removing the block ([below](#renaming-or-removing-an-auth-block)) | Not a Cognito rule: CloudFormation deletes the pool and, under `destroy`, every user. |

**Permitted** (both layers pass; `immutability-guard.cdk.test.ts` pairs each with a real synth and the deploy-time handler): password policy, MFA mode and factors, token validities, callback/logout URLs, `SupportedIdentityProviders`, adding a social provider, **adding** a custom attribute, adding a group, removal policy / deletion protection, and stating the default `CaseSensitive: true` explicitly. Everything outside the four properties is ignored.

**Layer 1 — a committed baseline, diffed at synth** (`src/cdk/immutability-baseline.ts`).

- **Where:** `<app>/aws-blocks/baselines/<stack>/<fullId>.auth-pool.json` — the directory of the `backendHandlerPath` the `BlocksStack` / `BlocksBackend` was created with (absolute in every template), so it lands in the app's source tree, gets committed, and is found whatever directory synth runs from. Not under `.blocks/` or `.blocks-sandbox/` (both git-ignored). Per-developer sandbox stacks get their own files; commit the production stack's.
- **What:** whether the block owns a pool and, if so, the four properties. Read from the pool's final L1 properties in a construct validation, so L1 escape-hatch assignments (`cfnPool.usernameConfiguration = …`) are seen. Raw `addPropertyOverride` on these four is not seen by either layer.
- **Outcomes:** no baseline → write it, report "commit it" (an info annotation), pass. If that first baseline records no owned pool (pool-less, or `userPool` wrapping one), synth also warns (`@aws-blocks/bb-auth:FirstBaselineWithoutPool`, `addWarningV2`): the layer cannot tell a new app from an `AuthCognito` app whose pool this deploy would delete, so it says so (`immutability-guard.cdk.test.ts`, *a first-ever baseline with no owned pool warns*). Permitted change → pass and rewrite (so an added custom attribute is protected from then on). A guarded change or a pool removal → synth fails with the property, old → new, the reason and the remedy; the file is left untouched. An unreadable baseline fails closed.
- **Escape hatch:** `BLOCKS_AUTH_REBASELINE=<fullId>[,<fullId>…]` on the synth/deploy command rewrites the named blocks' baselines and passes. It must name the block (`=1` does nothing), so a leftover variable cannot silently disarm every block. Use it to remove a pool deliberately, or when the baseline recorded a change that was never deployed. It does not make Cognito accept an immutable change — layer 2 still refuses that.
- **Outside a Blocks stack** (no `backendHandlerPath`, e.g. a bare test stack) layer 1 is off.
- **A renamed or removed block** — see [Renaming or removing an Auth block](#renaming-or-removing-an-auth-block). A baseline that records an owned pool also carries a `removalGuard`; the stack-level check in `@aws-blocks/core` fails synth for one no block claims.

**The CI caveat.** Layer 1 only protects a synth that sees the committed file. If the baseline was never committed, CI's checkout has none: its synth writes a fresh one from the *changed* configuration and passes. Layer 2 closes that gap only partly: it still refuses a change to one of the four properties of a pool the block owns, but not a pool removal — the pool going away (a pool-less or wrapped configuration), nor a rename or removal of the block (the guard is removed with the last pool, and the orphan check in core needs the old baseline on disk). And with a CI-only deploy flow, where the synth that writes the production baseline runs in CI and its file is thrown away with the workspace, the baseline never reaches the repository: every CI synth is a first synth, layer 1 never refuses anything, and the orphan check stays inert. **Commit the baselines from the deploy workflow** — after a successful deploy, commit `aws-blocks/baselines/` back to the branch (or fail the job when the synth left it changed or untracked, so a person commits it) — so the next synth compares against what is deployed.

**Layer 2 — a deploy-time custom resource** (`src/cdk/immutability-guard.ts`, handler `src/cdk/immutability-guard-lambda.ts`, bundled by `build:lambda`).

- **Ordering.** Each owned pool `DependsOn` the `Custom::BlocksAuthPoolGuard` resource, so CloudFormation runs the guard first and never starts the pool update when the guard fails. Nothing in the guard references the pool — a `Ref` would order it *after* the pool. Instead, the guard's `Pools` property carries each pool's logical id (a string, not a `Ref`) and a JSON snapshot of the four properties; the property changes only when the snapshot does, so the guard runs only for a deploy that touches one of the four (or adds/removes a pool).
- **What it compares.** On **Update**: the previous snapshot (`OldResourceProperties`) — CloudFormation computes the pool update from the same template diff, and the four cannot drift on the live pool. On **Create** (the guard appears beside a pool that may already exist — an `AuthCognito` app switching to `Auth`, or the first deploy after this guard shipped), or for a pool new to the guard: the **live** pool, located with `DescribeStackResource(<logical id>)` in this stack, then `DescribeUserPool`. Not by name: Cognito permits duplicate pool names, and a pool retained from a deleted stack carries the same name. Not in the stack yet → it is about to be created → pass. Against the live pool, a custom-attribute field is compared only where the template sets it (the live pool fills in defaults), and `sub` is ignored.
- **Lifecycle.** Delete is a no-op with no AWS call — it never blocks stack deletion. While the stack is in any `*ROLLBACK*` status (`DescribeStacks`), Create/Update pass without comparing: a rollback re-sends the previous snapshot, which is "a change" from the failed one, and failing there would leave `UPDATE_ROLLBACK_FAILED`. A failed guard Create is rolled back with a Delete (no-op). Lookup errors pass with a log line: the guard turns a certain rollback into a clear message; it never adds a new way to fail.
- **Lambda code, installed vs vendorized** (this guard and the IdP-registration Lambda alike, `deployTimeLambdaCode` from `@aws-blocks/core/cdk`). An installed package uses the `build:lambda` bundle in `dist/<name>-lambda/` as-is. A copy made by `blocks-vendorize` has only `src/` (its exports point at the `.ts` sources), so there is no bundle: the handler's source is bundled at synth instead, with the same esbuild options, through CDK local asset bundling (output in `cdk.out`). Edits to a vendorized handler therefore deploy. esbuild comes from the app, which already needs it for the default compute's `NodejsFunction`; if it is missing, or neither the bundle nor the source is there, synth fails with an error that says what to install or rebuild.
- **Packaging.** The release publishes what the root `npm run build` produces, so `build:lambda` is listed in the root `build:bundles` script; the package's own `build` and `pretest` running it is not enough, and without it the published package would ship no `dist/<name>-lambda/` and `cdk synth` in a consuming app would fail with `CannotFindAsset` (the bug `main`'s #739 fixed for `AuthOIDC`). `npm run check:packed-assets` fails when a packed tarball lacks the `bundleDir` a `deployTimeLambdaCode` spec names.
- **Pool removal is not refused here.** With one pool, the guard is removed together with it (Q6: no guard without a pool), so it could not refuse consistently. Layer 1 refuses it once a committed baseline records the pool (on a first synth it only warns); `removalPolicy: 'retain'` / deletion protection are the backstop — and only as already deployed, because CloudFormation applies the deletion policy of the template the pool leaves.
- **Footprint** — one per stack, shared by every `Auth` block that owns a pool, created only when one does: a Lambda (`BlocksAuthPoolGuardFn`, own log group, stack log retention), a `cr.Provider` (own log group), and the custom resource. All at the stack root, like `BlocksSecretsBulk`: new logical ids only, outside the block's subtree. **IAM** (read-only): `cloudformation:DescribeStacks` + `DescribeStackResource` on this stack (`AWS::StackId`), `cognito-idp:DescribeUserPool` on `userpool/*` in this account and region (the pool id cannot be named without the `Ref` that would invert the ordering). **VPC:** not placed in one, like every other Blocks custom-resource Lambda; it reaches only the CloudFormation and Cognito APIs, so it works unchanged in a VPC-enabled stack. Not exercised against a live stack yet (the D8 upgrade-in-place harness / sandbox e2e).

### Changing an immutable pool property

There is no in-place path: a pool keeps these four properties for life. To change one:

1. Add a **second** `Auth` block with a new id (so a new `fullId`, pool and session store) and the new configuration. Deploy.
2. Migrate users. Cognito cannot export password hashes; either let users reset their password, or migrate on sign-in with a Migrate-user Lambda trigger on the new pool ([AWS guide](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-migrate-user.html); `Auth` has no option for it yet — add it through the L1 pool). Re-key app data from the old `userSub` to the new one.
3. Move the app's API onto the new block; signed-in users sign in again.
4. When the old pool is empty of anyone you still need, remove the old block (set `removalPolicy: 'retain'` and deploy first if in doubt). Synth then fails on the old block's orphaned baseline ([below](#renaming-or-removing-an-auth-block)); re-baseline with `BLOCKS_AUTH_REBASELINE=<old fullId>`, which deletes the file, and commit the deletion.

### Renaming or removing an Auth block

The pool belongs to the block's `fullId` (`userPoolName` and the construct path both derive from it). Change the id (`new Auth(scope, 'auth')` → `'users'`), move the block under another scope, or delete it, and the pool leaves the template: CloudFormation deletes it and every user in it — or, under `removalPolicy: 'retain'`, detaches it from the stack and keeps it, orphaned. The block's own baseline check cannot see this (nothing reads the old file any more), and layer 2 is removed together with the last pool. This is the most likely way to lose a user directory, so synth refuses it (task D4b).

**The check.** Every `BlocksStack` / `BlocksBackend` gets one construct validation (`addOrphanedBaselineCheck` in `packages/core/src/cdk/baselines.ts`, registered in both constructors). At synth it lists `baselines/<stack>/*.json` and fails for each file that carries a `removalGuard` and that no block in this stack claimed. Each `Auth` block claims its own file at construction (`claimBaseline`), and writes `removalGuard` exactly when it owns its pool; a pool-less baseline (`ownsPool: false`) has none, so removing a pool-less block is fine. The message names the orphaned `fullId`, states that CloudFormation will delete the Cognito user pool and every user in it, and gives the remedies below.

- **Why in core.** It has to run when the app has *no* `Auth` block left — and then `@aws-blocks/bb-auth` need not even be imported, so no code of its own runs. The stack is the only thing that always exists. The check needs nothing from the block: the file describes itself (`removalGuard.deletes`, `rebaselineEnv`, `runbook`), so core stays free of any Cognito knowledge and any future block can use the same protocol.
- **Per stack.** Only `baselines/<this stack>/` is read (the `BlocksStack` id, or the `BlocksBackend` `fullId`), so another stack's baselines never trigger it.
- **No stray baseline from a failed synth.** While the stack has an orphan (`hasOrphanedBaselines`), an `Auth` block with no baseline yet does not write one (an info annotation says so). Otherwise the renamed block's first baseline would be left behind and, once the old id is restored, be reported as orphaned itself.
- **An unreadable, unclaimed file** in the directory (e.g. a merge conflict) fails closed.

**Remedies** (the error lists them):

1. **It was an accidental rename** — restore the old id. Keeping the pool under a new id is not a rename: it needs a CloudFormation resource import ([runbook](#runbook-moving-a-user-pool-to-a-new-logical-id-with-cdk-import)).
2. **Removing the block is intended** — first set `removalPolicy: 'retain'` on it (under its old id) and deploy, so CloudFormation keeps the pool (orphaned, outside the stack) when the block goes. Then remove it and re-baseline (3).
3. **Re-baseline deliberately** — `BLOCKS_AUTH_REBASELINE=<old fullId>` on the synth/deploy command deletes the stale baseline file (commit the deletion). It must name the `fullId`; `=1`, `true` or another block's id do nothing, so a leftover variable cannot disarm the check. Combined with a rename it accepts the rename: the old file is deleted and the new id gets a fresh baseline. Without `retain`, the next deploy deletes the pool.

### Hosted-UI federation (D3b)

Provisioned **only** when at least one provider federates through Cognito: any `socialProviders` or `samlProviders` entry, or an `oidcProviders` entry with `federateVia: 'cognito'` (`cognitoFederatedProviderIds()`). Directly federated OIDC (the D0 default) needs none of it. Without such a provider nothing below is synthesized and the template is exactly the email + password one — B1's fixture and the property snapshot run unchanged, and `federation.cdk.test.ts` asserts that the default and direct-only templates contain no domain, extra client, IdP, registration Lambda or federation config key. Code: `src/cdk/federation.ts` (constructs) and `src/cdk/federation-providers.ts` (pure option → registration mapping and checks).

| Child id | Resource | Notes |
|---|---|---|
| `domain` | `AWS::Cognito::UserPoolDomain` | Prefix domain; see [the prefix rules](#domain-prefix). **Create-only.** |
| `hosted-ui-client` | `AWS::Cognito::UserPoolClient` | A **separate** client — never `client`, whose `GenerateSecret` is replace-only and whose replacement would invalidate every refresh token. Public (no secret), authorization-code grant (the runtime sends PKCE), scopes `openid email profile`, explicit auth flows refresh-only, `SupportedIdentityProviders` = exactly the configured federated providers (no `COGNITO`: password sign-in goes through `client`). Depends on every IdP resource. |
| `idp-<id>` | `Custom::BlocksAuthIdentityProvider` | Google, Facebook, Login with Amazon, Sign in with Apple, and `federateVia: 'cognito'` OIDC — every provider that carries a secret. Depends on `BlocksSecretsBulk` when present. |
| `saml-<id>` | `AWS::Cognito::UserPoolIdentityProvider` | SAML carries no secret, so it is a native resource (metadata URL or inline file; `RequestSigningAlgorithm: rsa-sha256` with `signRequest`). |
| `idp-registration-fn`, `-logs`, `-provider`, `-provider-logs` | Lambda + `Provider` | Only when an `idp-<id>` exists. Log retention follows the stack default. |

**Why a deploy-time Lambda, not `ProviderDetails: '{{resolve:ssm-secure:…}}'`.** Provider secrets are `AppSettingRef`s (SSM SecureStrings). CloudFormation supports `ssm-secure` dynamic references only on a fixed list of resource properties, and `AWS::Cognito::UserPoolIdentityProvider.ProviderDetails` is not on it ([Get a secure string value from Systems Manager Parameter Store](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-ssm-secure-strings.html), *Resources that support dynamic parameter patterns for secure strings*); the same page says secure dynamic references are not supported in custom resources at all. So `Auth` ports `AuthOIDC`'s deployed approach: each `idp-<id>` carries the non-secret `ProviderDetails` plus `SecretDetails` — a map from detail key (`client_secret`, or Apple's `private_key`) to the SecureString **name** (the `AppSetting`'s `parameterName`; `/<fullId>` by default) — and `src/idp-registration-lambda.ts` reads and decrypts them at deploy time and calls `Create/Update/DeleteIdentityProvider`. The secret value never enters the template. A `Trigger` nonce changes every synth so a rotated secret is picked up on the next deploy (an idempotent update, shown in every `cdk diff`). The handler upserts (create, or update if the name already exists with the same type) and deletes only a provider whose type matches its own physical id, so a type change cannot delete its replacement. Its IAM: `Create/Update/Delete/DescribeIdentityProvider` on this pool, `ssm:GetParameter` on exactly the referenced parameters, `kms:Decrypt` via SSM.

**Providers.** Social providers use Cognito's fixed provider names (`google` → `Google`, `facebook` → `Facebook`, `amazon` → `LoginWithAmazon`, `apple` → `SignInWithApple`); OIDC and SAML use the provider id, which must be a valid Cognito provider name (3–32 characters, not `Cognito` or a social name). `cognitoProviderName()` / `cognitoFederatedProviders()` in `contract.ts` give the runtime the same names (`identity_provider=` on `/oauth2/authorize`). Sign in with Apple is a real `SignInWithApple` provider (Services ID, `teamId`, `keyId`, the `.p8` key as `private_key`) — `AuthOIDC` validated it as built-in but synthesized `ProviderType: 'OIDC'` and silently dropped it without an issuer URL. Default scopes: Google and OIDC `openid email profile`, Facebook `public_profile,email` (comma-joined, as Cognito expects), Amazon `profile`, Apple `email name`. OIDC passes `oidc_issuer`, `attributes_request_method` (default `GET`) and the four `endpoints` when given.

**Attribute mapping is declarative.** Defaults: `{ email: 'email', name: 'name' }` for social and OIDC, `{ email: '<the emailaddress claim URI>' }` for SAML; `attributeMapping` entries are merged over them (the caller wins). A key must be a Cognito standard attribute or a declared `users.attributes` name (emitted as `custom:<name>`); identity keys (`sub`, `userSub`, `userId`, `username`) are rejected, matching the type.

**Callback and logout URLs — the real front door.** `AuthOIDC` registered `https://localhost/aws-blocks/auth/callback` and never wired the real URL. `Auth` registers `<origin><callbackPath>` and `<origin><signOutPath>` (defaults `/aws-blocks/auth/callback` and `/aws-blocks/auth/signout`, `federationRedirectPaths()`), for each origin the browser can reach the auth routes through:

1. **The API's own URL** — the base of the block's compute `apiUrl` (`https://<api>.execute-api.<region>.amazonaws.com/<stage>`), split exactly as core's `Hosting` does (`Fn::Select(0, Fn::Split('/aws-blocks/api', apiUrl))`). This is the front door in sandbox mode and for a backend-only deploy.
2. **The `Hosting` public origin** — core's `Hosting` registers `BLOCKS_PUBLIC_ORIGIN` = `hosting.distributionUrl` (the custom domain when configured, else the CloudFront domain) in the stack's config registry; `AuthOIDC`'s runtime already prefers it for `redirect_uri`. `Hosting` is constructed after the backend module, so `Auth` reads it through a `Lazy` at template resolution. There is no cycle: the distribution does not depend on the app client.

Both are deploy-time tokens, never a placeholder. If neither exists, synth fails with the reason. The runtime (D6) must send exactly one of these as `redirect_uri` / `logout_uri`.

**Config keys** (`federationConfigKeys()`, registered only in a federated configuration): `BLOCKS_AUTH_COGNITO_<UPPER_FULLID>_DOMAIN` — the hosted-UI host `<prefix>.auth.<region>.amazoncognito.com` — and `…_HOSTED_UI_CLIENT_ID`. The frozen three keys are untouched.

**IAM for the runtime: none added.** The hosted-UI `/oauth2/token`, `/oauth2/revoke`, `/oauth2/userInfo` and `/logout` endpoints are OAuth HTTP endpoints, not SigV4 APIs; group reads for Cognito-federated users use the existing base statement (`AdminListGroupsForUser`). `federation.cdk.test.ts` checks that the shared role's policy is unchanged when a provider is added.

**`emailPassword: false`** restricts the native `client` to refresh-token only (see [Mapping notes](#mapping-notes)); its logical id and every other property are unchanged, which `federation.cdk.test.ts` asserts.

**Synth-time checks** (`federation-providers.ts`): a provider id used in two records; a provider id containing `/`; an invalid or reserved Cognito provider name; SAML with neither or both metadata sources, or a non-https URL; missing Apple team / key id; a plain-string secret, a non-secret `AppSetting`, or a secret that is not an `AppSetting`; `federateVia: 'cognito'` without `clientSecret`; an unknown social key; an unmappable attribute; a `redirects` path outside `/aws-blocks/auth/` or with a wildcard, query or fragment; an invalid `hostedUi.domainPrefix`; and hosted-UI federation on a wrapped `userPool` (refused: `Auth` would create a domain and IdPs on a pool it does not own).

**Provider secrets resolve through `AppSetting.parameterName`.** The SecureString name in `SecretDetails` (and in the registration Lambda's `ssm:GetParameter` grant) is the referenced `AppSetting`'s `parameterName` — read from its CDK layer, so it is exactly the name its runtime reads: the default `/<fullId>`, an explicit `name`, or an `AppSetting.fromExisting()` name all work. `secretParameterName()` (`federation-providers.ts`) **fails at synth**, naming the provider, for an `AppSetting` without `secret: true` (its `secret` is `false`: a provider secret in a plaintext SSM `String` is readable by anyone with `ssm:GetParameter`) and for an object that is not an `AppSetting` (a hand-made `{ fullId, get }` has no `parameterName`, and guessing `/<fullId>` could point the IdP at a parameter that does not exist). It never mis-resolves at deploy. An `AppSetting.fromExisting()` secret is owned outside the stack: it must exist before the deploy, and the registration needs no ordering on `BlocksSecretsBulk`. A customer-managed KMS key is covered by the Lambda's `kms:Decrypt` (via SSM), provided the key's own policy allows the role. (Before D3c, `AppSetting` did not expose its name, so `Auth` accepted only stack-managed secrets at the default name.)

#### Domain prefix

Derived by `deriveDomainPrefix(fullId)`: lowercase `fullId`, non-alphanumerics → `-`, Cognito's reserved words (`aws`, `amazon`, `cognito`) removed, truncated to 54 characters, then `-` + the first 8 hex characters of `sha256(fullId)`. The result always matches Cognito's pattern (`^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`, ≤ 63 characters, no reserved word — hex digits cannot spell one) and is deterministic, so the IdP redirect URI (`https://<prefix>.auth.<region>.amazoncognito.com/oauth2/idpresponse`, or `/saml2/idpresponse` for SAML) is known before the first deploy. Prefixes are global per region across all AWS accounts; `fullId` is unique enough in practice because scaffolded stack ids carry a random suffix, and the hash separates two long `fullId`s that differ only past the truncation point. `federation.cdk.test.ts` pins the algorithm's output.

`hostedUi: { domainPrefix }` overrides it (validated the same way). ⚠️ **Treat both as create-only.** `UserPoolDomain.Domain` is replace-only and globally unique: changing the prefix (or the block id, which changes `fullId`) deletes the domain, signs out every hosted-UI session, and breaks the redirect URI registered in every upstream IdP console until it is re-registered. It is `AuthOptions.hostedUi.domainPrefix` (`HostedUiOptions`), whose JSDoc carries the same warning.

#### Upgrading from `AuthOIDC`'s `cognitoFederated()`: the domain collision

`AuthOIDC` puts its domain (prefix = the provider's `cognitoDomain`) on its own pool at child id `cognito-pool`. Switching to `Auth` creates `pool` and `domain` and deletes the old ones, and CloudFormation creates before it deletes. With the derived prefix there is no collision — but every upstream IdP must then have the new redirect URI registered. If you set `hostedUi.domainPrefix` to the **old** prefix to keep the existing IdP redirect URIs, the new domain is created while the old one still exists and the deploy fails (prefixes are globally unique). Use two deploys:

1. Deploy without the old Cognito federation: remove the `cognitoFederated()` entries from `AuthOIDC`, or — if they were its only providers (`AuthOIDC` requires at least one) — remove the `AuthOIDC` block. The old `cognito-pool` and its domain are deleted, freeing the prefix. Cognito-federated sign-in is unavailable until step 2 completes, and the shadow users are lost either way (see the strategy doc's upgrade table).
2. Switch to `Auth` with `hostedUi: { domainPrefix: '<the old cognitoDomain>' }` and deploy. The IdP redirect URIs keep working.

## `validateUser` and the PreSignUp trigger (Q10)

Decision Q10: `validateUser` runs on **both** sign-in and sign-up, and a Cognito PreSignUp trigger is provisioned **only when the option is set**. Before FX2 the trigger was documented but not built, so a `SignUp` sent straight to Cognito (the hosted-UI client id is in every authorize URL), an `AdminCreateUser` from the console, and a social / SAML first sign-in all created pool users `validateUser` never saw.

**Where it runs.**

| Path | `phase` | Runs in | Notes |
|---|---|---|---|
| `auth.signUp()` | `signUp` | the app request (in-process), before `SignUp` | then the trigger, which recognises the marker and skips |
| `auth.admin.createUser()` | `signUp` | the app request, before `AdminCreateUser` | same; `provider: 'password'` |
| `SignUp` straight to Cognito | `signUp` | the trigger (`PreSignUp_SignUp`) | no marker → validated |
| `AdminCreateUser` from the console / CLI | `signUp` | the trigger (`PreSignUp_AdminCreateUser`) | no marker → validated |
| first sign-in of a social / SAML / `federateVia: 'cognito'` user | `signUp`, then `signIn` | the trigger (`PreSignUp_ExternalProvider`), then the callback | a federated user's first sign-in runs both phases |
| every sign-in (any mechanism) | `signIn` | the app request, before the session is issued | unchanged |
| directly federated OIDC (incl. `stubIdp()`) | `signIn` only | the app request | no pool user is ever created, so there is no sign-up phase on either runtime |

**CDK** (`src/cdk/pre-sign-up.ts`). Only when `validateUser` is set **and** the block creates its pool (`userPool` wraps someone else's pool and its triggers — synth warns `@aws-blocks/bb-auth:ValidateUserExternalPool` instead):

- `LambdaConfig.PreSignUp` on `pool` → the shared backend Lambda (`BlocksStack.handler`): the callback is app code, so the trigger must run the app's backend. Set as a property override on the L1 pool, not with `UserPool.addTrigger()`, whose permission id (`PreSignUpCognito`, under the function) would collide for a second `Auth` block.
- `pre-sign-up-permission` — `AWS::Lambda::Permission`: `lambda:InvokeFunction` for `cognito-idp.amazonaws.com`, `SourceArn` = this pool's ARN, `SourceAccount` = the stack account.
- **The cycle.** The pool now references the function; CDK makes the function depend on its role's whole subtree, including the default policy; and the block's `cognito-idp:*` grants on that default policy reference the pool ARN — pool → function → default policy → pool. The standard fix: with a trigger, those grants go into a separate `iam.Policy` (`pool-access`) attached to the same role, which the function does not depend on. Same statements, same pool-ARN scope, no wildcard. (On the deploy that adds `validateUser`, the statements move between two policies of the same role; IAM is eventually consistent, so expect at most a few seconds in which a request may see `AccessDenied` — the same window any grant change has.)
- `LambdaConfig` updates in place (no pool replacement) and is outside the four properties the [immutability guard](#immutability-guard-q5) watches, so adding or removing `validateUser` is a permitted change on both guard layers (`immutability-guard.cdk.test.ts`, *adding validateUser*).
- With the option unset nothing here runs: B1's identity fixture, the property snapshot and the guard tests are unchanged. No config key is added either way.

**Routing** (core, `lambda-handler.ts`). A Cognito trigger event (`triggerSource` + `userPoolId`) is its own event class, `cognito-trigger`, outside the HTTP timeout guard. Core looks up the handler registered under `EventSourceMapping.COGNITO_USER_POOL` (`aws:cognito-idp`) **and the event's user pool id** — the event carries no block id — awaits it, and returns the event unchanged: a handler accepts by resolving and rejects by throwing, and can never flip `response.autoConfirmUser` / `autoVerifyEmail` / `autoVerifyPhone`. An event for a pool no block registered fails the invocation, so Cognito rejects (fail closed) with a message naming no resource. The AWS layer (`index.aws.ts`, `AuthLayer.preSignUpTrigger`) registers an `Auth` under its `…_USER_POOL_ID` config value **only when the CDK layer flagged it as the trigger's owner**: the CDK layer registers `BLOCKS_AUTH_COGNITO_<UPPER_FULLID>_PRE_SIGN_UP_TRIGGER = 'true'` (`preSignUpTriggerConfigKey`) exactly when it wires `LambdaConfig.PreSignUp` (`ownsPreSignUpTrigger`: `validateUser` set and the pool is the block's own), and the runtime reads that flag rather than inferring ownership from the pool id. A second `Auth` wrapping the same pool (`userPool: Auth.fromExisting(…)`, e.g. for `admin`) therefore registers nothing; before this, it claimed the same key and, the registry being last-one-wins, silently replaced the owner's handler so every sign-up was accepted unchecked (R2-1). Core now also refuses a second registration for one key (`Scope.registerLambdaEventHandler` throws), so no future overlap can fail open. Mid-deploy, code and config can briefly disagree; every mix fails closed or runs the current check: the flag without `validateUser` (being removed) registers a handler that accepts, `validateUser` without the flag (being added) registers none, so core rejects the event until the config arrives. The mock layer registers nothing.

**Mapping** (`candidateFromTrigger`). `PreSignUp_SignUp` and `PreSignUp_AdminCreateUser` → `provider: 'password'`, built by the same `passwordSignUpCandidate()` the in-process path uses: `username` is the login (on a username-attribute pool Cognito's `userName` is a generated UUID, so the login is the email / phone attribute it filled; in-process, the attribute is filled from the login the same way). `PreSignUp_ExternalProvider` → the provider id behind the `<ProviderName>_<id>` prefix of `userName` (matched case-insensitively against `cognitoFederatedProviders()`; `Google` → `google`), `username` = Cognito's username. Always `phase: 'signUp'`, `subject: ''` (no pool user yet), `email` = the `email` attribute, `claims` = the user attributes Cognito passes. Any other event (another trigger source, no `userName`) is rejected.

**Order and idempotency.** In-process **first**: a rejection then reaches the client exactly as locally (same `ApiError`), and the trigger is only a backstop. The Cognito call then carries `ClientMetadata['blocks:auth:validated']` = `v1.<exp>.<base64url(login)>.<HMAC-SHA256>`, keyed by a key HKDF-derived from the session secret (`info` = `aws-blocks/bb-auth pre-sign-up marker v1`, the auto-sign-in bridge's `deriveKey`; R2-5 — so a marker and a session cookie are tags under unrelated keys, not just over differently formatted messages) and bound to the block's `fullId`, the login and a 5-minute expiry. The trigger skips `validateUser` for a marker that verifies and names this user (`userName`, or the email / phone a username-attribute pool filled); anything else — no marker, another block's, another user's, expired, tampered, or an unreadable secret — means it validates. Cognito passes `ClientMetadata` only server-to-server and the marker cannot be forged without the secret, so a direct `SignUp` cannot opt out. The caller's own `clientMetadata` is kept alongside; without `validateUser`, nothing is added.

**Rejecting.** The trigger maps the thrown value with the in-process policy (`toAuthApiError`: an `ApiError` keeps its name, status and message, scrubbed of ARNs and account ids; anything else becomes `InternalErrorException` with the generic message, logged server-side), encodes it as `bb-auth-rejection:<base64url JSON {n, s, m, r}>` (`trigger-rejection.ts`) and throws a plain `Error` with that message — nothing enumerable rides along. Cognito answers `UserLambdaValidationException` with `PreSignUp failed with error <message>.`, or, for managed login, redirects with that text in `error_description`. The app decodes it in two places: the error policy (`error-mapping.ts`, for `SignUp` / `AdminCreateUser`) and the hosted-UI callback (`federation-hosted-ui.ts`), so the client gets the developer's `AuthErrors` name and message, never the Cognito wrapping. A foreign `UserLambdaValidationException` (a trigger on a wrapped pool) gets the name's fixed message, its text logged (FX59; before, it passed through unchanged). The decoder is strict (name pattern, 4xx/5xx status, bounded message); anything else falls back to the ordinary mapping.

**Limits.** Cognito waits at most 5 seconds for a trigger and retries a timeout; the shared Lambda's cold start (config load + backend import) counts against it, so a slow `validateUser` or a cold start can surface as `UnexpectedLambdaException` (500, generic) — the user is not created. **This is a documented limitation.** Mitigation: keep `validateUser` fast (no slow network calls; cache any allowlist it fetches), and if the shared Lambda's cold start alone approaches the budget, configure provisioned concurrency on it. The trigger is skipped only on the in-process path, so a direct `SignUp` costs one extra Lambda invocation per attempt.

**Tests.** `pre-sign-up.cdk.test.ts` (trigger + scoped permission only when set; nothing else changes; no dependency cycle, checked on a real `BlocksStack` too; two blocks; wrapped pool; pool-less), `presignup-trigger.test.ts` (mapping per trigger source, marker, encoding), `index.aws.presignup.test.ts` (offline AWS runtime: Cognito played by `test-support/cognito-trigger.ts` invoking core's real Lambda handler), `federation-hosted-ui.test.ts` (*Q10*: a federated first sign-in rejected in the trigger, through the real routes and the fake managed login), `parity.presignup.test.ts` (mock ↔ AWS), and `test-apps/comprehensive/test/auth-validate-user.test.ts` (e2e: password sign-up and stub-IdP sign-in rejected locally; a direct `SignUp` against a deployed pool, sandbox-gated).

|---|---|---|
| email + password, social, SAML, OIDC with `federateVia: 'cognito'` | the username (on an email / phone-only pool, Cognito's generated one — see below) | the Cognito `sub` |

### Usernames and `users.signInWith` (D5d)

`signInWith` maps to one of Cognito's two sign-in models (`mapSignInWith`; the runtime reads the same split, `sign-in-mode.ts`). Both runtimes behave as Cognito documents ([sign-in attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html#user-pool-settings-aliases)):

| | `signInWith` without `'username'` (e.g. `['email']`) → `UsernameAttributes` | `signInWith` with `'username'` (the default `['username', 'email']`) → `AliasAttributes` |
|---|---|---|
| Stored username = `userId` = `cognito:username` | **generated, equal to `userSub`** — "The `SignUp` API populates the `username` attribute with a UUID for your user. This UUID has the same value as the `sub` claim"; `AdminCreateUser`: "Amazon Cognito automatically generates a username value" | the one the user chose |
| `email` / `phone_number` attribute | filled from the email / phone given as the username ("the user pool automatically populates the `email` attribute of the user with the `username` value") unless the caller set it | only what the caller sets — nothing is copied from the username |
| What `signUp` / `admin.createUser` accept as the username | an email / phone (else `InvalidParameterException`); one already in use is `UsernameExistsException` | anything **not** in the format of an alias attribute ("Amazon Cognito doesn't accept a username that matches a valid email address format") |
| What every other call accepts as the username | the generated username, or the email / phone (verified or not) — `admin.scan`'s `username` filter takes the generated one only, as `ListUsers` | the username, or a **verified** email / phone ("only become active aliases … after your user verifies") |
| Who may have the email / phone (FX49) | one user only, verified or not ("must not already be in use by another user. It doesn't have to be verified"): `signUp` / `admin.createUser` with one in use → `UsernameExistsException`; `updateUserAttributes` to one in use → `AliasExistsException` (the name is inferred: the guide names none, `UpdateUserAttributes` lists `AliasExistsException`; L2) | any number of users, but **verified** on one only ("can be in a verified state in only one account"): `signUp` accepts a duplicate ("registration succeeds"); `confirmSignUp` with the right code for one another user holds verified → `AliasExistsException`, the user stays unconfirmed (the code is checked first); `confirmUserAttribute` **moves** it, unverifying the other user's copy (no error); `admin.createUser` marking it verified → `AliasExistsException`. `Auth` never sends `ForceAliasCreation` |

So on an email-only pool, key app data on `userSub` (= `userId`), and show `attributes.email`. `admin.revokeUserSessions(email)` also deletes the session rows of that user (their rows carry the generated username; they are matched on the ID token's sign-in attribute). The `AdminCreateUser` attribute fill is stated by the docs for `SignUp` only; the parity harness applies it to both, and a sandbox run (L2) should confirm it.

**Groups.** `requireRole()` reads the user's current group membership on each guarded request (`AdminListGroupsForUser`, deduplicated per request), as `AuthCognito` does since #583, and narrows the result to the declared groups. A user deleted upstream fails closed with `403`. Directly federated users have no pool record; their groups come from the provider's `groupsClaim`.

## Mode gates

A gated method takes a trailing rest parameter typed by `PasswordGate<O, T>` (email + password methods) or `FederationGate<O, T>` (federated sign-in). `T` is the method's ordinary trailing optional parameters.

- Mode enabled → the gate resolves to `T`, so the method reads and calls normally.
- Mode disabled → the gate resolves to `[ERROR_…: never]`, so every call is a compile error.

`src/types-test.ts` proves the gate cases at compile time; `src/gate-diagnostics.test.ts` asserts the compiler's message text. Three findings from building them shaped the design:

1. **Why a parameter, not a conditional property type.** A conditional over the class's own `O` in a property position made `AuthCognito<O>` invariant in `O` and regressed 14 call sites. A rest parameter keeps `Auth<O>` assignable to `Auth`; `types-test.ts` case 9 guards it.
2. **The rest parameter is named after the error.** The TypeScript compiler (5.9) never prints a tuple element's label in an arity error; it prints the rest parameter's *name* ("Arguments for the rest parameter 'ERROR_emailPassword_is_disabled_on_this_Auth_instance' were not provided."). Naming the parameter is what puts the message in the diagnostic. The tuple label still appears in hover and signature help.
3. **The gate absorbs the trailing optional parameters.** If an optional parameter preceded the gate (`signIn(u, p, ctx, options?, ...gate)`), a disabled call that omits it is reported as "An argument for 'options' was not provided" — pointing at the wrong fix. Hence `signIn(u, p, ctx, ...gate: PasswordGate<O, [options?: SignInOptions]>)`.

**The wide `Auth` type** (no type argument, or options passed through a `: AuthOptions` variable) behaves like the zero-config instance, widened just enough that every configured instance is assignable to it:

- Email + password is *unknown* (`EmailPasswordEnabled` is `boolean`): the gate accepts both resolutions, so calls compile and the runtime `EmailPasswordNotEnabledException` backs them. Cost: hovering a password method on a zero-config instance shows the union, including the `ERROR_…` name.
- Federation is *closed* (`HasFederatedProvider` is `false`): `new Auth(scope, 'auth').getSignInUrl(…)` is a compile error, and a helper typed `(auth: Auth)` cannot call federation methods — type it with the instance's own type (`typeof auth`) instead.

Each gate is backed at runtime (D5/D6) by an `ApiError` — `EmailPasswordNotEnabledException` / `NoFederatedProviderException` — for untyped JavaScript callers.

**D5b's gates**, on the same rest-parameter technique:

| Gate | Methods | Open when | Wide `Auth` | Runtime backstop |
|---|---|---|---|---|
| `PasswordGate` | `scanDevices`, `rememberDevice`, `forgetDevice` | email + password on | open (union) | 409 `EmailPasswordNotEnabled` |
| `MfaGate` | `setUpTotp`, `verifyTotpSetup`, `updateMfaPreference`, `getMfaPreference` | `mfa` is `'optional'` / `'required'` (or `{ mode }`), and email + password on | open (union) | 400 `InvalidParameter` |
| `PasskeyGate` | `startPasskeyRegistration`, `completePasskeyRegistration`, `listPasskeys`, `deletePasskey` | `passkeys` is an options object, and email + password on | open (union) | 400 `WebAuthnNotEnabled` |
| `AdminGetterOf` | `auth.admin` | `admin` is an object (`admin: true` is rejected) | `AdminSurface \| AdminDisabled` — unusable without narrowing | `Error('admin not enabled …')` |
| `AdminActionGate` | each admin method | `admin.actions` omitted or lists the method's group | open (union) | 403 `NotAuthorized` |

User attributes and `deleteUser` are ungated (every configuration; a direct-OIDC user gets their session's profile claims from `getUserAttributes` and a 400 from the writes).

Three findings shaped these. (1) A gate that resolves to `T` on the wide type breaks variance when a narrow instance closes it: `(u, x: never) => P` is not assignable to `(u) => P` (arity, not bivariance). So `AdminActionGate` resolves to `T | [never]` for the wide `AuthOptions`, like `PasswordGate`. (2) A gate that is *closed* (`[never]`) on the wide type is fine for concrete instances, but a **generic** `Auth<O>` is then not assignable to the wide `Auth`: TypeScript relates `[never]` to the deferred `MfaGate<O>` branch by branch, and `[never]` is not assignable to an on-branch `[]`. (`FederationGate` survives this only because every method behind it has an optional parameter in `T`.) D5c's AWS test harness hit exactly this, so `MfaGate` and `PasskeyGate` resolve to the union on the wide type too — which also makes them callable on `new Auth(scope, id)` with no options (indistinguishable from the wide type), backed at runtime, the same trade-off `PasswordGate` makes. `types-test.ts` case 17 pins the generic assignment. (3) `AuthCognito`'s `AdminGetterOf` was `AdminDisabled` on the wide type, which made every admin-enabled instance unassignable to a plain `AuthCognito` (its `admin.types-test.ts` case 8 documented the exception); `Auth`'s is the union of both branches, so `types-test.ts` case 9 includes an admin-enabled instance and case 16 asserts the wide type still cannot reach the surface. `AdminActionGate` also absorbs the trailing optional parameters (`createUser(username, ...gate: AdminActionGate<O, 'lifecycle', [init?]>)`), like the other gates, so the diagnostic names the gate (`gate-diagnostics.test.ts`).

## Unknown options (D1b)

`Auth<const O extends AuthOptions>` infers `O` from the options literal, and TypeScript performs no excess-property check on an inferred type argument. Only a literal whose keys are *all* unknown is caught (it shares nothing with the all-optional `AuthOptions`, so TypeScript's weak-type check rejects it). So `{ emailPasword: false, session: { … } }` or a top-level `{ preferredChallenge: 'EMAIL_OTP', users: { … } }` compiled, and the setting was silently dropped. For an auth block, a security setting the developer believes is on would simply not apply.

**Runtime check.** Every entry's constructor (the mock and AWS `Auth` through `AuthBase`, plus the CDK `Auth`) calls `assertKnownAuthOptions` (`src/option-validation.ts`) before `super()`, so the same configuration fails the same way in `npm run dev`, at synth and in Lambda, and a rejected block never registers its id. The validator walks the options against a tree of known keys at every level: each group (`emailPassword`, `users`, `session`, …), array entries (`users.attributes[i]`, `users.groups[i]`, `stubIdp.users[i]`), and the *values* of the provider records. Provider ids are user-chosen, so they are never checked. `socialProviders` is a closed set, so its keys are checked. An OIDC entry's accepted keys depend on its engine: `federateVia: 'cognito'` accepts `attributesRequestMethod` but not `groupsClaim`, `oauth2` or `stubIdp`, and the error says which engine an option needs. Reference objects (`AppSettingRef`s, `Auth.fromExisting()`, a `Logger`), callbacks and free-form maps (`attributeMapping`, `StubUser.extra`) are not walked. A shorthand value (`emailPassword: true`, `mfa: 'required'`, `passkeys: false`) is not an object, so there is nothing to walk. The error lists every unknown key with its path and a hint, in this order: a case-only typo of a sibling; the same key where it belongs (`users.preferredChallenge`); a close sibling (edit distance, counting a transposition as one edit); a close key elsewhere. `codeDelivery` is known to every entry: the backend module type-checks against the mock's types and runs unchanged under the AWS and CDK entries, which ignore it.

**Boolean values are type-checked too** (R86, FX53). Each layer reads a boolean option by truthiness or `!== false`, so an untyped caller's non-boolean value decided the setting by accident: `selfSignUp: 0` enabled self-service sign-up (`selfSignUpEnabled`: `0 !== false`), `passkeys: 'false'` enabled passkeys. Every option typed `boolean` (`selfSignUp`, `autoSignIn`, `revealExistingUsers`, the four `passwordPolicy.require*`, `signRequest`, `stubIdp.unsafeAllowDeployed`, `users.attributes[].mutable` / `required`, both `users.deviceTracking` flags, `session.crossDomain`, `allowBearerAuth`, `deletionProtection`) must be `true`, `false` or `undefined`, and a group with a boolean shorthand (`emailPassword`, `passkeys`) must be a boolean or an object. The error lists each wrong value with its path and type (`` `emailPassword.selfSignUp` must be `true` or `false`, got the number 0 ``), after any unknown options. `passkeys: true` is a type error but a boolean, so it passes this check as before; synth then fails asking for `passkeys.relyingPartyId`. Strings, numbers and references are not type-checked.

**One source of truth.** Each node of the known-key tree is declared `satisfies ShapeOf<T>` against its interface in `types.ts`. That requires exactly `T`'s keys, so a key added to or removed from `types.ts` without the same change in the validator fails the package build. It also requires a walked spec, not `'value'`, for any key whose type is an options group, so a new nested group cannot be left unchecked, and `'boolean'` for any `boolean` key (a group that also takes a boolean needs `orBoolean`), so a new boolean option is type-checked. `types-test.ts` case 18 also pins the top-level key set.

**Why not a compile-time check too.** We tried an exact constructor parameter, `options?: O & ExactAuthOptions<O>`, with unknown keys at any depth mapped to an `'ERROR: not an Auth option …'` literal. It works for inline literals, and the gates, variance (`takesWide`, case 17) and `gate-diagnostics.test.ts` all stayed green. Two things broke:

1. `stubIdp()` / `github()` return subtypes whose extra keys (`stubIdp`, `oauth2`) the declared `OidcProviderOptions` union doesn't list. This is fixable by widening the shape the check uses.
2. **Generic wrappers.** This is not fixable. No check of that form can be proven for a still-generic `O` (we tried a key-filter mapped type, a non-distributive conditional and a homomorphic mapped type). So `function make<const O extends AuthOptions>(o: O) { return new Auth(scope, id, o); }` stopped compiling, and every generic layer had to re-declare `O & ExactAuthOptions<O>`. Four internal call sites hit this: the AWS harness `makeAwsAuth`, `awsAuth` in `federation-hosted-ui.test.ts`, and `mockSignedIn` / `awsSignedIn` in `parity.test.ts`, with more behind them in `index.aws.errors.test.ts`. The spread-with-defaults wrapper (`new Auth(scope, id, { ...options, codeDelivery })`, a natural "team defaults" helper) can't compile under the deep check at all without a cast.

That is the same kind of call-site regression the mode gates were designed to avoid (14 call sites, see above), and AGENTS.md rule 8 says a needed cast means the public type is wrong. So `Auth` ships the runtime check only. It runs at the first `npm run dev`, synth or unit test. `types-test.ts` case 18 pins both wrapper patterns so a later attempt at compile-time exactness sees what it would break.

## The local user pool (D5b)

`engines/native-mock.ts` is a port of `AuthCognito`'s mock (`bb-auth-cognito/src/index.ts`) behind `NativeEngine`: sign-up with an emailed code (Q2), `USER_PASSWORD_AUTH` and `USER_AUTH` (first-factor selection, email / SMS one-time codes, passkeys), the auto-sign-in bridge (`mock-signup-session-<sub>`, which skips the `USER_AUTH` one-time code as Cognito's SignUp `Session` does), `NEW_PASSWORD_REQUIRED`, MFA selection / setup / TOTP / SMS / email challenges, password reset and change, refresh, live groups, global sign-out, passkeys, the account surface and the admin surface (`native-mock-admin.ts`).

- **Errors are service-shaped**, not `ApiError`s: `serviceError(name, message)` with the Cognito exception name and wording. `AuthBase` maps them through the same `toAuthApiError` as the Cognito engine's, so status, `retriable` and enumeration masking are identical by construction (the mock's own `retriable` reclassification in `AuthCognito` is gone). Engine-side enumeration rules (`engines/types.ts`): `resetPassword` for an unknown user returns `fabricateCodeDelivery(...)`; `resendSignUpCode` resolves; a vanished user mid-challenge and a wrong password on `CONFIRM_SIGN_IN_WITH_PASSWORD` raise `incorrectCredentialsError()`. A wrong code uses Cognito's `CodeMismatchException` wording, which is exactly what an unknown user gets on the confirm-code flows.
- **Tokens: `alg: 'none'`, kept** (`mockJwt`, `AuthCognito`'s format). `AuthBase` never verifies a stored token — rows are reached only through the HMAC-signed cookie, which is the trust chain on both runtimes — so real signatures would buy nothing locally. Unlike `AuthCognito`'s mock (400-day tokens, no refresh), tokens last **1 hour** like Cognito's and carry `auth_time` (kept across refreshes), so the mock exercises `AuthBase`'s refresh path and `requireAuth({ fresh })` measures the sign-in. The ID token carries the user's attributes as Cognito's does: string claims, except `email_verified` / `phone_number_verified`, which are booleans — so, on both runtimes, they are not in `requireAuth().attributes` (the string claims) and reach `getAuthSession`'s ID token and `validateUser`'s `claims` as booleans; `getUserAttributes` and `admin.getUser` report them as the strings `'true'` / `'false'` (FX26; before, the mock's ID token carried the stored strings, so they appeared in `attributes` locally only). Likewise `updated_at` is a JSON number and `address` the OIDC address object `{ formatted }` in the mock's ID token, so neither is in `attributes` either (FX31; Cognito types these two itself — its pre-token-generation docs list them with the two flags as the ID-token claims a trigger can't make complex objects, and its schema types `updated_at` as `Number` — so a deployed app never saw them as string attributes; `getUserAttributes` reports both as strings on both runtimes). The access token carries `mock_token_revision`; a global sign-out (`signOut({ global })`, `admin.revokeUserSessions`) bumps the user's revision, which revokes older access tokens and refresh (as Cognito's `GlobalSignOut` does).
  ⚠️ Because nothing verifies them, mock tokens must never be accepted from a client on their own. With `allowBearerAuth` (D6c) the local layer's `MockPoolBearerVerifier` (`bearer-mock.ts`) accepts a mock access token only when it has this block's exact mock shape (`alg: none`, issuer `https://mock.bb-auth.local/<fullId>`, `client_id` `mock-client-<fullId>`, `token_use: access`, unexpired) **and** the local pool still recognises it (the engine's own access-token check: user exists with that `sub`, enabled, not revoked by a global sign-out). Someone who can read a real token's claims can mint an equivalent one — acceptable locally, and impossible on AWS: only `index.mock.ts` imports `bearer-mock.ts` (pinned by an import-graph test), and the AWS verifier accepts RS256 Cognito signatures only.
- **Codes**: 6 digits, 10 minutes, keyed `<purpose>:<username>` (attribute codes `attribute:<name>:<username>`). Each is written to `.bb-data/<fullId>/last-code.json` (`{ username, code, purpose }`) and passed to `codeDelivery` (`AuthMockOptions`, mock-only; the AWS layer ignores it) — else logged at info level. Challenges last 3 minutes and are persisted, so a dev-server restart mid-MFA keeps the challenge.
- **Contact verification at sign-up** (R67, FX34), as Cognito's developer guide ("Signing up and confirming user accounts") describes it. The pool's `AutoVerifiedAttributes` are the contact members of `users.signInWith` (`mapAutoVerify`; the default `['username', 'email']` auto-verifies the email only). `signUp` stores each email / phone given as unverified (`<name>_verified: 'false'`) and sends **one** code: to the phone when the phone is auto-verified and the user has one (given both, Cognito "chooses to verify the phone number"), else to the email when that is. `confirmSignUp` marks only that attribute verified. Any other contact stays unverified, which affects `displayName`, the `EMAIL_OTP` / `SMS_OTP` first factors, Email / SMS MFA and `getMfaPreference`, until the app verifies it with `sendUserAttributeVerificationCode` + `confirmUserAttribute` (Cognito's `GetUserAttributeVerificationCode` + `VerifyUserAttribute`). `admin.createUser` verifies nothing itself: only the `*_verified` flags the caller passes, as `AdminCreateUser` does. Before FX34 the local `confirmSignUp` marked **both** the email and the phone verified, so a user's phone looked verified locally only. `parity.test.ts` and `native-mock.test.ts` pin each case.
- **User attributes are checked against the pool's schema** (R74, FX39; `engines/mock-attribute-schema.ts`), as Cognito checks `SignUp`, `UpdateUserAttributes`, `AdminCreateUser` and a new-password challenge's `userAttributes` ([attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-attributes.html), [`AttributeType`](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AttributeType.html), [`CreateUserPoolClient`](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html)). The schema is the provisioned one: the standard attributes, the `*_verified` flags and the declared `users.attributes` as `custom:<name>` (`AuthBase` prefixes a declared name written bare; an undeclared bare name stays bare). The whole write is rejected, and nothing stored, when any attribute is: **unknown** (an undeclared `custom:` name included) → `InvalidParameterException`; **not a string** → `InvalidParameterException` (Cognito: "you must pass the value as a string"); **longer than 2,048 characters** → `InvalidParameterException`; `email_verified` / `phone_number_verified` through `signUp` or `updateUserAttributes` → `NotAuthorizedException` (the app client sets no `WriteAttributes`, and Cognito's default write set is the standard attributes; `admin.createUser` may set them, as `AdminCreateUser` may); `sub`, or a `mutable: false` custom attribute after creation (`updateUserAttributes`, a challenge's `userAttributes`) → `InvalidParameterException` ("You can only write a value to an immutable attribute when you create a user"). Before FX39 the mock stored anything, e.g. one attribute named `attributes` holding an object, which a Kotlin client sent before FX32 (R65 (c)), and returned it from `getUserAttributes`. A wrapped pool (`userPool`, `Auth.fromExisting`) has a schema the mock cannot see, so there any `custom:` name is accepted. `parity.attributes.test.ts` pins every case against a stand-in for the documented rules; Cognito's own wording doesn't matter: both runtimes send the name's fixed message (FX59), which the parity tests compare. `Number`-typed custom attributes are not checked for a numeric value, and the standard attributes' formats (`birthdate`, `email`, `phone_number`) are not checked. **On AWS** (R78, FX43) the Cognito engine applies the rules that need no schema itself, before the SDK call: a non-string or over-long value and `sub` → `InvalidParameterException`, a `*_verified` flag through `signUp`, `updateUserAttributes` or a new-password challenge → `NotAuthorizedException`. The AWS JS SDK validates nothing: it sends a number, boolean, object or array `Value` as-is and drops a `null` one, and Cognito's JSON protocol answers a wrong-typed member with `SerializationException`, which would reach the client as a 500 `InternalErrorException`. Both engines take these rules from `engines/attribute-write-rules.ts` (pure, in the AWS import graph; `mock-attribute-schema.ts` adds the schema-dependent rules around them), and a rejected write sends nothing (`index.aws.attributes.test.ts`). Unknown names and immutability stay Cognito's on AWS, since only Cognito knows the deployed schema; its `InvalidParameterException` reaches the client by name, with the fixed message (FX59). **Precedence** (R79, FX44): when one write breaks several rules, both engines name the same one, because both apply the rules in one order, each over the whole write before the next: `signUp` on a pool without self-service sign-up (`selfSignUp: false`, or `emailPassword: false`; `selfSignUpEnabled` in `cdk/contract.ts`, which also sets the pool's `selfSignUpEnabled`) → `NotAuthorizedException`, before any attribute rule, and on AWS without a Cognito call; then any non-string value; then any value over 2,048 characters; then a `*_verified` flag through the app client; then the schema (`sub`, unknown names, immutable attributes). Within a rule the first attribute in input order is named. Cognito documents no order; this one follows how its JSON API reads a request (deserialization, then model constraints, then authorization), and it is the only one in which the AWS engine's answer never depends on the schema it can't see, since every schema rule is the same `InvalidParameterException` and comes last.
- **Password-reset codes go to a verified contact** (R75, FX39), as `ForgotPassword` does ([account recovery](https://docs.aws.amazon.com/cognito/latest/developerguide/how-to-recover-a-user-account.html), [`ForgotPassword`](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_ForgotPassword.html)): the first contact in the pool's `AccountRecoverySetting` priority that is present and verified, skipping the one whose factor is the user's preferred MFA ("Users whose preferred MFA is by SMS message can't receive a password-reset code by SMS"). Every provisioned pool has `verified_phone_number` (1), `verified_email` (2) — CDK's default `AccountRecovery.PHONE_WITHOUT_MFA_AND_EMAIL`, also Cognito's order with no setting — so the phone wins when both are verified. A user with no such contact (an unconfirmed user, or any user on a pool that auto-verifies nothing) gets Cognito's `InvalidParameterException` and no code; `AuthBase` masks it (FX3) unless `revealExistingUsers` is set. Before FX39 the code went to the email if there was one, else the phone, verified or not, and a confirmed user with no verified contact still got one. `parity.reset.test.ts` pins each case.
- **Users** are keyed by username; account calls resolve the user from the access token's `username` and require the same `sub` (a re-created username is a different user), an enabled user, an unexpired and unrevoked token.

### `.bb-data` compatibility with `AuthCognito`

`state.json` is `AuthCognito`'s format, read **as-is** (`native-mock-store.ts` documents it): `{ users, groups, codes, challenges, sessionSecret }`. An app that switches `AuthCognito` → `Auth` with the same id keeps its local users (passwords, confirmation, attributes), group memberships, MFA enrolment, devices, passkeys and — because `sessionSecret` is the field `AuthBase` signs cookies with and the `sessions` store is the same `KVStore` — its signed-in browsers. `Auth` adds two optional user fields `AuthCognito` ignores (`passwordResetRequired`, `tokenRevision`) and keeps unknown top-level keys, so the file stays readable by `AuthCognito` (rollback). Proven both ways in `native-mock.test.ts` with the real `AuthCognito` mock.

**Tolerant loading** — never a throw: a file that does not parse or is not a JSON object is moved aside to `state.json.corrupt-<ISO>` (never deleted) and the pool starts empty; malformed users / groups / codes / challenges are dropped; both are logged at `warn`. The engine writes the file (atomically, write-then-rename) in its constructor, so the session secret is on disk before `AuthBase` first reads it (`readMockSessionSecret`).

Behaviour changes from `AuthCognito`'s mock, all toward Cognito's: `selfSignUp: false` rejects sign-up (`NotAuthorizedException`); `admin.resetUserPassword` makes sign-in fail with `PasswordResetRequiredException` until the forgot-password flow completes (the old mock forced a new password instead); MFA defaults to `mfa.types ?? ['SMS', 'TOTP']` everywhere (the CDK layer's default — the old mock used `['SMS','TOTP','EMAIL']` for preferences); `getUserAttributes` / admin users include `sub`; a confirmed attribute code marks `<name>_verified`; the sign-up code verifies only the contact it was sent to, not every email / phone (FX34); user attributes are checked against the pool's schema (unknown names, non-string or over-long values, the `*_verified` flags, immutable attributes — FX39); a password-reset code goes only to a verified contact, phone first (FX39); `verifyTotpSetup` rejects with `EnableSoftwareTokenMFAException`; the `USER_AUTH` password leg continues into MFA.

## Runbook: moving a user pool to a new logical id with `cdk import`

For the rare case where a pool's construct path must change (for example, a pool created by `AuthOIDC`'s `cognitoFederated()` at child id `cognito-pool`, which `Auth` would otherwise replace with a new `pool`). Rehearse in a sandbox stack first; this runbook is validated by the upgrade-in-place harness (D8), not yet against a live stack.

1. **Protect the pool.** On the current code, set `removalPolicy: 'retain'` and enable deletion protection on the pool, then deploy. Confirm the template shows `DeletionPolicy: Retain` and `DeletionProtection: ACTIVE` on the `AWS::Cognito::UserPool`, and that the deploy was an in-place update (no replacement).
2. **Detach it.** Deploy a version of the stack with the old pool resource removed and the new one not yet added. CloudFormation drops the resource from the stack but keeps the pool, because it is retained. Record the `UserPoolId` first.
3. **Import it.** Switch to the new code (the pool at its new construct path, still `retain`), then run `cdk import` (through the app's usual synth command, which loads the backend with `--conditions=cdk`) and supply the recorded `UserPoolId` when prompted. An import deploy may contain no other changes.
4. **Verify.** `cdk diff` shows no changes to the pool; the `UserPoolId` is byte-identical; an existing user can still sign in.
5. **Re-point.** Update everything that referred to the old resource: app clients, groups and domains that were detached with it (import or recreate them — a recreated app client invalidates its refresh tokens), the runtime configuration, and the redirect URIs registered with each upstream IdP.

## Known gaps (documented, not built)

- **Remembered devices on AWS.** `rememberDevice` throws `501` on the AWS runtime (as `AuthCognito`'s did): Cognito needs the device key from `NewDeviceMetadata` at sign-in, a client-derived device verifier and `ConfirmDevice`, none of which the session layer captures. `scanDevices` / `forgetDevice` work. The local mock mints a synthetic device key.
- **Account linking.** One person signing in with both a password and a social or OIDC provider gets two unrelated users; `Auth` does not link them.

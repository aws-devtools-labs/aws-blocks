# FileBucket — Design

Design document for FileBucket. For usage, see [README.md](./README.md).

**Package:** `@aws-blocks/bb-file-bucket`
**Type:** Primitive (new infrastructure)
**AWS Service:** Amazon S3

## Design Decisions

**D-FB-1: Buffer body type instead of ReadableStream**
**Decision:** `put()` accepts `Buffer | string`, `get()` returns `Buffer` in `FileContent.body`.
**Rationale:** ReadableStream adds complexity for the common case (small-to-medium files). Buffer is simpler to work with in Lambda (where the entire response must be buffered anyway). For large files, presigned URLs (`getUrl`/`putUrl`) are the recommended pattern. This favors client-safe return types.

**D-FB-2: Segregated internal storage in mock**
**Decision:** The mock stores user content, sidecar metadata, and version history under separate sibling roots inside `.bb-data/{fullId}/`:
```
content/{key}                     file body (byte-identical to what was written)
meta/{key}.json                   sidecar metadata
versions/{key}/{versionId}        version body
versions/{key}/{versionId}.json   version metadata
versions/{key}/__deleted__        delete marker (sentinel)
```
**Rationale:** Keeps file content byte-identical (no wrapping format) while guaranteeing internal bookkeeping can never collide with user keys. Co-locating metadata as `{path}.__meta__.json` next to each file and relying on marker substrings would let a user key like `data.__meta__.json` or a directory named `x.__versions__/` be silently hidden or shadowed by `scan()`. Because user content lives only under `content/`, `scan()` walks that root without filtering by bookkeeping-like filenames. On versioned buckets it separately omits keys with an active delete-marker flag.

**D-FB-3: deleteBatch chunks at 1,000**
**Decision:** `deleteBatch()` internally chunks into groups of 1,000 and issues separate `DeleteObjects` calls.
**Rationale:** S3 `DeleteObjects` API supports max 1,000 keys per request. Chunking is transparent to the caller. Batch methods handle pagination internally.

**D-FB-4: Presigned URL default expiry of 3600 seconds**
**Decision:** Both `getUrl` and `putUrl` default to 1 hour expiry.
**Rationale:** Matches the S3 SDK default. Long enough for typical browser upload/download flows, short enough to limit exposure.

**D-FB-5: scan returns AsyncIterable**
**Decision:** `scan()` returns `AsyncIterable<FileInfo>` with internal pagination.
**Rationale:** AsyncIterable is used for unbounded result sets. S3 `ListObjectsV2` paginates at 1,000 keys; the iterable handles continuation tokens transparently.

**D-FB-6: Version-aware runtime API**
**Decision:** Versioning (on by default — see D-FB-10) enables S3 object versioning and unlocks version-aware methods (`listVersions`, `restoreVersion`, optional `versionId` on `get`/`delete`/`getUrl`/`getFileHandle`). With the literal `versioned: false`, versioning is off and the `versionId` options drop out of the typings.
**Rationale:** When versioning is on, the runtime API exposes the full version lifecycle — listing, retrieving specific versions, permanent deletion of individual versions, and restoring old versions. `restoreVersion` is implemented as a CopyObject from the old version (S3 has no native restore), which creates a new version that becomes current.

**D-FB-7: Mock versioning uses filesystem directories**
**Decision:** Versioned mock stores each version in `versions/{key}/v{n}` with monotonic IDs. Delete markers are `versions/{key}/__deleted__` sentinel files.
**Rationale:** Simple, inspectable, and matches the S3 semantics closely enough for local development. Monotonic IDs (`v1`, `v2`, ...) are deterministic and easy to reason about in tests, unlike S3's opaque version IDs. Version history lives under the segregated `versions/` root (see D-FB-2), so it never appears in `scan()` or collides with a user key.
**Limitation:** The sentinel represents only the active deleted state. `put()` removes it rather than retaining a historical delete-marker entry. Deleting a later upload therefore cannot make an earlier marker current again, unlike S3. See "Historical delete markers are not retained" below.

**D-FB-8: Bucket name validated at synth against S3's naming rules**
**Decision:** The derived bucket name (`scope.fullId`) is validated against S3's naming rules (`bucket-name.ts`) before the bucket is constructed. An invalid name throws a `ValidationFailed` error with an actionable message. The same validator runs in the mock constructor so local dev (`bb dev`) fails identically — parity. `FileBucket.fromExisting(...)` skips validation since the name is externally owned.
**Rationale:** S3 bucket names are globally unique and immutable. Truncating to fit 63 chars risks collisions, and a name that shifts between deploys (e.g. after a hash input changes) would orphan or replace the customer's data — a far worse outcome than a fast, fixable synth error. Erroring puts the fix in the developer's hands (shorten a scope id once; the name is then stable forever) and matches the manual-shortening pattern already used in `bb-agent`. This deliberately differs from DynamoDB-backed BBs (KVStore/DistributedTable) which `substring(0, 255)` — DynamoDB's 255 limit is generous and table names are internal, disposable, and not globally unique, so silent truncation is acceptable there.
**Length:** An over-long `fullId` is shortened deterministically rather than rejected — see D-FB-18. Every other naming rule here throws.

**D-FB-9: TLS enforced unconditionally (enforceSSL)**
**Decision:** Every provisioned bucket (the data bucket and the opt-in access-log bucket) sets `enforceSSL: true`, so CDK attaches a bucket policy denying any request where `aws:SecureTransport` is `false`. Not configurable.
**Rationale:** All FileBucket traffic — SDK calls and presigned URLs alike — is already HTTPS, so enforcing TLS closes the in-transit exposure gap with zero functional cost. There is no legitimate reason a FileBucket consumer needs plaintext S3 access, so this is a hard default rather than an option. Covered by the `enforces SSL` CDK test.

**D-FB-10: Versioning on by default**
**Decision:** `versioned` defaults to `true`; consumers opt out with the literal `versioned: false`. The version-aware option typings (`GetOptionsFor` et al.) select the non-versioned (optionless) form only for the literal `versioned: false` — a non-literal `boolean` or an absent value resolves to the versioned-aware form, matching the runtime default.
**Rationale:** Accidental overwrites and deletes are unrecoverable without versioning; defaulting it on makes the safe choice the default and matches the "secure by default" posture of D-FB-9. Prior versions add storage cost, which D-FB-14 bounds. The literal-`false` typing gate is a deliberate consequence of `extends { versioned: false }`: TypeScript cannot narrow a widened `boolean` to the `false` branch, so the versioned-aware typings are the safe fallback.

**D-FB-11: Opt-in server access logging with a dedicated locked-down log bucket**
**Decision:** `accessLogging: true` provisions a second, dedicated S3 bucket (all public access blocked, S3-managed encryption, `enforceSSL`) that receives the main bucket's server access logs under the `access-logs/` prefix. When `accessLogging` is omitted it falls back to `scope.defaults.storageAccessLogging`, then `scope.defaults.accessLogging`. Logs expire via a lifecycle rule after the stack's `scope.defaults.logRetention` (`ONE_WEEK` in sandbox / `ONE_YEAR` in production); `RetentionDays.INFINITE` omits the rule, so logs are kept indefinitely. Retention is not configurable per block — see D-FB-13.
**Rationale:** Access logging is off by default because it has a real cost (extra bucket, log storage) and most consumers don't need an audit trail; making it opt-in keeps the default lean. The log bucket is kept **separate** from the data bucket so log delivery can't loop back onto the bucket being logged.

**D-FB-12: Wildcard-origin CORS + mutating method rejected at synth**
**Decision:** A CORS rule whose `allowedOrigins` includes `'*'` and whose `allowedMethods` includes a mutating method (`PUT`/`POST`/`DELETE`, the `MUTATING_CORS_METHODS` set) throws a synth-time `Error`. Wildcard + safe methods (`GET`/`HEAD`) is allowed; explicit origins + mutating methods is allowed.
**Rationale:** A wildcard origin on a state-changing method lets any website issue authenticated cross-origin writes/deletes against the bucket — a CSRF-shaped exposure. Rather than silently deploying it, FileBucket fails loud at synth with an actionable message pointing the developer at explicit origins. It is a hard error, not a warning: a warning would still let the rule deploy.

**D-FB-13: Posture knobs route through the framework `BlocksDefaults`**
**Decision:** `removalPolicy`, `accessLogging`, and access-log retention are resolved from the stack-wide `BlocksDefaults` model (exposed as `scope.defaults`), not from a `sandboxMode` CDK context read. Each posture knob follows the framework's `options?.field ?? scope.defaults.field` contract (the same pattern `bb-kv-store` uses for `removalPolicy`/`deletionProtection`, and documented on the `Scope.defaults` getter in `@aws-blocks/core/cdk`):
- `removalPolicy` — an explicit per-block `'destroy'|'retain'` wins; when omitted it falls back to `scope.defaults.removalPolicy` (`DESTROY` in the sandbox preset, `RETAIN` in production).
- `accessLogging` — falls back to `scope.defaults.accessLogging` when not set per-block, so a production-postured stack can opt every FileBucket into logging without a per-block flag.
- **access-log retention** — derives from `scope.defaults.logRetention` (a `RetentionDays` enum: `ONE_WEEK` sandbox / `ONE_YEAR` production). `RetentionDays` is a numeric enum whose member value *is* the day count, so it maps directly to `Duration.days(...)`; the one non-day member `INFINITE` omits the lifecycle expiry rule (logs kept forever) rather than expiring at a spurious 9999 days.
**Rationale:** Posture should come from the one stack-level model every block already consumes, not from per-block numbers or a `sandboxMode` context flag. Centralizing on `BlocksDefaults` means a stack picks `BlocksPresets.sandbox`/`.production` once and every FileBucket inherits a coherent removal + logging + retention posture, while per-block overrides remain available for the knobs that accept them (`removalPolicy`, `accessLogging`). This package does not read the `sandboxMode` context.

**D-FB-14: Noncurrent-version expiration bounded by default (90 days)**
**Decision:** When versioning is enabled (the default — D-FB-10), the main bucket gets a lifecycle rule (`ExpireNoncurrentVersions`) that permanently expires **noncurrent** object versions after `noncurrentVersionExpirationDays` (default `DEFAULT_NONCURRENT_VERSION_EXPIRATION_DAYS = 90`). The value's FORMAT is validated at synth whenever the option is provided, regardless of `versioned`: a non-positive or non-integer value throws (a degenerate `Duration.days(0)`/negative would otherwise only surface at deploy — same fail-fast principle as D-FB-8/D-FB-12). The rule itself is only APPLIED when versioning is on. There is no "disable" sentinel; to drop the rule entirely, disable versioning (`versioned: false`), which removes it along with versioning. The rule is inert on the mock and browser runtimes (no AWS resource).
**Rationale:** Defaulting versioning ON (D-FB-10) makes overwrites/deletes recoverable but lets prior versions accrue storage cost without bound. Capping noncurrent versions at 90 days by default keeps the safe-by-default posture affordable — the common case (recover from a recent bad write) is well within 90 days, while stale versions don't pile up indefinitely. It offsets the storage cost of the versioning default.

**D-FB-15: No CORS by default — `corsRules` is explicit, not derived**
**Decision:** A FileBucket created without `corsRules` gets no CORS configuration. CORS origins are not derived from `scope.defaults.allowedOrigins`, not seeded with `http://localhost:3000` by the sandbox posture, and not injected by `Hosting` from its distribution URL. Browser access to a deployed bucket requires an explicit `corsRules` entry; the README's "Browser Uploads and Downloads (CORS)" section documents this.
**Rationale:** Considered and rejected: code defaults (a sandbox-posture localhost origin, or Hosting adding its `distributionUrl` to the FileBuckets it fronts, the way it injects `CORS_HOSTING_ORIGINS` for the API). Each adds configuration overhead — a new `BlocksDefaults` knob or Hosting→FileBucket wiring, plus an opt-out for buckets that should stay server-only — for what most buckets don't need, since most FileBuckets are only accessed server-side. Deriving from the existing inputs also doesn't work: `defaults.allowedOrigins` holds regex patterns that have no S3 `AllowedOrigin` equivalent, and the Hosting URL is a token from a construct created after the backend in `index.cdk.ts`. Documenting the one explicit rule keeps the bucket's exposure visible in the app's own code.

**D-FB-16: Encryption at rest is selectable — SSE-S3 default, SSE-KMS with a dedicated or imported CMK**
**Decision:** `encryption` accepts the same values as `KVStore` / `DistributedTable`: `'aws-managed'` (default, SSE-S3), `'customer-managed'` (SSE-KMS with a dedicated key this block creates, rotation on, sharing the bucket's removal policy), or `FileBucket.fromKmsKey(arn)` (SSE-KMS with an existing key). The value is parsed by core's shared `resolveKmsEncryption` (`@aws-blocks/core/cdk/internal`), the same parser the DynamoDB resolver delegates to, so an unrecognized value fails the synth with an error listing the valid values, exactly as it does for the tables, rather than falling back to SSE-S3 (which would silently downgrade a customer-managed-key request). SSE-KMS buckets enable S3 Bucket Keys. `grantReadWrite` on a bucket with an `encryptionKey` also grants the runtime role the key permissions, so presigned URLs (signed by that role) keep working. The access-log bucket stays SSE-S3 because S3 server access logging can't deliver to an SSE-KMS target.
**Rationale:** `'aws-managed'` maps to SSE-S3 rather than the `aws/s3` KMS key so the default adds no KMS charges or KMS request throttling. The dedicated key is created by this block instead of by `s3.Bucket` so rotation is always on and its removal policy can be set to the bucket's — a sandbox teardown doesn't leave a billed key behind, and a retained bucket is never left without its key.

**D-FB-17: Object Lock with a default retention, rejected at synth when it can't work**
**Decision:** `objectLock: { mode: 'governance' | 'compliance', retentionDays }` enables S3 Object Lock with a default retention on the bucket. The shared validator (`validateFileBucketOptions`, so the mock rejects the same shapes) rejects `versioned: false`, an unknown `mode`, and a `retentionDays` outside 1–36500. The CDK layer additionally rejects a resolved DESTROY removal policy — including the sandbox preset's default — because locked versions can't be emptied, so the auto-delete handler and the stack teardown would fail; the error tells the user to pass `removalPolicy: 'retain'`. Adding `objectLock` to a deployed bucket is an in-place CloudFormation update (verified against real CloudFormation, us-east-1); S3 can't turn Object Lock off afterwards, which is documented on the option. `putUrl()` / `createUploadHandle()` throw `PresignedUploadUnsupported` on an `objectLock` bucket, in both the mock and the AWS runtime (they read the same `objectLock` option the CDK layer does): verified against real S3 (us-west-2), an upload to a bucket with a default retention needs a `Content-MD5` or `x-amz-checksum-*` header, and an unsigned one is rejected (`AccessDenied: There were headers present in the request which were not signed`), so a URL presigned before the body is known always fails with `400 InvalidRequest`. Server-side `put()` works because the SDK sends a CRC32 checksum.
**Rationale:** A default retention (rather than enable-only) is what gives write-once protection without code changes at every write site; enable-only would protect nothing until something set per-object retention, which the API doesn't expose. Silently downgrading DESTROY to RETAIN was rejected: it would leave buckets behind on teardown without the user choosing it. Browser uploads to an Object Lock bucket would need a presigned POST whose policy admits a client-computed checksum field; that is a separate upload protocol, which FileBucket does not implement.

**D-FB-18: Over-long derived names are shortened (prefix + hash), not rejected**
**Decision:** The bucket name is `deriveBucketName(fullId)` (`bucket-name.ts`). A `fullId` of 63 characters or fewer is used byte-identical. A longer one becomes its first characters (trailing `-`/`.` trimmed), then `-`, then the first 8 hex characters of `sha256(fullId)` — at most 63 characters, the same pattern `bb-auth` uses for its hosted-UI domain prefix. The CDK, AWS-runtime, and mock layers each call `deriveBucketName` on the same `fullId`, so they resolve the same name without handing it between them (the mock registers its `mock-` twin). The result still goes through `validateBucketName`, so the other S3 rules (lowercase, allowed characters, begin/end) still fail synth.
**Rationale:** Long stack names plus nested block ids routinely exceed 63 characters — e.g. an `Agent`'s internal `sn` session bucket under a production stack name — and the developer often doesn't control those ids, so "shorten a scope id" is no fix. D-FB-8's two concerns still hold, and this design meets both: the name is a pure function of `fullId`, so it never shifts between deploys; and the hash covers the whole `fullId`, so two scope chains that share a long prefix stay distinct (a residual 32-bit collision would fail at deploy on S3's global uniqueness, never silently share a bucket). Identity is preserved: names that fit are untouched, and earlier versions of this package rejected over-long names at synth, so shortening renames no deployed bucket. `deriveBucketName`'s output is frozen once deployed and pinned in `bucket-name.test.ts`.

**D-FB-19: Presigned uploads always sign a Content-Type; opt-in type and size constraints shared by both runtimes**
**Decision:** `putUrl()` / `createUploadHandle()` always sign a `Content-Type` — the caller's `contentType`, or `application/octet-stream` when omitted. The S3 presigner leaves `content-type` out of the signed headers by default, so the AWS runtime passes `signableHeaders: ['content-type']` to `getSignedUrl`; `content-length` is signed by default whenever `ContentLength` is set, so `PutUrlOptions.contentLength` maps straight to it. Two bucket options restrict uploads: `allowedContentTypes` (exact media types or `type/*` wildcards, matched case-insensitively without parameters, against the effective content type after the default is applied) and `maxUploadBytes` (presigned uploads must pass `contentLength` and stay at or under it; `put()` checks the body size). `put()` applies the same default and checks, and the AWS runtime sends the resolved content type on `PutObject`, so S3 stores `application/octet-stream`, as the mock does, rather than S3's own `binary/octet-stream` default. All resolution and checks live in `upload-constraints.ts`, called by both runtimes in the same order (key → objectLock → constraints → expiry). The option shapes are validated by `validateFileBucketOptions` (CDK synth and mock), by the external-bucket branches of both (the checks are enforced in the runtime methods, so they also apply to a wrapped bucket), and by the AWS runtime constructor. The AWS runtime constructor validates only the upload-constraint options, while the mock runs the full `validateFileBucketOptions`: on AWS the remaining options are rejected at CDK synth, and only the upload constraints are read at request time. Each `contentType` passed to `put()` / `putUrl()` / `createUploadHandle()` must be one well-formed media type — `type/subtype` (RFC 9110 token characters) plus optional `; name=value` parameters whose value is a token or quoted string — with or without `allowedContentTypes`. A comma outside a quoted string, non-ASCII or control characters, or an empty value is rejected, because the signed and stored value must be exactly what was matched (a browser reading `image/png, text/html` uses the last type). A `type/*` wildcard matches when the parsed type equals `type`, except for the active document types (D-FB-23). The value signed, stored and returned in the upload descriptor is the canonical rendering of the caller's value: `type/subtype` as written, then each parameter as `; name=value` — one space after each `;`, none around `=` — with a quoted-string value unescaped and written bare when its content is a token, or re-quoted with only `"` and `\` escaped otherwise. HTTP clients that parse and re-render a `Content-Type` (Ktor, which the native Kotlin `FileUploadHandle` uses, renders `text/plain;charset=utf-8` as `text/plain; charset=utf-8` and `charset="utf-8"` as `charset=utf-8`) then send exactly the signed bytes, where signing the caller's spelling would make S3 answer 403.
**Rationale:** An unsigned Content-Type lets whoever holds an upload URL store an object under any type, which the browser later honors when the object is downloaded. Signing the type the API method chose — and letting the bucket declare which types and sizes it accepts — keeps that decision on the server. The constraints are request-time checks rather than S3 bucket policy because a bucket policy can't see the content type or size a URL was presigned for, and keeping them in shared code means the mock rejects exactly what AWS rejects. Wildcards cover the common "any image" case without listing every subtype.

**D-FB-20: Opt-in `Content-Disposition` on download URLs**
**Decision:** `getUrl()` / `getFileHandle()` accept `attachment?: boolean | string`. `true` signs `ResponseContentDisposition: 'attachment'` into the URL; a filename signs `attachment; filename="<ascii>"; filename*=UTF-8''<encoded>` (RFC 6266 / RFC 5987): control characters, the directional formatting characters (U+202A–U+202E, U+2066–U+2069, U+200E, U+200F, U+061C) and the zero-width characters (U+200B–U+200D, U+FEFF) are removed, a name that is empty or trims to `.` or `..` afterwards is rejected with `ValidationFailed`, `/` and `\` are replaced with `_` in both parameters, the quoted ASCII fallback replaces `"`, `\`, `%` and non-ASCII characters with `_`, and `filename*` carries the full UTF-8 name. The value is built by `content-disposition.ts`, shared by both runtimes. The mock signs it into the local download token and the dev file-server serves it. Without the option, S3 serves no Content-Disposition, and the dev file-server sends `attachment`.
**Rationale:** Presigned downloads come from the S3 origin, but an object displayed inline still renders as a page, so an uploaded HTML/SVG file runs script wherever it is displayed. Forcing `attachment` on every download would break legitimate inline use (images, PDFs), so it is opt-in and documented as the recommendation for user-uploaded content. Signing it (rather than setting object metadata at upload time) lets each download choose, and means the URL can't be edited to drop it.

**D-FB-21: Request-input rejections are HTTP 400 with static messages**
**Decision:** Every request-input rejection (`ValidationFailed` from key / prefix validation, presigned URL expiry, upload constraints, `attachment`, and the mock's containment guard) is built by `validationFailed()` in `validation-error.ts`: an `ApiError` with status 400, name `ValidationFailed`, and the message `ValidationFailed: <message>`. Messages are static and never include the key, prefix or other input. `restoreVersion()`'s `VersionNotFound` message is likewise the static `The requested version does not exist` in both runtimes. Bucket-name errors (`blocksError`) and bucket-option errors (plain `Error`) thrown at construction are not `ApiError`s: they surface at synth, not over the wire.
**Rationale:** A branded plain error crosses the RPC wire as a 500, which tells clients and monitoring that the server failed when the caller sent bad input. `ApiError` with a status is the existing way other blocks (`bb-data`, `bb-kv-store`, `bb-auth`) return a 4xx. Messages cross the wire, so they carry no caller data.

**D-FB-22: Shared key and prefix rules**
**Decision:** Besides the base rules (non-empty string, no leading slash, no empty segment, no ASCII control characters), `assertValidKey` rejects a backslash, C1 control characters (U+0080–U+009F), U+2028 / U+2029, bidirectional embedding/override/isolate characters (U+202A–U+202E, U+2066–U+2069), a segment that contains a `.` or `..` piece once `%2e`, `%2f` and `%5c` (either case) are decoded and the result is split on `/` and `\` (`a/%2e%2e/b`, `a/..%2f../b`, `a/%2e%2e%2fb`), and a key longer than 1,024 bytes in UTF-8. No other percent sequence is decoded, so `100%done.txt` and `50%25.txt` stay valid; decoding is a single pass, so a double-encoded `%252e` is not decoded again. `scan({ prefix })` runs `assertValidPrefix`, the same character and segment rules except that the prefix may be empty and may end with `/`. Both run identically in the mock and the AWS runtime.
**Rationale:** These characters have no use in an object key and either act as path syntax for some consumers (backslash, `%2e%2e` for code that URL-decodes keys) or change how a key reads in logs and UIs (line separators, bidi controls). Decoding only `%2e`, `%2f` and `%5c` keeps the rule narrow and unambiguous: it never misreads a literal `%` in a filename, and never rejects a key because its percent-encoding is malformed. Validating prefixes means no key-shaped input reaches S3 or the mock's filesystem walk unchecked.

**D-FB-23: `type/*` wildcards do not match active document types**
**Decision:** In `allowedContentTypes`, a `type/*` entry does not match `text/html`, `image/svg+xml`, `application/xhtml+xml`, `text/xml`, `application/xml`, `text/xsl`, `text/javascript`, `text/ecmascript`, `application/javascript`, `application/ecmascript` or `application/x-javascript` (`ACTIVE_CONTENT_TYPES` in `upload-constraints.ts`), nor any subtype with the `+xml` structured-syntax suffix (RFC 6839), such as `application/atom+xml`. Each of these is accepted only when listed exactly, in any case. Exact entries match as listed, and a wildcard matches every other subtype of its type. The check is in the shared `resolveUploadContentType`, so the mock and the AWS runtime agree.
**Rationale:** A browser displaying one of these types inline renders it as a page or runs it as a script. A developer writing `image/*` or `text/*` usually means raster images or plain text, and is unlikely to expect SVG or HTML to be included. Excluding them from wildcards keeps the common case safe for inline display, while listing a type exactly still accepts it. The `+xml` suffix rule covers XML vocabularies a browser parses as XML (and can apply an XSLT stylesheet to) without listing each one. The list is the set of widely rendered active types, not every type a browser can execute, so `attachment` remains the recommendation for serving user uploads (D-FB-20).

## Infrastructure (CDK)

Creates a single S3 bucket (plus a dedicated log bucket when `accessLogging` is enabled):

- **Bucket name:** Derived from `scope.fullId` (the bucket id joined to its parent scope ids with `-`); used as-is when it fits S3's 63 characters, else shortened to a truncated prefix plus an 8-character hash — see D-FB-18. Validated at synth against S3's naming rules — see D-FB-8.
- **Block public access:** All four settings enabled (BLOCK_ALL)
- **Encryption:** SSE-S3 by default; SSE-KMS with a dedicated rotating CMK (`'customer-managed'`) or an imported key (`FileBucket.fromKmsKey`), with S3 Bucket Keys on. See D-FB-16.
- **Object Lock:** Off by default; `options.objectLock` enables it with a default retention (requires versioning and a retained bucket). See D-FB-17.
- **TLS:** Enforced unconditionally (`enforceSSL: true`) — a bucket policy denies any request where `aws:SecureTransport` is `false`. Not configurable. See D-FB-9.
- **Versioning:** Enabled by default (secure default); opt out via `options.versioned: false`. See D-FB-10. When on, a lifecycle rule expires noncurrent versions after `options.noncurrentVersionExpirationDays` (default 90, validated as a positive integer at synth) to bound version-storage cost. See D-FB-14.
- **Server access logging:** Enabled per-block via `options.accessLogging`, falling back to `scope.defaults.storageAccessLogging`, then `scope.defaults.accessLogging`, when omitted; when on, provisions a separate, locked-down log bucket whose logs expire after the stack posture's `scope.defaults.logRetention` (`ONE_WEEK` sandbox / `ONE_YEAR` production; `INFINITE` = no expiry). See D-FB-11 and D-FB-13.
- **CORS:** Configured from `options.corsRules` if provided; otherwise the bucket has no CORS configuration, so browser `fetch()` of presigned URLs is blocked. Not derived from `scope.defaults.allowedOrigins` (API-only regex patterns) or the Hosting domain — see D-FB-15. A bare wildcard origin (`'*'`) combined with a mutating method (PUT/POST/DELETE) is rejected at synth. See D-FB-12.
- **Lifecycle rules:** Configured from `options.lifecycleRules` if provided (merged with the noncurrent-version expiration rule above)
- **Removal policy:** Resolved from `options.removalPolicy` (`'destroy'|'retain'`) when set, else the stack posture default `scope.defaults.removalPolicy` (DESTROY sandbox / RETAIN production). See D-FB-13.
- **Auto-delete objects:** Enabled when removal policy is DESTROY
- **Permissions:** `grantReadWrite` to the parent scope's handler automatically

## Mock Implementation

- Files stored on the local filesystem at `.bb-data/{scope.fullId}/` via `getMockDataDir()` from core.
- Internal data is segregated into sibling roots so it can never collide with user keys (see D-FB-2):
  - `content/{key}` — file body, byte-identical to what was written.
  - `meta/{key}.json` — sidecar metadata.
  - `versions/{key}/{versionId}` (+ `.json` sidecars, `__deleted__` marker) — version history.
- Path mapping for both the mock and the dev file-server is centralized in `paths.ts` so they stay in lockstep.
- Data persists across dev server restarts. Customers can wipe with `rm -rf .bb-data`.
- Presigned URLs are served by the dev file-server at `/.bb-file-bucket/{scope.fullId}/{path}?token=...`. The path segments are URL-encoded; the server decodes them and validates an HMAC token scoped to method, path, and expiry. The HMAC secret (`LOCAL_FILE_SECRET` in `tokens.ts`) is a **per-process random value** — the token-minting mock and the validating dev file-server share the same in-process module instance, so tokens are unforgeable without being a hardcoded, source-visible literal.
- Downloads are served with `X-Content-Type-Options: nosniff` and a `Content-Disposition`: the one signed into the token by `getUrl({ attachment })` (D-FB-20), or plain `attachment` otherwise. The stored body is caller-controlled, so serving it inline would let an uploaded `text/html`/SVG payload run in the local app origin. Forcing a download + disabling MIME sniffing is dev-server hardening only; deployed content is served via S3 presigned URLs, where the stored `Content-Type` is the one signed into the upload URL (D-FB-19) or passed to `put()`, no `nosniff` is applied, and a `Content-Disposition` is only sent when the URL was created with `attachment` — do not assume this dev-server behavior reflects the deployed path.
- A download with an explicit `versionId` resolves its body and metadata only from that version. A missing version returns HTTP 404, without falling back to the current object. Downloads without `versionId` resolve the current object.
- `scan()` recursively walks only the `content/` root, without hiding user keys based on bookkeeping-like filenames. It omits keys with an active delete-marker flag on versioned buckets.
- The dev file-server's PUT handler delegates to the registered `FileBucket` instance (via a process-global registry) so uploads get versioning, key validation, and metadata. There is no direct-write fallback; an unregistered bucket fails loud with a 500.
- Key length validated against S3's 1,024-byte limit: a longer key is rejected, as on AWS (D-FB-22).
- Object keys are validated identically on the mock and the AWS runtime via the shared, filesystem-independent `assertValidKey` (`validation.ts`), called from every key-accepting method on both layers. It rejects (`ValidationFailed`, HTTP 400) an empty/non-string key, a leading slash, an empty path segment (interior `a//b` or trailing `a/`, which the mock's `path.join` would otherwise collapse while S3 keeps literal), ASCII and C1 control characters, U+2028/U+2029, bidirectional formatting characters, a backslash, and a `..`/`.` path segment (including its `%2e` spelling) — see D-FB-22. `scan({ prefix })` runs the prefix variant, `assertValidPrefix`. The mock additionally applies a filesystem realpath/symlink containment guard (`assertContainedPath`) as local-only defense. `deleteBatch` validates every key up front on both layers, so a mixed valid/invalid batch deletes nothing.
- Basic versioning: each `put` writes to `versions/{key}/v{n}` and removes any active `__deleted__` sentinel; delete without `versionId` places that sentinel, `listVersions` reads stored data versions, and `restoreVersion` copies an old version via `put`. Historical delete markers are not retained.
- Deleting the newest stored data version updates the current `content/` and `meta/` copies from the next stored data version, including its original modification time, without creating a new version or removing an active delete-marker flag. Deleting the last stored data version removes the current copies. Deleting older or unknown versions leaves the current copies unchanged. The synchronous version reader is shared with `listVersions()`, so selection follows the same newest-first ordering and deletion does not yield between reading and reconciling the version history. This reconciles current copies with the data versions the mock retains; it does not reconstruct discarded delete-marker history.
- The shared version reader considers only regular files, excluding directories that belong to nested object keys. Current-copy updates or removal complete before the target version is unlinked; missing copies and sidecars are tolerated, but other filesystem errors propagate so callers can retry the same deletion. The version body is removed last, after its metadata sidecar.

### Mock vs AWS Behavior Differences

| Behavior Difference | Impact | Mitigation |
|------------|--------|------------|
| Historical delete markers are not retained | The mock has one `__deleted__` flag, removed by the next `put()`, rather than delete markers ordered among data versions. For `put(old)` → `delete()` → `put(replacement)` → permanent deletion of the replacement version, the mock exposes `old`, includes the key in `scan()`, and marks the older data version current in `listVersions()`. S3 instead makes the earlier delete marker current, so a read without a version ID treats the key as deleted. | Do not use the local mock to assert S3 deletion-history behavior across re-uploads; exercise that case in a sandbox. Correct historical promotion needs a model that retains ordered delete markers and defines compatibility with existing local data. Current-copy reconciliation alone does not address it. |
| Non-atomic version deletion | Current body, metadata, and version history are separate filesystem writes. An I/O failure or process interruption can leave partially updated current copies until deletion is retried; this is not an atomic S3 operation or a rollback guarantee. | The target version body remains until current-copy reconciliation and version-sidecar removal succeed. After resolving the I/O error, retry deletion with the same version ID to finish reconciliation. |
| No lifecycle rules | Objects never expire or transition locally | No mitigation — lifecycle rules are a background S3 process |
| No CORS enforcement | Browser requests succeed regardless of origin locally; a missing `corsRules` only fails after deploy | CORS is enforced by the browser + S3, not the mock. The README's "Browser Uploads and Downloads (CORS)" section documents that `corsRules` is required for deployed browser access |
| No storage classes | Transition rules have no effect locally | No mitigation — storage classes are a cost optimization |
| No multipart upload | Large files use simple write locally | No mitigation — mock uses `fs.writeFile` regardless of size |
| Presigned URLs are localhost-only | URLs only work against the local dev server | No mitigation — expected behavior for local development |
| No encryption or Object Lock retention | `encryption` has no effect locally (files are stored unencrypted on disk), and locked versions can still be deleted with `delete(path, { versionId })` | The options are validated identically and presigned uploads are rejected on an `objectLock` bucket in both runtimes (D-FB-17), so a shape that fails `cdk synth` or a deployed upload also fails locally. Retention is enforced by S3 only |
| No IAM enforcement | Permission errors only surface in AWS | No mitigation — IAM is handled by CDK grants automatically |
| Filesystem path limits | Some OS path length limits differ from S3 key limits (1,024 bytes) | Both runtimes reject a key over 1,024 bytes in UTF-8 (D-FB-22). A shorter key can still exceed a local filesystem's per-component or total path limit and fail only in the mock |
| Windows-specific key rules | On Windows, the mock maps keys onto NTFS paths, where `:`, reserved device names (`CON`, `NUL`, `COM1`, …), trailing dots or spaces in a segment, and drive-style keys (`C:/x`) are invalid or change meaning. S3 accepts all of these as literal keys, and the shared validator does not reject them. | Known gap, tracked for a follow-up. Avoid these key shapes, or test them against a sandbox. |
| Content-Type comparison on presigned PUT | The dev file-server compares the request's `Content-Type` to the signed value as raw strings, while S3 canonicalizes signed header values (trims them and collapses runs of spaces) before comparing. A header that differs from the signed value only in whitespace runs is rejected locally but accepted by S3. | Signed values are canonical (D-FB-19), and the upload handles and native clients send them unchanged, so the difference only affects hand-built requests. |
| 403 response body on a signature mismatch | The dev file-server answers a rejected presigned request with a plain-text body; S3 answers with an XML `SignatureDoesNotMatch` error document. | Branch on the HTTP status, not the response body. |
| Non-atomic `put()` | On a versioned bucket, `put()` performs several separate `writeFileSync` calls (version body, version metadata, current body, current metadata, delete-marker cleanup). A crash or process kill mid-`put()` can leave torn state — a body with no metadata sidecar, or a version body with no `.json`. Real S3 `PutObject` is atomic per object. | No mitigation — the filesystem layout has no transaction boundary. Acceptable for a dev mock (re-running `put()` heals it). See Open Question 4 (storage engine). |
| Metadata key case | S3 lowercases user metadata keys, while the mock keeps them as written, so code that reads `metadata.Owner` works locally and gets `undefined` on AWS. | Use lowercase metadata keys. |
| Monotonic version IDs | Mock uses `v1`, `v2`, ... vs S3's opaque IDs | No impact — customer code should treat version IDs as opaque strings |
| Unknown `versionId` raw error names differ | The mock signals an unresolvable `versionId` directly (missing sidecar → `null` on `get`, no-op on `delete`, `NoSuchVersion` on `restoreVersion`), while S3 raises different **raw** codes depending on the operation and id shape: `InvalidArgument` ("Invalid version id specified") on `GetObject`/`DeleteObject`, `InvalidRequest` on `CopyObject`, and `NoSuchVersion` only for a well-formed id that no longer exists (verified against real S3, us-west-2). | Normalized in the AWS runtime so the **observable** contract matches the mock: `get()` returns `null`, `delete()` is a no-op, and `restoreVersion()` throws a clean `FileBucketErrors.VersionNotFound` (`NoSuchVersion`) with no `$metadata`. The raw S3 codes are folded only when a `versionId` was supplied, so an unrelated `InvalidArgument` still surfaces. Covered by `src/parity.test.ts` (both runtimes) and the cross-runtime suite. |
| Content-Type and Content-Length signed into presigned PUT URLs | `putUrl`/`createUploadHandle` always sign `content-type` (the caller's `contentType`, or `application/octet-stream`) and, when `contentLength` is given, `content-length` (D-FB-19), so real S3 returns `403 SignatureDoesNotMatch` if the uploaded request's `Content-Type` or `Content-Length` differs from (or omits) the signed value. The dev file-server enforces the same checks against the values signed into its token (`src/file-server.ts`), so an upload that would fail in prod also fails locally with 403, rather than silently succeeding. Uploads via `createUploadHandle().upload()` always send the signed `Content-Type` (on the server and after client hydration), so the typed-handle path round-trips in both environments. Covered by `src/file-server.test.ts` and `src/parity.test.ts`. |
| Default download disposition | Without `attachment`, S3 serves a download with no `Content-Disposition`, so the browser may display it inline; the dev file-server always sends `Content-Disposition: attachment` (and `nosniff`). With `attachment`, both send the same signed value. | Pass `attachment` for user-uploaded content (D-FB-20); test inline rendering against a sandbox. |

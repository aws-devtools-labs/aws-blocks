# @aws-blocks/bb-database

`Database` is a PostgreSQL schema on an Aurora DSQL cluster that the block owns or shares with other blocks. Query it with the `sql` tag; write migration files in DSQL, as AWS documents it, and the block runs them as written. The query code is the same whichever cluster a block runs on.

```sh
npm install @aws-blocks/bb-database
```

**When to use:** relational data, joins, foreign keys, views, and multi-statement transactions, on a cluster that creates in seconds, costs nothing when idle, and needs no VPC.

**When not to use:** key/value lookups (use `KVStore`) or records with secondary indexes (use `DistributedTable`); both have no cluster to manage. Triggers, PL/pgSQL, extensions, Row Level Security on raw SQL, or transactions over 3,000 rows need all of PostgreSQL: a `provisioned` cluster (Aurora Serverless v2) is planned for this block and not yet available.

This is a preview. `@aws-blocks/bb-data` and `@aws-blocks/bb-distributed-data` are unchanged, and the umbrella package `@aws-blocks/blocks` still exports `bb-data`'s `Database`; import this block from `@aws-blocks/bb-database`. Internals and local-versus-AWS differences are in [DESIGN.md](./DESIGN.md).

## Quick start

Define the blocks in `aws-blocks/index.ts`:

```ts
import { Database, DatabaseCluster, sql } from '@aws-blocks/bb-database';

// 1. Default. The block owns an Aurora DSQL cluster.
const shop = new Database(scope, 'shop');

// 2. Several blocks on one cluster. Each gets its own schema.
const shared = new DatabaseCluster(scope, 'shared', { type: 'dsql' });
const audit = new Database(scope, 'audit', { cluster: shared });
const search = new Database(scope, 'search', { cluster: shared });
```

Create tables in a migration file, not in a handler. On a `dsql` cluster the app's database role can only read and write rows, so `CREATE TABLE` at runtime fails, locally and on AWS. Put it in `aws-blocks/migrations/shop/001_init.sql`, written in DSQL (see [Migrations](#migrations)):

```sql
CREATE TABLE customers (id TEXT PRIMARY KEY, email TEXT UNIQUE NOT NULL);
CREATE TABLE orders (id BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 65536) PRIMARY KEY, customer_id TEXT NOT NULL REFERENCES customers(id), total INTEGER NOT NULL);
```

Then query from an `ApiNamespace` method:

```ts
export const api = new ApiNamespace(scope, 'api', (context) => ({
  async signUp(email: string) {
    const id = crypto.randomUUID();
    await shop.execute(sql`INSERT INTO customers (id, email) VALUES (${id}, ${email})`);
    return { id };
  },

  async placeOrder(customerId: string, total: number) {
    return shop.transaction(async (tx) => {
      const customer = await tx.queryOne<{ id: string }>(sql`SELECT id FROM customers WHERE id = ${customerId}`);
      if (!customer) throw new Error('no such customer');
      await tx.execute(sql`INSERT INTO orders (customer_id, total) VALUES (${customerId}, ${total})`);
      return tx.queryOne<{ n: number }>(sql`SELECT count(*)::int AS n FROM orders WHERE customer_id = ${customerId}`);
    });
  },
}));
```

`npm run dev` runs this with no AWS account; `npm run deploy` creates the cluster and applies the migration before the new code goes live.

## API

```ts
const db = new Database(scope, id, options?);
const cluster = new DatabaseCluster(scope, id, { type: 'dsql', removalPolicy? });
```

| Method | Returns | Description |
|---|---|---|
| `query(sql, options?)` | `Promise<T[]>` | Run a query and return every row. Empty array when nothing matches. `options.schema` types and validates the rows, see [Typed results](#typed-results). |
| `queryOne(sql, options?)` | `Promise<T \| null>` | Run a query and return the first row, or `null` when nothing matches. Same `options.schema`. |
| `execute(sql)` | `Promise<{ rowCount: number }>` | Run an `INSERT`, `UPDATE`, or `DELETE` and return the rows affected. |
| `transaction(fn, options?)` | `Promise<T>` | Run `fn(tx)` in one transaction; `tx` has the three methods above. Commits when `fn` resolves, rolls back when it throws. See [Transactions](#transactions). |
| `db.cluster` | `{ kind, id }` | Which cluster the block runs on: `id` is `'default'` when owned, otherwise the `DatabaseCluster`'s full id. |
| `db.schemaName` | `string` | The schema this block's tables live in. |

`sql` is a tagged template: every `${value}` becomes a bound parameter, never string interpolation. Table and column names cannot be parameters.
`bigint` values (identity columns, `count(*)`, `sum()` over integers) come back as JavaScript numbers, locally and on DSQL. A value beyond ±2^53 comes back as a `BigInt`, which JSON cannot serialize, so returning one from an `ApiNamespace` method fails at the RPC serializer; cast such a column in the query (`::text`, or `::float8` when precision loss is acceptable).

### Typed results

A query's row type can come from a value instead of a type argument. Pass `{ schema }`, any [Standard Schema](https://standardschema.dev) (Zod, Valibot, ArkType, or your own), and the method returns the schema's output type after validating every row against it. A row that does not match throws `DatabaseErrors.ResultValidationFailed`, naming the row and the failing field, instead of reaching your handler as the wrong shape. The same option is on the `tx` inside `transaction()`. The first issue's path and message are part of the error message, which reaches the client; the schema libraries' built-in messages describe only the expected shape, so keep any custom refinement message free of row values.

```ts
import { z } from 'zod';

const Customer = z.object({ id: z.string(), email: z.string() });

const customers = await shop.query(sql`SELECT id, email FROM customers`, { schema: Customer });
// customers: { id: string; email: string }[]

const one = await shop.queryOne(sql`SELECT id, email FROM customers WHERE id = ${id}`, { schema: Customer });
// one: { id: string; email: string } | null
```

`query<T>(sql)` with a type argument still works; the argument is an unchecked assertion, so prefer `schema` where the shape matters.

**Runtime only.** Call the data methods inside an `ApiNamespace` method, `RawRoute` handler, job handler, or a runtime script, not at the top level of `aws-blocks/index.ts`. Top-level code also runs during CDK synth, where the block is its infrastructure construct and every data method throws `Database.query() cannot be called during CDK synth`. Constructing the block at module scope is fine; only the calls must move into handlers. Every `ApiNamespace` method is a public endpoint, so gate it with `await auth.requireAuth(context)` from an auth block.

## Options

An option goes on the cluster if every block on that cluster must share it, and on the block otherwise.

Cluster options:

| Option | Type | Description |
|---|---|---|
| `type` | `'dsql'` | Required. Aurora DSQL. The value is required so that the planned `provisioned` kind adds a value without changing this line. |
| `removalPolicy` | `'retain' \| 'destroy'` | What happens to the cluster when the stack is destroyed. When omitted, the stack-wide `defaults` apply: `production` retains with deletion protection on, `sandbox` destroys. Most apps never set this. A renamed `Database` or `DatabaseCluster` id keeps the old cluster and its data under `retain`, but points the app at a new, empty one. |

Block options:

| Option | Type | Description |
|---|---|---|
| `cluster` | `DatabaseCluster` | The cluster to run on. Omit it and the block owns a `dsql` cluster. |
| `migrationsPath` | `string` | Directory of `.sql` files, relative to the project root. Defaults to `./aws-blocks/migrations/{id}`; the default may be missing, an explicit path must exist. |
| `schemaName` | `string` | The PostgreSQL schema for this block's tables. `public` when the block owns its cluster, otherwise the block id. Two blocks on one cluster cannot share a schema. |
| `removalPolicy` | `'retain' \| 'destroy'` | Only when `cluster` is omitted. With a shared cluster, set it on the `DatabaseCluster`. |
| `logger` | `ChildLogger` | Logger for internal operations. Defaults to a `Logger` at error level. |

`Database` and `DatabaseCluster` ids are unique per app; a second block with the same id is an error at construction.

## Sharing a cluster

```ts
const shared = new DatabaseCluster(scope, 'shared', { type: 'dsql' });
const audit = new Database(scope, 'audit', { cluster: shared });
const search = new Database(scope, 'search', { cluster: shared });
```

The `DatabaseCluster` is the only thing that provisions: one DSQL cluster, one pair of migration Lambdas, and one database role for the app, `blocks_app_{clusterId}`. Each `Database` on it adds a schema named after its id, a custom resource that applies that block's migrations into the schema, and grants on the schema's tables. At request time each block opens its own connection pool to the same cluster as the same role, with `search_path` set to its schema, so ``audit.query(sql`SELECT * FROM events`)`` reads `audit.events` and the same text on `search` reads `search.events`. Locally the cluster is one PGlite and the blocks are two schemas in it, the same layout as on AWS.

**Isolation is by namespace, not by permission.** Both blocks connect as one role that has DML on every schema on the cluster. A query that qualifies a table name, ``sql`SELECT * FROM search.events` `` from `audit`, works, and so does a join across the two schemas in one statement. Treat the schema as a naming convention that keeps two blocks' tables apart, not as a boundary between tenants or trust levels; a block that must not see another block's data belongs on its own cluster.

**Why share on DSQL.** A DSQL cluster costs nothing when idle, so sharing saves no money, unlike Aurora where a cluster has a capacity minimum. Share when you want one migration pipeline instead of one per block, when you need to query across the blocks' tables, or to stay under the default quota of 20 clusters per account and Region, which per-developer sandboxes count against. Keep separate clusters when the blocks have different lifecycles: the removal policy is set on the cluster, blocks on one cluster migrate one at a time, and moving a block to another cluster later means copying its data.

## Migrations

Your `Database` runs on Aurora DSQL, so write its migrations in DSQL, as AWS documents it: [DDL and distributed transactions](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-ddl.html), [`CREATE TABLE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/create-table-syntax-support.html), [`ALTER TABLE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/alter-table-syntax-support.html), [`CREATE SEQUENCE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/create-sequence-syntax-support.html) and [Asynchronous indexes](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-create-index-async.html). The block never changes the SQL you wrote; what is in the file is what runs on the cluster. It checks every statement with [`dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint) on your machine and at synth, runs one DDL statement per transaction, waits for the job that each `ASYNC` statement starts, and resumes a failed file at the failed step.

Each block has one directory of `.sql` files, `./aws-blocks/migrations/{id}` unless `migrationsPath` says otherwise. Block ids are unique per app because they name this directory and, on a shared cluster, the block's schema. Files run in name order, once each:

```
aws-blocks/migrations/
  shop/
    001_init.sql
    002_orders_customer_index.sql
  audit/
    001_events.sql
```

### Coming from PostgreSQL

Most DDL is the same on DSQL. These spellings differ; a file that uses the PostgreSQL form stops with the DSQL one in the error (see [What is rejected](#what-is-rejected)).

| PostgreSQL | DSQL |
|---|---|
| `id SERIAL PRIMARY KEY` (also `BIGSERIAL`, or `INTEGER … AS IDENTITY`) | `id BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 65536) PRIMARY KEY`. Identity columns and sequences are `bigint` and need an explicit cache of `1` or at least `65536`. With `CACHE 65536` each session takes a block of values locally, so an insert needs no coordination round across the cluster; values are unique but can have gaps and arrive out of order. `CACHE 1` keeps values close to sequential at the cost of that round trip per value; use it when order matters more than insert rate. |
| `CREATE SEQUENCE s` | `CREATE SEQUENCE s CACHE 65536`, same choice of cache |
| `CREATE INDEX i ON t (c)` | `CREATE INDEX ASYNC i ON t (c)`, as its own statement. DSQL returns a job id and builds the index in the background; the block waits for the job before the next statement. |
| `ALTER TABLE t ADD CONSTRAINT c FOREIGN KEY (…) REFERENCES …` or `… CHECK (…)` | The same statement ending in `NOT VALID`, then `ALTER TABLE ASYNC t VALIDATE CONSTRAINT c`. The constraint applies to new rows at once; validating the existing rows is a job the block waits for. A `REFERENCES` or `CHECK` inside `CREATE TABLE` is written as in PostgreSQL. |
| `ALTER TABLE t ADD CONSTRAINT u UNIQUE (c)` | `UNIQUE` inline in `CREATE TABLE`, or `CREATE UNIQUE INDEX ASYNC u ON t (c)` |
| `ALTER TABLE t ADD COLUMN c TEXT DEFAULT 'x'` (or `… NOT NULL`) | `ALTER TABLE t ADD COLUMN c TEXT`, then `ALTER TABLE t ALTER COLUMN c SET DEFAULT 'x'`, then backfill the existing rows with `UPDATE … WHERE c IS NULL` in batches of at most 3,000 rows, the per-transaction limit |
| `ALTER TABLE t ALTER COLUMN c SET NOT NULL` or `… TYPE bigint` | Not available on DSQL. Add a new column, copy the values over in batches, switch your queries, then drop the old column. |

You do not need to write `sys.wait_for_job(…)` after an `ASYNC` statement; the block waits for the job. A wait copied from the AWS examples runs anyway, and locally it returns at once (see [Local mode](#local-mode)).

On DSQL the rows an `ON DELETE CASCADE` foreign key deletes count toward the 3,000-row transaction limit, and a delete that fans out past it fails whole; prefer `NO ACTION` or `RESTRICT` for unbounded parent-child relationships.

### What is rejected

Every file is checked with [`dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint), the linter the Aurora DSQL team maintains, at `npm run dev` and at `cdk synth`, before any deploy. The check covers what DSQL cannot run (`CREATE TRIGGER`, `CREATE EXTENSION`, `CREATE POLICY`, `TRUNCATE`, array columns, `ADD COLUMN … DEFAULT`, `SET NOT NULL` or `TYPE` on an existing column, `ADD CONSTRAINT … UNIQUE (…)`, and so on) and the PostgreSQL spellings in the table above (`serial_type`, `index_async`, `foreign_key_not_valid`, `check_not_valid`, `sequence_cache_missing`). Nothing is rewritten for you: the error names the file, the rule, dsql-lint's suggestion, and the DSQL documentation page, and the fix is yours to make in the file:

```
Migration validation failed for Aurora DSQL (cluster kind 'dsql'):
  001_init.sql: serial_type: Column `id` uses SERIAL, which is not supported in DSQL. Use `BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 1)` instead. Checked against https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility.html
  002_index.sql: index_async: CREATE INDEX without ASYNC is not supported in DSQL. Index: orders_customer Use `CREATE INDEX ASYNC ...` instead. Checked against https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility.html
```

One check is the block's own: `GRANT … ON SCHEMA public`, which dsql-lint accepts but DSQL rejects at runtime because `public` is a system schema that roles can use without a grant.

`dsql-lint` is a native binary that `@aws/dsql-lint` installs per platform as an optional dependency (macOS, Linux, and Windows on x64; macOS and Linux on arm64). It runs on your machine and at synth, never on AWS. If your package manager skipped optional dependencies, run `npm install @aws/dsql-lint --include=optional`, or point `DSQL_LINT_PATH` at a build.

### How migrations deploy

Locally, a block applies its pending files before its first query. On AWS, each block has one CloudFormation custom resource that applies its files at deploy; blocks on one cluster migrate one at a time, and every app function waits for the migrations of the blocks it uses, so new code never runs against the old schema. An index build or constraint validation is a DSQL job; the resource polls it every 30 seconds for up to two hours. Applied files are recorded in a `_migrations` table in the block's schema. If a file fails partway, the error names the failed step and the file is not recorded; fix the cause and deploy again, and the runner resumes at that step.

## Transactions

DSQL uses optimistic concurrency: a transaction never waits on a lock, and two transactions that change the same row both run to the end, after which one commit fails with `SerializationFailure` (SQLSTATE `40001`, HTTP 409, flagged retriable). `SELECT … FOR UPDATE` is supported and makes a read conflict with concurrent writes, which is how a read-modify-write stays correct.

- A single `query` or `execute` outside a transaction is retried for you, three times at 50, 100 and 200 ms.
- A `transaction()` callback is re-run only when you pass `{ retryOnConflict: true }`, because a callback may have side effects. `maxRetries` defaults to 3.
- A transaction may change at most 3,000 rows (cascaded deletes included) and 10 MiB of data; past either it fails with `TransactionRowLimitExceeded` and nothing is kept. Split bulk work into batches.
- DDL and DML never share a transaction, and only migrations run DDL.
- A throw inside the callback rolls the transaction back. An `ApiError` (a 404 you throw, or the 401 from `requireAuth`) and any branded Blocks error reach the caller unchanged; any other error becomes `TransactionFailed` and its text stays on the server.

```ts
import { ApiError } from '@aws-blocks/core';

// Safe to re-run: the callback reads, decides, writes, and has no side effects outside the database.
await shop.transaction(async (tx) => {
  const row = await tx.queryOne<{ total: number }>(sql`SELECT total FROM orders WHERE id = ${orderId} FOR UPDATE`);
  if (!row) throw new ApiError('no such order', 404); // the client receives a 404
  await tx.execute(sql`UPDATE orders SET total = ${row.total + delta} WHERE id = ${orderId}`);
}, { retryOnConflict: true });
```

For tests, `simulateConflict(shop)` from `@aws-blocks/bb-database/testing` makes the next commit fail with `SerializationFailure` in local mode, so a test can cover the retry without a deployed cluster. It throws in the Lambda runtime, where a conflict comes from the cluster itself.

## Errors

Query and transaction failures carry a `DatabaseErrors` name. Match them with `isBlocksError(e, DatabaseErrors.X)` on the server or the client; only the name and a fixed message cross the wire, the driver error stays on the server. Setup mistakes (a duplicate id, a missing `migrationsPath`), `dsql-lint` findings (`DsqlValidationError`) and migration failures (`MigrationFailedException`) have their own names; fix those rather than catch them.

| Error | When | Retried automatically |
|---|---|---|
| `QueryFailed` | Any other SQL error, including a foreign-key or check violation | No |
| `ConnectionFailed` | Endpoint or network failure | No |
| `TransactionFailed` | The callback threw an error that is not an `ApiError`, a Blocks error or a database error, or the commit failed for a reason other than a conflict | No |
| `UniqueConstraintViolation` | SQLSTATE `23505` (HTTP 409) | No |
| `SerializationFailure` | SQLSTATE `40001` at commit (HTTP 409, retriable) | A single `query` or `execute`: three times. A `transaction()` callback: only with `retryOnConflict: true` |
| `TransactionRowLimitExceeded` | More than 3,000 rows changed (cascades included) or more than 10 MiB written in one transaction, locally and on DSQL (SQLSTATE `54000`) | No; split the work |
| `ResultValidationFailed` | A row did not match the `schema` passed to `query()` or `queryOne()`; the message, which reaches the client, names the row and the first issue's path and text | No; fix the schema or the query |

DSQL's stale-schema-cache error (`OC001`) is retried once wherever it happens.

```ts
import { isBlocksError } from '@aws-blocks/core';
import { DatabaseErrors, sql } from '@aws-blocks/bb-database';

try {
  await shop.execute(sql`INSERT INTO customers (id, email) VALUES (${id}, ${email})`);
} catch (err) {
  if (isBlocksError(err, DatabaseErrors.UniqueConstraintViolation)) return { conflict: 'email already registered' };
  throw err;
}
```

## Local mode

`npm run dev` needs no AWS account. Each cluster is one PGlite (PostgreSQL compiled to WebAssembly) under `.bb-data/`, with one schema per block, as on AWS.

A `dsql` cluster adds DSQL's checks locally. Every statement a handler issues goes through `dsql-lint` first (once per distinct statement), so unsupported SQL fails on your machine instead of in production; DDL outside a migration is refused because the deployed app role can only run DML; and a transaction that changes more than 3,000 rows (cascades included) or 10 MiB fails and rolls back, as it does on DSQL.

PGlite runs your DSQL migration files with two keyword strips: `CREATE INDEX ASYNC` runs as `CREATE INDEX` and `ALTER TABLE ASYNC … VALIDATE CONSTRAINT` as `ALTER TABLE … VALIDATE CONSTRAINT`, both synchronously, so the block's job wait has nothing to wait for. A stub of DSQL's `sys` schema stands in for the real one: `sys.wait_for_job(job_id)` returns `true` at once and `sys.jobs` is empty, so a wait copied from the AWS examples, `SELECT sys.wait_for_job('…')` or `SELECT sys.wait_for_job(job_id) FROM sys.jobs WHERE …`, runs locally unchanged.

| | Owned default | `DatabaseCluster` |
|---|---|---|
| Engine | PGlite with `dsql-lint` and the DSQL limits | One PGlite per cluster, one schema per block, same checks |
| Data | `.bb-data/{fullId}/` | `.bb-data/{clusterFullId}/` |
| Migrations | Before the block's first query | Same, per block, into its schema |

PGlite has one session, so local work on a cluster runs one statement or transaction at a time. Bugs that need two requests to overlap do not reproduce locally; `simulateConflict()` from `@aws-blocks/bb-database/testing` covers the retry path.

## What it provisions (AWS)

Per cluster, whether a block owns it or a `DatabaseCluster` declares it:

- **One Aurora DSQL cluster** (`AWS::DSQL::Cluster`). No VPC, no secret, no security group, no proxy; IAM token authentication over the public endpoint. Deletion protection follows the stack `defaults`.
- **Two migration Lambdas** built from one bundle (`onEvent` and `isComplete`), one log group, and a custom-resource provider that polls DSQL jobs every 30 seconds for up to two hours.
- **IAM:** the app's execution role gets `dsql:DbConnect` on the cluster; the migration Lambdas get `dsql:DbConnectAdmin`.
- **Config:** `BLOCKS_{CLUSTER_ID}_ENDPOINT` and `BLOCKS_{CLUSTER_ID}_REGION` (the cluster's full id upper-cased), injected through the config bucket.

Per block: one S3 asset with its migration files and one CloudFormation custom resource that applies them. The migration Lambda also creates a per-cluster database role for the app, maps it to the execution role with `AWS IAM GRANT`, and grants it `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the block's tables, `SELECT` on its views, and `USAGE` on its sequences. DDL needs the admin token, which only the migration Lambdas hold.

**Cost.** A DSQL cluster has no charge when idle; usage is billed per million request units and per GB-month, with a monthly free tier ([pricing](https://aws.amazon.com/rds/aurora/dsql/pricing/)). The migration Lambdas run only during deploys. A `Database` that owns its cluster is one cluster against the [default quota](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html) of 20 per account and Region; blocks on a shared `DatabaseCluster` count once.

## Access through the AWS SDK

`getSdkIdentifiers(db)` from `@aws-blocks/core` returns the block's `clusterId` and `schemaName`. In a deployed Lambda it also returns the cluster's `clusterEndpoint` and `region`, which is what a `DsqlSigner` needs to open your own `pg` connection as the same role. The umbrella's typed overloads do not know this block yet, so the result is a `Record<string, string>`.

# @aws-blocks/bb-database

`Database` is a PostgreSQL schema on an Aurora DSQL cluster. The block owns the cluster or shares it with other blocks. Query it with the `sql` tag. Write migration files in DSQL, as the AWS documentation shows them; the block runs them unchanged on the cluster. The query code is the same on every cluster.

```sh
npm install @aws-blocks/bb-database
```

**When to use:** relational data, joins, foreign keys, views, and multi-statement transactions, on a cluster with no VPC to manage.

**When not to use:** data that one key or one table pattern can serve. `KVStore` and `DistributedTable` have no cluster to manage. Triggers, PL/pgSQL, extensions, Row Level Security on raw SQL, and transactions over 3,000 rows need full PostgreSQL. A `provisioned` cluster (Aurora Serverless v2) is planned for this block and not yet available.

This is a preview. `@aws-blocks/bb-data` and `@aws-blocks/bb-distributed-data` are unchanged. The umbrella package `@aws-blocks/blocks` still exports `bb-data`'s `Database`. Import this block from `@aws-blocks/bb-database`. Internals and local-versus-AWS differences are in [DESIGN.md](./DESIGN.md).

## Quick start

Define the blocks in `aws-blocks/index.ts`:

```ts
import { ApiNamespace, Scope } from '@aws-blocks/core';
import { AuthBasic } from '@aws-blocks/bb-auth-basic';
import { Database, DatabaseCluster, sql } from '@aws-blocks/bb-database';

const scope = new Scope('app');
const auth = new AuthBasic(scope, 'auth');
export const authApi = auth.createApi(); // clients sign in with authApi.setAuthState({ action: 'signUp', username, password })

// 1. Default. The block owns an Aurora DSQL cluster.
const shop = new Database(scope, 'shop');

// 2. Several blocks on one cluster. Each gets its own schema.
const shared = new DatabaseCluster(scope, 'shared', { type: 'dsql' });
const audit = new Database(scope, 'audit', { cluster: shared });
const search = new Database(scope, 'search', { cluster: shared });
```

> **⚠️ Data lives on the cluster. AWS Blocks does not move it.** Treat the cluster a `Database` first deploys to as permanent. If you change its `cluster` option, or rename a `Database` or `DatabaseCluster` id, the block points at a different, empty cluster or schema. Nothing copies the rows. The old data stays where it was. A schema on a shared cluster is never dropped. An owned cluster that leaves the template is kept under `removalPolicy: 'retain'` (the production default). Under `'destroy'` (the sandbox default) it is **deleted in that same deploy**. To move data: 1. Add a new block on the target cluster. 2. Copy the rows. 3. Switch your handlers. 4. Remove the old block. See [Sharing a cluster](#sharing-a-cluster).

Create tables in a migration file, not in a handler. The deployed app can only read and write rows. Put the file at `aws-blocks/migrations/shop/001_init.sql`, written in DSQL (see [Migrations](#migrations)):

```sql
CREATE TABLE customers (id TEXT PRIMARY KEY, email TEXT UNIQUE NOT NULL);
CREATE TABLE orders (id BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 65536) PRIMARY KEY, customer_id TEXT NOT NULL REFERENCES customers(id), total INTEGER NOT NULL);
```

Then query from an `ApiNamespace` method, gated with the auth block. `requireAuth` returns the signed-in user:

```ts
import { ApiError } from '@aws-blocks/core';

export const api = new ApiNamespace(scope, 'api', (context) => ({
  async saveProfile(email: string) {
    const { userId } = await auth.requireAuth(context);
    await shop.execute(sql`INSERT INTO customers (id, email) VALUES (${userId}, ${email})`);
  },

  async placeOrder(total: number) {
    const { userId } = await auth.requireAuth(context);
    await shop.transaction(async (tx) => {
      const customer = await tx.queryOne<{ id: string }>(sql`SELECT id FROM customers WHERE id = ${userId}`);
      if (!customer) throw new ApiError('save your profile first', 404);
      await tx.execute(sql`INSERT INTO orders (customer_id, total) VALUES (${userId}, ${total})`);
    });
  },
}));
```

The 404 thrown inside the transaction reaches the client as an `ApiError` with `status` 404.

`npm run dev` runs this with no AWS account. `npm run deploy` creates the cluster and applies the migration before the new code goes live.

## API

```ts
const db = new Database(scope, id, options?);
const cluster = new DatabaseCluster(scope, id, { type: 'dsql', removalPolicy? });
```

| Method | Returns | Description |
|---|---|---|
| `query(sql, options?)` | `Promise<T[]>` | Run a query and return every row. Empty array when nothing matches. `options.schema` types and validates the rows, see [Typed results](#typed-results). |
| `queryOne(sql, options?)` | `Promise<T \| null>` | Run a query and return the first row, or `null` when nothing matches. Same `options.schema`. |
| `execute(sql)` | `Promise<{ rowCount: number }>` | Run an `INSERT`, `UPDATE`, or `DELETE` and return the rows affected. |
| `transaction(fn, options?)` | `Promise<T>` | Run `fn(tx)` in one transaction; `tx` has the three methods above. Commits when `fn` resolves, rolls back when it throws. See [Transactions](#transactions). |
| `db.cluster` | `{ kind, id }` | Which cluster the block runs on: `id` is `'default'` when owned, otherwise the `DatabaseCluster`'s full id. |
| `db.schemaName` | `string` | The schema this block's tables live in. |

`sql` is a tagged template. Every `${value}` becomes a bound parameter, never string interpolation. Table and column names cannot be parameters.

`bigint` values (identity columns, `count(*)`, `sum()` over integers) come back as JavaScript numbers, locally and on DSQL. A value outside the safe-integer range comes back as a `BigInt`. JSON cannot serialize a `BigInt`, so an `ApiNamespace` method that returns one fails at the RPC serializer. Cast the column in the query: `::text`, or `::float8` if you accept the precision loss.

### Typed results

A query's row type can come from a value instead of a type argument. Pass `{ schema }` with any [Standard Schema](https://standardschema.dev) (Zod, Valibot, ArkType, or your own). The method validates every row and returns the schema's output type. A row that does not match throws `DatabaseErrors.ResultValidationFailed`. The client sees the row index and the column name, never the values. The same option is on the `tx` inside `transaction()`.

```ts
import { z } from 'zod';

const Customer = z.object({ id: z.string(), email: z.string() });

const customers = await shop.query(sql`SELECT id, email FROM customers`, { schema: Customer });
// customers: { id: string; email: string }[]

const one = await shop.queryOne(sql`SELECT id, email FROM customers WHERE id = ${id}`, { schema: Customer });
// one: { id: string; email: string } | null
```

`query<T>(sql)` with a type argument still works. The argument is an unchecked assertion, so prefer `schema` where the shape matters.

**Runtime only.** Construct the block at module scope. Call the data methods only inside an `ApiNamespace` method, a `RawRoute` handler, a job handler, or a runtime script. Top-level code also runs during CDK synth, where every data method throws. Every `ApiNamespace` method is a public endpoint, so gate it with `await auth.requireAuth(context)` from an auth block.

## Options

An option goes on the cluster if every block on that cluster must share it, and on the block otherwise.

Cluster options:

| Option | Type | Description |
|---|---|---|
| `type` | `'dsql'` | Required. Aurora DSQL; a second kind is planned. |
| `removalPolicy` | `'retain' \| 'destroy'` | What happens to the cluster when it leaves the stack. When omitted, the stack-wide `defaults` apply: `production` retains with deletion protection on, `sandbox` destroys. Data stays on the cluster when a block is renamed or moved; see the callout in [Quick start](#quick-start). |

Block options:

| Option | Type | Description |
|---|---|---|
| `cluster` | `DatabaseCluster` | The cluster to run on. Omit it and the block owns a `dsql` cluster. |
| `migrationsPath` | `string` | Directory of `.sql` files, relative to the project root. Defaults to `./aws-blocks/migrations/{id}`. The default may be missing; an explicit path must exist. |
| `schemaName` | `string` | The PostgreSQL schema for this block's tables. `public` when the block owns its cluster, otherwise the block id as a PostgreSQL identifier (lower-cased, `_` for other characters). Two blocks on one cluster cannot share a schema. |
| `removalPolicy` | `'retain' \| 'destroy'` | Only when `cluster` is omitted. With a shared cluster, set it on the `DatabaseCluster`. |
| `logger` | `ChildLogger` | Logger for internal operations. Defaults to a `Logger` at error level. |

`Database` and `DatabaseCluster` ids are unique per app. A second block with the same id is an error at construction.

## Sharing a cluster

```ts
const shared = new DatabaseCluster(scope, 'shared', { type: 'dsql' });
const audit = new Database(scope, 'audit', { cluster: shared });
const search = new Database(scope, 'search', { cluster: shared });
```

The `DatabaseCluster` provisions the cluster. Each `Database` on it gets a schema named after its id, with its own migrations and tables. An unqualified table name resolves to the block's schema: ``audit.query(sql`SELECT * FROM events`)`` reads `audit.events`, and the same text on `search` reads `search.events`. Locally the cluster is one PGlite with the same schemas.

**Isolation is by namespace, not by permission.** Both blocks connect as one role that has DML on every schema on the cluster. Qualified table names and joins across schemas work from any block on the cluster. The schema is a naming convention that keeps two blocks' tables apart. It is not a boundary between tenants or trust levels. A block that must not see another block's data belongs on its own cluster.

**Why share.** For one migration pipeline instead of one per block, for queries across the blocks' tables, or to use one [cluster quota](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html) slot instead of one per block. Keep separate clusters when the blocks have different lifecycles: the removal policy is set on the cluster, blocks on one cluster migrate one at a time, and a block cannot move to another cluster later without you copying its data.

## Migrations

Your `Database` runs on Aurora DSQL, so write its migrations in DSQL, as the AWS documentation shows them: [DDL and distributed transactions](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-ddl.html), [`CREATE TABLE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/create-table-syntax-support.html), [`ALTER TABLE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/alter-table-syntax-support.html), [`CREATE SEQUENCE`](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/create-sequence-syntax-support.html) and [Asynchronous indexes](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-create-index-async.html). What is in the file is what runs on the cluster. Every file is checked with [`dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint) before anything runs (see [What is rejected](#what-is-rejected)).

Each block has one directory of `.sql` files, `./aws-blocks/migrations/{id}` unless `migrationsPath` says otherwise. Block ids are unique per app because they name this directory and, on a shared cluster, the block's schema. Files run in name order, once each:

```
aws-blocks/migrations/
  shop/
    001_init.sql
    002_orders_customer_index.sql
  audit/
    001_events.sql
```

### Coming from PostgreSQL

Most DDL is the same on DSQL. Four spellings differ: `SERIAL`, a plain `CREATE INDEX`, an `ADD CONSTRAINT` without `NOT VALID`, and a sequence without a cache. The first `npm run dev` stops on each and prints the DSQL form (see [What is rejected](#what-is-rejected)).

To convert an existing PostgreSQL or `pg_dump` file once, run `npx dsql-lint --fix old.sql -o 001_init.sql` and review the output. The binary is installed with the block. If `npx` cannot find it, run `node_modules/@aws/dsql-lint/bin/dsql-lint`. Exit code 3 means it fixed everything but changed a meaning, such as an index becoming asynchronous. It writes `CACHE 1` (see below), and it adds `NOT VALID` to constraints without the `ALTER TABLE ASYNC … VALIDATE CONSTRAINT` that validates existing rows; add that statement yourself.

**Identity columns and sequences** need a cache. `CACHE 65536` gives each session a local block of values: fast inserts, unique values, but gaps and out-of-order values. `CACHE 1` keeps values close to sequential at one round trip per value. The lint error repeats this trade-off when a cache is missing.

**Changes DSQL cannot express** are adding a column with a `DEFAULT` or `NOT NULL`, and `ALTER COLUMN … SET NOT NULL` or `… TYPE`. To add a constrained column:

1. Add the column without the constraint.
2. Backfill existing rows with `UPDATE … WHERE c IS NULL`, in batches of at most 3,000 rows (the per-transaction limit).
3. Switch your queries.

To change a column's type: add a new column, copy the values in batches, switch your queries, then drop the old column.

You do not need to write `sys.wait_for_job(…)` after an `ASYNC` statement; the block waits for the job. A wait copied from the AWS examples runs anyway (see [Local mode](#local-mode)).

On DSQL the rows an `ON DELETE CASCADE` foreign key deletes count toward the 3,000-row transaction limit. A delete that fans out past it fails whole. Prefer `NO ACTION` or `RESTRICT` for unbounded parent-child relationships.

### What is rejected

Every file is checked with [`dsql-lint`](https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint) at `npm run dev` and at `cdk synth`, before any deploy, for what DSQL cannot run (triggers, extensions, policies, `TRUNCATE`, array columns) and for the PostgreSQL spellings of DSQL forms. Nothing is rewritten for you. The error names the file, the rule, dsql-lint's suggestion and the DSQL documentation page:

```
DsqlMigrationValidationError: Migration validation failed for Aurora DSQL (cluster kind 'dsql'):
  001_init.sql: serial_type: Column `id` uses SERIAL, which is not supported in DSQL. Use `BIGINT GENERATED BY DEFAULT AS IDENTITY (CACHE 1)` instead. CACHE 65536 avoids a coordination round trip per value (values can have gaps); CACHE 1 keeps them close to sequential. Checked against https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility.html
  002_index.sql: index_async: CREATE INDEX without ASYNC is not supported in DSQL. Index: orders_customer Use `CREATE INDEX ASYNC ...` instead. Checked against https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility.html
```

`dsql-lint` is a native binary installed as an optional dependency of `@aws/dsql-lint`. If your package manager skipped optional dependencies, run `npm install @aws/dsql-lint --include=optional`, or point `DSQL_LINT_PATH` at a build.

### How migrations deploy

Locally, a block applies its pending files before its first query. On AWS they run during `cdk deploy`, before any function on the stack is updated, so new code never runs against the old schema. Blocks on one cluster migrate one at a time.

If a deploy fails in a migration, the error names the file and the failed statement. Fix the cause and deploy again; the file resumes where it stopped. A failed index build or constraint validation usually means the data does not satisfy it: fix the rows, then deploy again. Do not edit a file that has partly run. The next deploy detects the edit, refuses the file and names it. Put the change in a new file instead.

## Transactions

DSQL uses [optimistic concurrency](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-concurrency-control.html): a transaction never waits on a lock. Two transactions that change the same row both run to the end. Then one commit fails with `SerializationFailure` (SQLSTATE `40001`, HTTP 409, flagged retriable). `SELECT … FOR UPDATE` is supported and makes a read conflict with concurrent writes, which is how a read-modify-write stays correct.

- Pass `{ retryOnConflict: true }` to re-run the callback on a conflict. It is off by default because a callback may have side effects. `maxRetries` defaults to 3. A single `query` or `execute` outside a transaction is always retried (see [Errors](#errors)).
- A transaction may change at most 3,000 rows (cascaded deletes included) and 10 MiB of data. Past either it fails with `TransactionRowLimitExceeded` and nothing is kept. Split bulk work into batches.
- A throw inside the callback rolls the transaction back. An `ApiError`, a branded Blocks error or a `DatabaseErrors` error reaches the caller unchanged. Any other error becomes `TransactionFailed` and its text stays on the server.
- Inside the callback, `shop.query()`, `shop.queryOne()` and `shop.execute()` on the block that opened the transaction run in it, as `tx` does. Prefer `tx`: it shows the transaction where the statement is written.

```ts
import { ApiError } from '@aws-blocks/core';

// Safe to re-run: the callback reads, decides, writes, and has no side effects outside the database.
await shop.transaction(async (tx) => {
  const row = await tx.queryOne<{ total: number }>(sql`SELECT total FROM orders WHERE id = ${orderId} FOR UPDATE`);
  if (!row) throw new ApiError('no such order', 404); // the client receives a 404
  await tx.execute(sql`UPDATE orders SET total = ${row.total + delta} WHERE id = ${orderId}`);
}, { retryOnConflict: true });
```

For tests, `simulateConflict(shop)` from `@aws-blocks/bb-database/testing` makes the next commit fail with `SerializationFailure` in local mode. It throws in the Lambda runtime.

## Errors

Query and transaction failures carry a `DatabaseErrors` name. Match them with `isBlocksError(e, DatabaseErrors.X)` on the server or the client. Only the name and a message free of row values cross the wire; the driver error stays on the server. Three kinds of error are not for `catch`: setup mistakes (`DatabaseConfigurationError`: a duplicate id, a missing `migrationsPath`), `dsql-lint` findings (`DsqlMigrationValidationError` in a file, `DsqlValidationError` in a handler's statement), and migration failures (`MigrationFailedException`). Fix the cause.

| Error | When | Retried automatically |
|---|---|---|
| `QueryFailed` | Any other SQL error, including a foreign-key or check violation | No |
| `ConnectionFailed` | The connection to the cluster failed or was lost (SQLSTATE class `08`) | A single `query` or `execute`: once, on a fresh connection. Inside a transaction: no |
| `TransactionFailed` | The callback threw an error that is not an `ApiError`, a Blocks error or a database error, or a statement reached the transaction after it ended (a promise the callback did not await) | No |
| `UniqueConstraintViolation` | SQLSTATE `23505` (HTTP 409) | No |
| `SerializationFailure` | SQLSTATE `40001`, usually at commit (HTTP 409, retriable) | A single `query` or `execute`: three times. A `transaction()` callback: only with `retryOnConflict: true` |
| `TransactionRowLimitExceeded` | More than 3,000 rows changed (cascades included) or more than 10 MiB written in one transaction, locally and on DSQL (SQLSTATE `54000`) | No; split the work |
| `ResultValidationFailed` | A row did not match the `schema` passed to `query()` or `queryOne()`. The message, which reaches the client, names the row index and the first issue's path; the library's issue messages stay on the server-side `cause` | No; fix the schema or the query |

```ts
import { isBlocksError } from '@aws-blocks/core';
import { DatabaseErrors, sql } from '@aws-blocks/bb-database';

try {
  await shop.execute(sql`INSERT INTO customers (id, email) VALUES (${id}, ${email})`);
} catch (err) {
  if (isBlocksError(err, DatabaseErrors.UniqueConstraintViolation)) return { conflict: 'email already registered' };
  throw err;
}
```

## Local mode

`npm run dev` needs no AWS account. Each cluster is one PGlite (PostgreSQL compiled to WebAssembly) under `.bb-data/`, with one schema per block, as on AWS.

A `dsql` cluster adds DSQL's checks locally: `dsql-lint` on every handler statement (cached per statement text), no DDL outside a migration, and the 3,000-row and 10 MiB transaction limits (see [Transactions](#transactions)). Unsupported SQL fails on your machine, not in production.

Your DSQL migration files run unchanged. `ASYNC` index builds and constraint validations complete at once, and a `sys.wait_for_job(…)` copied from the AWS examples returns immediately.

| | Owned default | `DatabaseCluster` |
|---|---|---|
| Engine | PGlite with `dsql-lint` and the DSQL limits | One PGlite per cluster, one schema per block, same checks |
| Data | `.bb-data/{fullId}/pglite/` | `.bb-data/{clusterFullId}/pglite/` |
| Migrations | Before the block's first query | Same, per block, into its schema |

PGlite has one session, so local work on a cluster runs one statement or transaction at a time. Bugs that need two requests to overlap do not reproduce locally; `simulateConflict()` from `@aws-blocks/bb-database/testing` covers the retry path.

A call to another block on the same cluster from inside a `transaction()` callback behaves differently in the two places. Locally it runs inside the transaction and rolls back with it. On DSQL it runs on its own connection and commits on its own. Write such a call so both outcomes are acceptable, or move it after the transaction.

Tests that call gated methods through the dev server need the auth cookie to persist between requests. Call `installCookieJar()` from `@aws-blocks/blocks/utils` once at the top of the test file.

## What it provisions (AWS)

Per cluster, whether a block owns it or a `DatabaseCluster` declares it:

- **One Aurora DSQL cluster** (`AWS::DSQL::Cluster`). IAM token authentication; no VPC, no secret, no security group, no proxy. Deletion protection follows the stack `defaults`.
- **Two migration Lambdas** (`onEvent` and `isComplete`), one log group, and a custom-resource provider that waits for DSQL index and validation jobs for up to 55 minutes.
- **IAM:** the app's execution role gets `dsql:DbConnect` on the cluster; the migration Lambdas get `dsql:DbConnectAdmin`.
- **Config:** `BLOCKS_{CLUSTER_ID}_ENDPOINT` and `BLOCKS_{CLUSTER_ID}_REGION` (the cluster's full id upper-cased, with `_` for other characters), injected through the config bucket.

Per block: one CloudFormation custom resource that applies its migrations, and one S3 asset with the migration files when it has any. The migration Lambda also creates a per-cluster database role for the app, maps it to the execution role with `AWS IAM GRANT`, and grants it `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the block's tables, `SELECT` on its views, and `USAGE, SELECT` on its sequences. DDL needs the admin token, which only the migration Lambdas hold.

**Cost.** See [Aurora DSQL pricing](https://aws.amazon.com/rds/aurora/dsql/pricing/). The migration Lambdas run only during deploys. A `Database` that owns its cluster takes one slot of the account's [cluster quota](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html); blocks on a shared `DatabaseCluster` take one together.

## Access through the AWS SDK

`getSdkIdentifiers(db)` from `@aws-blocks/core` returns the block's `clusterId` and `schemaName`. In a deployed Lambda it also returns the cluster's `clusterEndpoint` and `region`, which is what a `DsqlSigner` needs to open your own `pg` connection as the same role. The umbrella's typed overloads do not know this block yet, so the result is a `Record<string, string>`.

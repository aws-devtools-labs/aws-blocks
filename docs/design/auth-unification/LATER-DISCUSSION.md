### 🟡 L9 — Cookies on API error responses (A1b + A1c merged)

### 🟡 L12 — `bb-auth` gate: hover shows the `ERROR_…` name on the wide `Auth` type (from D1)
On TypeScript 5.9 the compiler never prints a tuple *label* in an arity error, so the strategy doc's "the tuple label becomes the editor diagnostic" is wrong as written. D1 fixed it: the gate absorbs the method's trailing optional parameters, and the rest parameter is *named* `ERROR_emailPassword_is_disabled_on_this_Auth_instance`, so a disabled call reports that name — proven by a test that drives the TypeScript compiler API. The cost: on the **wide** `Auth` type (`O = AuthOptions`), `emailPassword` is `boolean`, so the password gate is a union and hovering a method shows the `ERROR_…` alternative. The alternative (treat wide as enabled) makes `emailPassword: false` instances not assignable to `Auth`, which is the variance regression that broke `AuthCognito` before. **Assumption:** keep the union; revisit in D5 once real methods exist, if the hover reads badly in practice.

*Update from D5b:* the same trade-off now applies to the MFA and passkey gates. On the wide `Auth` type they are open (callable), with the runtime 409 behind them, because a closed `[never]` gate can't be compared against a generic `Auth<O>`'s unresolved gate, and the ported AWS harness relies on assigning `Auth<O>` to `Auth`. Concretely, `new Auth(scope, id)` with **no options at all** can call `setUpTotp` / passkey methods at compile time and gets a runtime error. Any options object that omits `mfa` or sets it to `'off'` is still a compile error. Pinned by `types-test.ts` case 17.

### 🟡 L14 — Disabled/deleted users are detected at next session refresh, not per request (from D5a)
`requireAuth` sees that a user was disabled or deleted only when their session next refreshes — up to the access-token lifetime (default 60 min). `AuthCognito` has the same limitation (documented in its `DESIGN.md`). Detecting it per request would cost a Cognito call on every authenticated request. **Assumption:** keep it as-is and make `requireAuth`'s JSDoc truth table say exactly this (D5c). `requireRole` already fails closed for a *deleted* user (live group read → 403). For a hard cap, lower the access-token validity. Override if you want a per-request liveness check.

### 🟡 L15 — Transient refresh failures keep the session (from D5a; differs from `AuthCognito`)
When refreshing tokens fails *transiently* (network, throttling, a Cognito 5xx), `Auth` keeps the session and returns a retriable 5xx; `AuthCognito` deletes the session and signs the user out. A definitive failure (revoked or invalid refresh token) still deletes the session in both. **Assumption:** keep `Auth`'s behaviour — a Cognito blip shouldn't sign every active user out. Noted because it's a behaviour change from `AuthCognito`.

### 🟡 L17 — `addPropertyOverride` bypasses the immutability guard (from D4)

### 🟡 L18 — Federated templates aren't deterministic: a `Date.now()` nonce re-registers IdPs every deploy (from D3b)
IdP registration runs as a deploy-time custom resource, because CloudFormation can't pass `ssm-secure` values to Cognito IdP `ProviderDetails` or to custom resources ([AWS docs](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-ssm-secure-strings.html)). To pick up a rotated provider secret, `bb-auth-oidc` triggers it with a `Date.now()` nonce, so every federated synth differs and every deploy re-registers the IdPs. D3b kept that behaviour. Only federated configs are affected; the default and direct-only templates stay deterministic, so B1/D3a/D4 are unaffected. **Assumption:** keep it for parity with what `AuthOIDC` deploys today. Alternative: a content hash of the secret parameters' *versions*, resolved at deploy time — deterministic synth, but rotation is only picked up when the version changes. Worth deciding before GA.

### 🟡 L21 — Local sign-out doesn't revoke the refresh token (from D5c)
Local (non-global) `signOut()` deletes the server-side session row and clears the cookie, but doesn't call Cognito `RevokeToken`, so the refresh token stays valid in Cognito until it expires (30 days by default). That matches `AuthCognito`. The refresh token lives only in the deleted session row, so exploiting it needs a copy taken from the session store beforehand. **Assumption:** keep parity (no extra call). Revoking would be a cheap hardening step — override if you want it.

### 🟡 L23 — Pipeline stages that reuse a stack id share one baseline directory (from D4b)
Baselines live at `baselines/<stack id>/`. A deployment pipeline that deploys the same stack id to several stages (e.g. beta and prod accounts) shares one baseline per block, so stages whose auth config differs would trip layer 1 for each other. Not introduced by this work, and moot when every stage runs the same config (the usual case). **Assumption:** leave it. If stage-specific auth configs become a real need, key the directory by stage as well.

### 🟡 L24 — `admin.revokeUserSessions` now also deletes the user's session rows, via a table scan (from D5b)
`AuthCognito` on AWS only revoked refresh tokens, so a live session kept working until its access token expired. `Auth` additionally deletes that user's rows from the `sessions` table, so revocation is **immediate on both runtimes**. The cost: `KVStore` has no secondary index, so finding a user's rows is a full scan of the sessions table. Admin-only and rare, but O(sessions). **Assumption:** keep it — immediate revocation is what an admin calling "revoke" expects. If session tables get large, add a username index.

### 🟡 L41 — `AuthState.user` carries more on the wire than its type declares (from D7b)

### 🟡 L46 — The PreSignUp trigger must finish within Cognito's 5-second limit (from FX2)

### ✅ ~~R96 — FX59's "no engine text reaches a client" was incomplete: both federation callbacks still quoted the IdP's `error_description` in the message the `<Authenticator>` renders (FX60; reviewer A on FX59/R93, L71)~~
**What reviewer A found.** FX59 (R93) made every engine error reach the client as a fixed, block-authored message per error name, with the raw text logged and the login redacted.

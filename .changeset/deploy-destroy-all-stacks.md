`npm run destroy` now acts on every top-level stack in the app (`cdk destroy --all`), the same selection `npm run deploy` and `npm run sandbox` deploy with, and the `cdk watch` loop of `npm run sandbox` now watches each of those stacks too. Stacks inside a CDK `Stage` are not included. Before, an app with more than one stack could not be destroyed in production: CDK refused with "specify which stacks to use". Examples are an app with `Hosting` given an explicit `env.region` other than us-east-1, which adds a us-east-1 stack for the CloudFront alarm, an app with `Hosting` and a Lambda@Edge function (an edge-runtime route or Next.js middleware) deployed outside us-east-1, which adds an `edge-lambda-stack-*` stack in us-east-1 (that Region must be bootstrapped too), or an app with an extra stack of its own, such as one for an `ec2.Vpc.fromLookup`. The sandbox's `cdk watch` on such an app never redeployed and showed no error. A single-stack app watches and destroys the same stack as before.

`npm run destroy` deletes every top-level stack of the app, dependent stacks first, and CDK prints each stack as it deletes it. Run in a terminal on an app with more than one top-level stack, it first lists the stacks and asks `Delete them? (y/N)`; anything but `y` or `yes` deletes nothing. Pass `npm run destroy -- --force` (the `--` is needed), or the new `force: true` option of `destroy()`, to skip the question. Runs without a terminal (CI, piped, scripts) and single-stack apps delete without asking, as before. New apps' `aws-blocks/scripts/destroy.ts` pass `--force` through; in an existing app, add `force: process.argv.includes('--force')` to the `destroy({ ... })` call to get the flag. If your app also defines a stack you deploy and delete on its own, move it to a separate CDK app before running `npm run destroy`. Resources with a `RETAIN` removal policy are kept, with their data: when a delete attempt fails, `npm run destroy` and `npm run sandbox:destroy` empty only the S3 buckets the stack's delete removes before they retry. A bucket whose `DeletionPolicy` in the deployed template is not `Delete` is no longer emptied (before, a retry emptied every bucket of the stack). Reading that template needs the `cloudformation:GetTemplate` permission; without it, no bucket of the stack is emptied and a warning says so. As with `npm run sandbox:destroy`, the retry finds the buckets of every stack, and checks whether AWS throttled the delete, in each stack's own Region, with the profile and Region CDK uses, and when the Lambda@Edge stack fails to delete because CloudFront still replicates its function, `npm run destroy` says to run it again later instead of retrying.

`npm run console` now uses the stack that has the `ApiUrl` output rather than the first stack in the outputs file, as the deploy and the sandbox do, and all three warn if several stacks have one.

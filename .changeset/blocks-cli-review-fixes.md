fix(blocks): `blocks` output streams, non-interactive runs and usage errors

- `--no-input` and `CI` reach `blocks secret`, `blocks config` and `blocks db pull`: a value prompt that the run cannot show is a usage error (exit 2) naming `--value-stdin`, even on a terminal. A missing key, an unknown subcommand, a missing flag value, an unknown `db` verb (with a suggestion) and an unconfirmed `secret remove --force` also exit 2. The global `--yes` confirms `secret remove --force`, as `--yes` after the command does.
- `--quiet` does not hide the dev server's RPC errors; it sets only `BLOCKS_LOG_LEVEL=quiet`. A `BLOCKS_DEV_QUIET` you set yourself still applies.
- Text output: the CLI runs core with `BLOCKS_LOG_STREAM=stderr`, so progress, CDK milestones, raw CDK output and streamed CloudFormation events go to stderr, and stdout keeps the deployment target, `BLOCKS_DEPLOYED` and the final URLs. `blocks generate spec` follows it too: its progress lines go to stderr, and stdout keeps the `✅ OpenRPC spec written to …` line.
- `blocks deploy` and `blocks sandbox deploy` print no JSON or `--query` result after a failed or interrupted run. The result comes from `.blocks-sandbox/last-deploy.json`, which the deploy runner writes: the stack outputs core read when it deployed, so a concurrent deploy of the other stage that rewrites `.blocks-sandbox/outputs.json` cannot change or empty it, and the account and Region the deploy itself used. When the runner recorded no result, the command exits 1 with an error instead of printing null fields.
- A closed terminal no longer makes `blocks deploy` exit 1 while the deploy goes on: the runners other than the dev server run as `node --import` with the `tsx` loader, with no `tsx` process between the CLI and the runner, and the CLI reports the deploy's own exit code and result.
- Arguments after `--` are rejected with exit 2 (`unexpected arguments after --`) for commands that do not forward them, instead of being dropped.
- `--telemetry-file <path>` (or `--telemetry-file=<path>`) is a global option. The CLI passes it, as an absolute path, to the lifecycle runners, where core's telemetry client reads it, so `npm run dev -- --telemetry-file=/tmp/events.json` captures events as it did with the scripts.
- `blocks sandbox --deploy-only` runs `blocks sandbox deploy`, as a hidden alias of the old script flag.
- `package.json` `"blocks": { "dev": { "frontend": false } }` runs the backend only, as `--no-frontend` does, even when `vite` or `next` is installed. It cannot be combined with `frontendCommand` or `frontendPort`.
- A `--host` or `blocks.dev.host` is also exported to the dev server as `BLOCKS_DEV_HOST`, so the local realtime WebSocket (`/realtime`) accepts that host's origins, as it does for a `BLOCKS_DEV_HOST` you set yourself; a `BLOCKS_DEV_HOST` already in the environment is kept.
- A `package.json` that starts with a UTF-8 byte order mark is read as npm reads it, so `blocks dev`, `blocks dev stop` and the sandbox commands accept it instead of failing with `cannot read …/package.json`.
- Global options apply after `secret`, `config`, `db` and `vendorize` too, up to a `--`: `blocks secret remove KEY --profile prod` deletes in that profile's account, and `blocks config set KEY value --output json` exits 2, instead of the CLI forwarding the options to the tool, which wrote them into the value or a file name, or ignored them. Global options can also sit between the words of a command (`blocks generate --debug client`), and before the command they take the same forms as after it (`-qv`, `-C<dir>`). `--version` after any command prints the version and runs nothing.
- `--output json` and `--query` exit 2 with `… is not supported for "blocks <command>"` on a command without a JSON result, after the command name as before it, and without a command. A single-valued global option given twice with different values (`--cwd a -C b`), `-C` naming a file, `-y=false` and `-C=<dir>` are usage errors; `--port -1` takes `-1` as the value; `blocks --region <bad> help` shows the help.
- `--query` checks the whole path against the command's result before the command runs, so `blocks dev stop --query stopped.0.nope` or `blocks deploy --query apiUrl.x` exits 2 without stopping a server or deploying. A list element is named by its index (`stopped.0.port`); an element past the end of a list, as in an empty `stopped`, prints an empty line.
- The help of a `db`, `secret` or `config` verb (`blocks secret set --help`, `blocks help db pull`) works outside an app too, instead of failing with `not inside an AWS Blocks app`.
- `blocks vendorize` without a package, with two packages or with an option other than `--force` is a usage error (exit 2), with one `Error:` line, instead of the tool's usage and `blocks vendorize failed (exit code 1)`.
- Error hints say only what helps: `Run with --verbose for the full tool output` follows a failed lifecycle runner, whose output `--verbose` extends; a failed `db`, `vendorize` or `generate client` says that the tool's own output is above; `--debug` prints the stack trace of an error the CLI raised itself too. A runner prints a failure's message, and its stack trace only with `--debug`. The command line that `--verbose` echoes is quoted for a POSIX shell, so a path with a space or the runner's JSON options can be pasted back.
- A Ctrl-C that reaches a command after its tool finished (`blocks db migrate` applied every migration and exited 0) reports the tool's success, exit 0, instead of `interrupted` and 130. `blocks dev` and `blocks sandbox`, which exit 0 when Ctrl-C stops them, still exit 130.
- A relative path given to `blocks db` or to `blocks generate types --out`/`--include` is resolved from the directory you run the command in (or `-C`), as `blocks generate client` and `generate spec` already did, instead of from the project root. `blocks db` drops the `--` that ends the CLI's options instead of forwarding it to bb-data as a directory name.
- `blocks generate types` rejects `--check` with `--watch`, and an empty `--out`, `--include` or `--module`, as usage errors (exit 2), instead of passing them to typegen, which failed with exit 1 or wrote an invalid `declare module ""`.
- `blocks generate client <foundation> <output>` and `blocks generate spec <backend> [output]` run outside an app, as `blocks-generate-client` and `blocks-generate-spec` did; only their default paths need one.
- A typo of a hidden alias suggests the canonical command: `blocks consol` suggests `sandbox console`, `blocks typegn` suggests `generate types`.
- A relative `--telemetry-file` is resolved from the directory you run the command in for the commands that run core in the CLI process too (`blocks sandbox console`), instead of from the project root.
- `blocks telemetry enable|disable` outside an app is a usage error that suggests `--global`, instead of writing a `.blocks/config.json` into the current directory; `blocks -C <dir> telemetry` reads `<dir>`, not the shell's directory.
- `blocks destroy` prints the target with `.env.production` applied, as `blocks deploy` and `blocks whoami` do, and core's destroy now uses it too, so all three name the same credentials and Region.
- `blocks destroy` passes the stack it names to core, so destroying a production stack that does not exist (already deleted, or another Region) says there is nothing to delete instead of `✅ Production stack destroyed!`. `blocks sandbox destroy` on a machine with no `.blocks-sandbox/sandbox-id.txt` says there is no sandbox to delete and exits 0, without creating a sandbox id or running cdk.
- An explicit `--profile` wins over access keys in the environment: the CLI empties `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` (and their `AMAZON_` names) for the run, so neither the shell nor a stage env file can make CDK or `blocks whoami` use another account, and says so on stderr. `blocks whoami` prints the same warning as `deploy` and `destroy` when exported keys win over an exported `AWS_PROFILE`.
- `blocks deploy` checks the `--wait-live` budget before anything runs: `--wait-live=SECONDS` and `--wait-live-timeout=SECONDS` take a whole number from 1 to 3600, `--wait-live-timeout` needs `--wait-live`, and the budget is given once. Anything else exits 2, instead of deploying with a warning about the default budget, or silently ignoring the flag.
- `blocks sandbox console` opens this machine's sandbox stack, in the Region it was deployed to (from `last-deploy.json`, else the sandbox's configured Region with `.env.local`), instead of the first stack in `.blocks-sandbox/outputs.json`, which is the production stack after a `blocks deploy`. Without a sandbox id or a recorded deploy of the sandbox it exits 1 and suggests `blocks sandbox deploy`.
- After a successful `blocks sandbox destroy`, the CLI removes the deleted sandbox from `.blocks-sandbox/last-deploy.json` and `outputs.json`, and removes `config.json` when the sandbox wrote it, so `blocks sandbox console` and the frontend no longer point at the deleted stack. The sandbox id and the production records stay.
- Credential, bootstrap and sandbox recovery guidance names the `blocks` command that was run, with its `-C`, `--profile` and `--region`, for example `Then re-run \`blocks deploy --profile prod\`.`, instead of `npm run deploy`, `npm run sandbox` (for `sandbox deploy` too) or `npm run sandbox:destroy`, which an app without those scripts does not have.
- `blocks destroy` refuses, deleting nothing, when the CDK app does not define the `<stackId>-prod` stack it names and asked to delete (for example an older app whose `index.cdk.ts` names its own stack). `blocks deploy` warns when CDK deployed another stack than `<stackId>-prod`. Without a `stackId`, both say which id to choose and add a `Try:` line that lists the existing production stacks.
- `blocks whoami` tells a malformed `.blocks/config.json` (`(invalid .blocks/config.json)`, with the parse error as a warning) from a missing file or a missing `stackId`; `blocks deploy` and `destroy` print the parse error.
- `blocks whoami --profile <name>` for a profile that does not exist says the profile is not in your AWS config, instead of "no AWS Region is set".
- A SIGTERM or SIGHUP sent to the pid of `blocks dev` alone (`kill <pid>`, an IDE stop button, a harness) stops the dev server and its frontend at once, as one sent to its process group does, instead of after 10 s. `blocks sandbox` in watch mode stops at once too.
- `blocks dev` exits 1 with the reason when its dev server fails to start (another dev server owns the port, the bind fails), instead of waiting for a file change forever. Stopping `blocks dev` while its backend is not running (`blocks dev stop` after a crash, or a SIGTERM) exits 0 instead of reporting `failed (exit code 143)`.
- `--port`, `--frontend-port` and the `blocks.dev` ports accept only decimal port numbers from 1 to 65535: `1e3`, `0x10`, `0b…`, `" 41082 "` and `-1` are usage errors (exit 2) that name the value, instead of binding port 1000 or 16.
- `blocks dev stop --all --port N` and `blocks cleanup --port N` are usage errors (exit 2), instead of ignoring `--port` and stopping every recorded dev server.
- `blocks dev stop` reads only `blocks.dev.port`, so it stops the server while another `blocks.dev` setting is invalid. `blocks dev`, `dev stop` and `sandbox` warn about a `blocks.dev` key that nothing reads (a typo such as `prot`), with the nearest setting; `generateClient` is accepted.
- `blocks dev stop` without `--port` stops the only dev server the app recorded when none is recorded on the configured port (a server started with `blocks dev --port 4000`), and says which port. With several recorded, it lists them and points to `--port` and `--all`.
- `blocks dev` and `blocks sandbox` warn when a `frontendCommand` you set (`--frontend-command` or `package.json`) does not contain the frontend port the dev server proxies to, as with a hard-coded `npx vite --port 3100` and `--frontend-port 41079`, which answered 502. The README example config no longer sets `frontendCommand`.
- Ctrl-C or Ctrl-D at the hidden prompt of `blocks secret set` or `blocks config set` exits 130 with `Interrupted; nothing was set.`, instead of exit 13 and Node's "unsettled top-level await" warning.
- `blocks secret set KEY` and `config set KEY` with stdin that is not a terminal say `stdin is not a TTY`, instead of blaming `--no-input or CI` when neither was set.
- A bare `blocks secret` or `blocks config` exits 2 with `needs a verb: set, list or remove` and its help command, instead of `Unknown subcommand undefined`. An invalid key and an empty value exit 2, with no `--verbose` hint.
- `blocks generate client -q` (and `blocks-generate-client` at `BLOCKS_LOG_LEVEL=quiet`) hides the warnings that loading the backend prints, such as `[Realtime] BLOCKS_RT_WS_URL not set`, which say nothing about the generated client.
- `blocks db --help` shows `blocks db migrate aws-blocks/migrations` and `blocks db status aws-blocks/migrations`, the migrations directory of the templates, instead of examples that fail with `Migrations directory not found: ./migrations`. `blocks db <verb> --help` prints `Usage: blocks db <verb> …`, not `Usage: bb-data <verb> …`.
- A SIGTERM, SIGINT or SIGHUP sent to `blocks generate client` (or `blocks-generate-client`) alone reaches the client generator, and the command ends after it, instead of leaving the generator running to write `aws-blocks/client.js` after the command reported a failure.
- `blocks generate client` and `blocks generate spec` report a missing backend the same way, `cannot find the backend entry at <path>.` with exit 1, before anything runs (`generate client` exited 2). A backend that does not load (a syntax error) gives a one-line `❌ Client generation failed: …` with exit 1, as `❌ Spec generation failed: …` does, instead of a raw Node stack trace; both print the stack with `--debug`.
- A `db`, `vendorize` or `generate` tool stopped by a signal fails with `<tool> was stopped by SIGTERM.`, without `its output is above`, which it may not have printed. `blocks generate spec` fails as `blocks generate client` does: `blocks-generate-spec exited with code 1; its output is above.`
- A `blocks dev` startup refusal (another dev server on the port, a port in use) prints its reason once: the runner's `❌` message, then exit 1, without an `Error:` line repeating it.
- `blocks generate spec <backend>` outside an app runs from the backend's directory, so the backend's local mock storage (`.bb-data/`) is not created in the directory you run it from.
- `blocks generate types --out <dir>` naming a directory is a usage error (exit 2), instead of a raw `EISDIR` error.
- `blocks generate client` in an app whose `package.json` sets `"blocks": { "dev": { "generateClient": false } }` (the Amplify overlay) refuses to replace `aws-blocks/client.js`, with exit 2 and the hint `npm run blocks:generate-client`; `--force` writes it anyway.
- A single-valued command option given twice with different values (`blocks dev stop --port 1 --port 2`) is a usage error, as for global options. `blocks dev --port N stop -h` shows the help of `blocks dev stop`, the command the run names. A global value option without a command (`blocks --profile deploy`, where `deploy` became the profile) exits 2 instead of printing the help with exit 0.
- `blocks deploy --wait-live-timeout=0` without `--wait-live` suggests `--wait-live=SECONDS`, not a value `--wait-live` rejects. The `aws cloudformation describe-stacks` hint for a missing stackId passes the run's `--profile` and `--region`.
- A `blocks deploy --wait-live` whose liveness wait fails still records the deploy in `.blocks-sandbox/last-deploy.json` and, with `--output json` or `--query`, prints its result with `"live": false`; it exits 1 with `blocks deploy deployed the stack, but --wait-live could not confirm that the new build is live`, not `blocks deploy failed`. The `blocks deploy` JSON result has a `live` field: `true` when `--wait-live` confirmed the build, `null` without `--wait-live` or a frontend.
- `blocks sandbox` (watch mode) records the sandbox deploy in `last-deploy.json` after its first deploy, as `blocks sandbox deploy` does, so `blocks sandbox console` still opens the running sandbox after a production deploy rewrote `.blocks-sandbox/outputs.json`.
- `blocks dev` exits 1 when its dev server fails on its first start (a backend that throws while it loads, an import that does not resolve, an unreadable file, a malformed `.env.local`), instead of exiting 0: `tsx watch` ignores the runner in `node_modules` and ended by itself. A dev server that dies before anything stopped it (out of memory, `kill -9`) and leaves `tsx watch` with nothing to watch fails too. A failure after a reload still waits for the fix, as before.
- Ctrl-C ends a `blocks dev` whose dev server was killed (`kill -9`, the OOM killer), as a SIGTERM does: `tsx watch` waits forever for a runner that a signal ended, so once no runner is left the CLI SIGKILLs it after 1 s. It exits 130.
- A SIGTERM sent to `blocks` that ends the operation it runs (`blocks sandbox deploy`, `sandbox destroy`, `deploy`, `destroy`; for example core aborts a deploy on a second SIGTERM) exits 143 with `<command> stopped by SIGTERM.`, instead of exit 1 with `failed (signal SIGTERM)` and a `--verbose` hint. A runner that core aborted on the operator's SIGINT exits 130. A runner killed by a signal that `blocks` did not receive still fails with exit 1.
- A `package.json` that is valid JSON but not an object (`null`, `[]`, a string) fails `blocks dev`, `dev stop`, `sandbox` and `generate client` with `<path>/package.json must be a JSON object, not an array.` (exit 1), instead of `Cannot read properties of null`, a dev server on the default port, or a raw `ERR_INVALID_PACKAGE_CONFIG` stack.
- An installed `@aws-blocks/core` that does not match `@aws-blocks/blocks` (an upgrade that kept an older core in the lockfile) fails with `@aws-blocks/blocks <version> cannot load @aws-blocks/core <version>, which does not match it: …` and `Try: reinstall @aws-blocks/core to match @aws-blocks/blocks <version>: npm install '@aws-blocks/core@<range>'`, instead of a raw `ERR_PACKAGE_PATH_NOT_EXPORTED` or `does not provide an export named` stack, also when the CLI itself fails to load. `--version` and `--help` never load core.
- After a successful `blocks destroy`, the CLI removes the deleted production stack from `.blocks-sandbox/last-deploy.json` and `outputs.json`, and removes `config.json` when a production deploy wrote it, as `blocks sandbox destroy` does for the sandbox, so the local client and `--output json` no longer point at the deleted API. The sandbox records stay.
- `blocks sandbox console` opens a sandbox that no record on this machine names (one that the old npm-script wrappers deployed, after a production deploy rewrote `.blocks-sandbox/outputs.json`) when CloudFormation has its stack, looked up with the sandbox's credentials and Region. It refuses only a stack that does not exist, with `the sandbox stack <stack> does not exist in <Region>.`; when the lookup cannot tell (no credentials, no network), it opens the console.
- `Try:` lines and the deploy, sandbox and credential re-run guidance name `blocks` commands as `npx --no -- blocks …`, as the app's AGENTS.md does, so they can be copied into the app's shell, where a bare `blocks` is not on `PATH` (exit 127). The `--all --port` refusal suggests `npx --no -- blocks dev stop --all` instead of the hidden `blocks cleanup` alias.

Production `cdk deploy` now passes `--revert-drift` **only when the target CloudFormation stack already exists AND is in an updatable state** (i.e. its next deploy is an UPDATE change set), reconciling configuration drift (e.g. introduced by the `cdk watch`/hotswap dev loop) against the template. It is **omitted on a first/CREATE deploy** — and likewise omitted for stacks that resolve in `DescribeStacks` but still deploy as CREATE (`REVIEW_IN_PROGRESS` = a change set was never executed; `ROLLBACK_COMPLETE` = a failed initial create that must be recreated; any `DELETE_*` = gone or going): `--revert-drift` maps to the CloudFormation REVERT_DRIFT deployment mode, which is allowed only on UPDATE change sets — CFN rejects it on CREATE ("Change set of type CREATE is not supported for change sets with deployment mode REVERT_DRIFT"). The deploy resolves this by checking the stack's status (best-effort/fail-safe: on any error it omits the flag rather than breaking the deploy). The sandbox/dev-loop path is unchanged.

Requires an `aws-cdk` CLI new enough to expose `--revert-drift`; the pinned `^2.1138.0` is the validated floor (`--revert-drift` is unavailable on older CLIs, where it would surface as an unknown option). A hermetic real-CDK probe runs the UPDATE-deploy argv — `--revert-drift` included — against exactly that pinned CLI and asserts it parses (reaching the credential check, not an unknown-option error), so the flag is proven accepted rather than merely present in the argv.

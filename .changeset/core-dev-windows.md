fix(core): the dev server's stop, reload and port reclaim on Windows

- On Windows, the dev server finds a listener on an IPv6 address too (`[::1]`, where a `localhost` Vite binds), and on a Windows that does not say `LISTENING`: it reads `netstat -ano`, which lists TCP and TCPv6, instead of `netstat -ano -p tcp`, which lists IPv4 only. Before, a port that the frontend held was reported as `in use (its owner could not be found)`.
- On Windows, the dev server records its frontend too: the processes of the frontend's tree that listen on its port, with their creation times, since Windows has no process groups. A `tsx watch` restart on a backend save, or a hard kill of `blocks dev` (`Stop-Process`, Task Manager), leaves the frontend (Vite and esbuild) running, because a process that a shell started outlives its parent there. The next dev server now reclaims the port from that frontend, and `blocks dev stop` stops it, instead of failing with `port 3100 is in use (its owner could not be found)`. A pid that Windows has since given to another process is never stopped.
- On Windows, `blocks dev stop` and `blocks dev stop --all` end the whole `blocks dev` session: the dev server records the `blocks dev` CLI at the top of its session, and the stop ends that CLI with its whole tree (`taskkill /T /F`), then waits for the ports to be free and removes the pidfile. Before, it ended only the dev server: the CLI and `tsx watch` kept running, and the next save started the dev server again. The CLI is ended only while the recorded `tsx watch` still descends from it (CIM's parent pids and creation times), else the `tsx watch` while the dev server descends from it, so a pid that Windows has given to another process is never ended. On POSIX the stop is unchanged.
- On Windows, a dev server that fails its first start (its port held, another dev server of the app running, a listen error) ends its `tsx watch` too, so `blocks dev` exits 1 after the error instead of hanging: `blocks dev` tells the dev server that it runs under `tsx watch` (`BLOCKS_DEV_UNDER_WATCH=1`), which it could not read from its parent's command line there.
- On Windows, the hints of a port that stays in use name Windows commands: ``Stop it with `taskkill /PID <pid> /T /F` `` and ``Find the process that holds it with `netstat -ano | findstr :<port>` ``, instead of `kill` and `lsof -i`.

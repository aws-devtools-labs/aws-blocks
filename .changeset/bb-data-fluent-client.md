Add `@aws-blocks/bb-data/fluent`: a typed, schema-aware query client for everyday reads and writes.

```ts
import { createDataClient } from '@aws-blocks/bb-data/fluent';
import { tableMeta, type TableMeta } from './schema/database.meta.js';

const data = createDataClient<TableMeta>(db, tableMeta);

const notes = await data.from('notes')
  .select('id', 'text')        // result narrows to { id, text }
  .eq('done', false)
  .order('created_at', 'desc')
  .limit(20);

await data.from('notes').insert({ text: 'hello' });
await data.from('notes').update({ done: true }).eq('id', 1);
await data.from('notes').delete().eq('id', 1);
```

Table and column names are checked against the schema generated by `@aws-blocks/bb-data/schema-sync`, so a migration rename that breaks a query is a compile error. Values are always parameterized and identifiers are validated against the schema at runtime as well.

Behaviour worth knowing:

- **Writes require a filter.** `update()` and `delete()` throw unless narrowed, so a forgotten `.eq(...)` cannot rewrite or empty a table.
- **Errors throw** rather than being returned as a tuple; `first()` returns `null` when nothing matches, because not-found is ordinary control flow.
- Queries are real promises — `.catch()`, `.finally()` and `Promise.all` all work — and execute once however often they are awaited.
- `insert()` accepts exactly what Postgres will: server-managed columns are rejected, columns with a default or that are nullable are optional, the rest required.

`db.crud()` covers similar ground and remains supported. New code should prefer the fluent client, which checks column names and narrows result types.

Generated table metadata now includes an `optional` list (columns with a default or that are nullable). This is additive: existing consumers are unaffected, and regenerating picks it up.

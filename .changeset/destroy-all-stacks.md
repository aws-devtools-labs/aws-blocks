`npm run sandbox:destroy` now removes every stack the sandbox deploy creates (`cdk destroy --all`, the same selection `npm run sandbox` deploys with). Before, a sandbox app with more than one stack, such as one with a separate stack for an `ec2.Vpc.fromLookup`, or with `Hosting` and a Lambda@Edge function (an edge-runtime route or Next.js middleware) deployed outside us-east-1, which adds an `edge-lambda-stack-*` stack, could not be torn down: CDK refused with "specify which stacks to use", and the command failed after its retries without deleting any stack. Every top-level stack the app synthesizes in sandbox mode is deleted, dependent stacks first, including a stack you add yourself, and CDK prints each stack as it deletes it. Give such a stack a name derived from the sandbox's stack name, so it is not shared with production or other sandboxes, and don't create a stack in sandbox mode if it must outlive the sandbox.

When a delete attempt fails, the S3 buckets that are emptied before the retry, and the stack events that tell whether AWS throttled the delete, are now read from every stack of the app, each looked up in its own Region (the edge stack is in us-east-1) with the profile and Region CDK uses (`cdk.json`, `AWS_DEFAULT_PROFILE`), instead of only the stacks `cdk ls` names, with the SDK's default Region. A Lambda@Edge function can only be deleted after CloudFront removes its replicas, which can take a few hours: when the edge stack fails to delete for that reason, the command now says so and stops instead of retrying; run `npm run sandbox:destroy` again later. The destroy also passes the same `projectRoot` as the sandbox deploy, so both resolve the same stack names.
